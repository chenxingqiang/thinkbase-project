\begin{abstract}
Large Language Models are increasingly deployed as autonomous agents,
yet their behavior is orchestrated through ad-hoc prompt engineering and
per-provider function calling, making it difficult to specify, analyze,
and optimize systematically. We present AgentISA, an instruction set
architecture that treats agent behavior as a first-class compilable
artifact: (1) a formal instruction set with compositional semantics, a
type system, and pre/post-conditions---checked offline for pure
instructions by a shipped bounded verification checker and bracketed at
runtime by pre-dispatch context validation; (2) Agentic Calling, lifting
provider-specific function calling into reusable, cacheable
instructions; (3) instruction learning that mines recurring patterns
from traces and promotes them as composite-replay instructions; and (4)
a compiler and runtime applying classical optimization---fusion,
dead-code elimination, pipeline scheduling, and dynamic hot-path
specialization---to agent instruction streams.

We evaluate AgentISA on four fronts. A reproducible microbenchmark suite
drives the real compiler, cache, and optimizer against a mock LLM
backend: result caching reduces simulated API calls by 59.5--79.6\% on
synthetic Zipf workloads (2,000 tasks, 5 seeds), a saving that grows
with skew; static compilation reduces the effective instruction count by
34.2\% (35.4\% at sequence length 1,000), with an independent-draw
ablation attributing the shrink to fusion and dead-code elimination (a
replication, not a decomposition; Section 5.5); dynamic hot-path
optimization shrinks repeatedly executed traces by 65.8\%. Two
real-gateway experiments extend the validation beyond the mock: the
cache reproduces the computed hit/miss statistics at every skew level
and converts avoided calls into measured wall-clock and token savings,
and the compiled, hot-path-adopted stream issues zero new gateway calls
with byte-identical artifacts (cache-mediated). A four-task system-level
characterization (12.5--25.0\% per-task compile shrink) calibrates the
synthetic headline, and 43 multi-agent coordination and security tests
provide functional validation. We position these results as
controlled-setting evidence, not as production end-to-end measurements.
\end{abstract}

\section{Introduction}\label{introduction}

Recent advances in Large Language Models (LLMs) have produced systems
with strong natural language understanding, generation, and---through
instruction tuning and human feedback---instruction-following
capabilities {[}1, 2, 3, 4, 5, 6{]}. Building on these capabilities, a
rapidly growing body of work couples LLMs with tools, memory, and
control loops to construct autonomous agents {[}9, 10, 11, 12{]}. Yet
the engineering substrate beneath these agents remains largely ad hoc:
behaviors are specified as prompts and provider-specific
function-calling schemas, which are difficult to specify precisely,
analyze formally, or optimize systematically.

\subsection{Background and Motivation}\label{background-and-motivation}

Function calling---selecting an API from a declared tool set and
emitting structured arguments---has become the dominant interface
between LLMs and external systems {[}13, 14, 15{]}. Standardization
efforts such as the Model Context Protocol {[}18{]} are consolidating
this interface layer, while evaluation harnesses such as the Berkeley
Function Calling Leaderboard {[}17{]} measure it. However, the unit of
interaction remains the individual API call: each call is dispatched,
priced, and forgotten independently, even when an agent repeatedly
executes structurally identical work.

This per-call statelessness stands in sharp contrast to how computing
systems have historically handled repetitive execution. Classical
compilers and hardware translate recurring patterns into cheaper
forms---instruction fusion, dead-code elimination, caching, and
trace-based dynamic optimization {[}33, 34, 45{]}. Our motivating
hypothesis is that these same techniques apply to LLM agent workloads:
if agent behavior is expressed as an explicit instruction stream rather
than as opaque prompts, then recurring patterns become visible to a
compiler and can be optimized with well-understood, semantics-preserving
transformations.

\subsection{Challenges in Current LLM-based Agent
Systems}\label{challenges-in-current-llm-based-agent-systems}

Five structural challenges motivate AgentISA:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Per-call statelessness of tool interfaces.} Mainstream
  function-calling and tool-use protocols treat each call as an isolated
  event {[}13, 14, 18{]}. The provider has no notion of a \emph{program}
  being executed, so repeated identical work incurs repeated cost;
  caching, when present, is a bolt-on afterthought rather than a
  semantic property of the execution model.
\item
  \textbf{Experience that does not accumulate as compiler-visible
  instruction structure.} Agent paradigms such as Reflexion {[}10{]} and
  Voyager {[}12{]} do accumulate experience, but as verbal reflections
  or skill libraries consumed by the model at inference time. The
  lessons are not reified as reusable, statically optimizable
  instructions that a compiler can fuse, schedule, or eliminate.
\item
  \textbf{Absence of a shared behavioral contract.} Each multi-agent
  framework defines its own abstractions for roles, messages, and
  workflows {[}19, 20, 21, 22, 23, 24{]}. There is no instruction-level
  contract that is independent of any single framework, which fragments
  tooling and makes cross-framework analysis difficult.
\item
  \textbf{Cost pressure at the wrong layer.} FrugalGPT {[}28{]}
  demonstrates that LLM inference cost is a first-order concern, and the
  serving-systems community has attacked this below the API boundary
  with paged attention, continuous batching, KV-cache-centric
  architectures, and attention kernels {[}38, 39, 40, 41{]}. What is
  missing is the complementary, above-the-API layer: reducing the
  \emph{number and size} of calls an agent issues in the first place.
\item
  \textbf{Integration complexity across providers.} Portability across
  LLM providers is handled today primarily at the library level {[}26,
  27{]}. Agent logic written against one provider's function-calling
  surface does not transfer cleanly to another, and capability
  differences between providers are hard to reason about systematically
  {[}17{]}.
\end{enumerate}

\subsection{Research Objectives and
Contributions}\label{research-objectives-and-contributions}

This paper introduces AgentISA, an instruction set architecture that
addresses these challenges by making agent behavior a first-class
compilable artifact. Our contributions are:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{A formal instruction set} for LLM agents with compositional
  semantics, a type system, and pre/post-conditions on every instruction
  (Section 3.1). Two deliberately modest sanity results are stated as
  design rationale rather than headline novelty: Turing completeness
  (Theorem 3.1), read as negative certification that the instruction set
  does not constrain expressiveness, and type safety for the pure core
  (Theorem 3.2), which fixes the well-formedness obligation that the
  offline bounded checker discharges for pure instructions (Section
  3.3.3) and that the runtime brackets with pre-dispatch context
  validation.
\item
  \textbf{Agentic Calling}, a mechanism that lifts provider-specific
  function calling into reusable, cacheable, semantically specified
  agent instructions, with a model-adapter layer for cross-provider
  portability (Section 3.2).
\item
  \textbf{Automatic instruction learning}, which mines recurring
  instruction patterns from interaction traces using frequency-based
  sequence mining and deterministic behavior grouping, and promotes
  validated recurring patterns into candidate instructions whose
  \texttt{execute} bodies replay the mined constituent instruction
  sequence by sequential composition over a shared context (Section 3.3;
  replay reproduces the recorded subsequence's outputs on the same
  inputs and does not generalize beyond them, as the section states).
\item
  \textbf{A compiler and runtime} that apply instruction selection,
  fusion, dead-code elimination, pipeline scheduling, and dynamic
  hot-path specialization to agent instruction streams (Sections 3.4 and
  4), with semantic-preservation arguments for each transformation
  (Theorems 3.4--3.6, proofs in Appendix C).
\item
  \textbf{An empirical evaluation} of the implemented system, with full
  methodology disclosure. On synthetic Zipf-distributed workloads (5
  random seeds each), caching reduces simulated API calls by
  59.5--79.6\% depending on skew, static compilation reduces the
  effective instruction count by 34.2\% \(\pm\) 1.8\% (sequence length
  200), and dynamic optimization shrinks repeatedly executed traces by
  65.8\% \(\pm\) 4.6\%. Two real-gateway experiments (Sections 5.7 and
  5.7.1) validate the cache and the compiled pipeline against a real LLM
  gateway, and a four-task system-level characterization (Section 5.8)
  composes the mechanisms on realistic (non-synthetic) instruction
  streams.
\item
  \textbf{Multi-agent coordination infrastructure} with capability-based
  agent selection, execution planning, fallback strategies, and a
  security monitor enforcing authentication, authorization,
  resource-access, and data-sensitivity policies (Section 3.5 and
  Section 5.6), validated by 43 passing functional tests.
\end{enumerate}

Our empirical claims are scoped accordingly: Sections 5.2--5.5 exercise
the real \texttt{agentflow.core.isa} implementation against a mock LLM
backend on synthetic workloads, and Sections 5.7--5.8 extend the
validation at reduced scale on realistic streams. None of these are
production end-to-end measurements (threats to validity in Section 5.9).

The rest of this paper is organized as follows: Section 2 reviews
related work. Section 3 details the design of AgentISA. Section 4
describes the implementation. Section 5 presents the empirical
evaluation. Section 6 discusses limitations and future work, and Section
7 concludes.

\section{Related Work}\label{related-work}

AgentISA draws on eight lines of work: foundation LLMs and their
function-calling interfaces, reasoning-and-acting agent paradigms,
tool-calling standardization, multi-agent frameworks, prompt compilation
and cost optimization, agent benchmarks, classical compiler and
architecture techniques, and LLM serving systems. We review each in turn
and position our contributions.

\subsection{Foundation LLMs and Function
Calling}\label{foundation-llms-and-function-calling}

Modern LLMs are autoregressive transformers trained at large scale {[}1,
2, 3, 4{]}, with instruction tuning and reinforcement learning from
human feedback making them reliable instruction followers {[}5, 6{]}.
Their text distribution is conventionally factorized as:

\[
P(y|x) = \prod_{t=1}^{T} P(y_t|x, y_{<t}; \theta)
\]

where \(x\) is the input context, \(y\) the generated output, and
\(\theta\) the model parameters. Function calling constrains this
distribution to a structured output space:

\[
F(x) = \text{argmax}_{f \in \mathcal{F}} P(f|x, \mathcal{F})
\]

where \(\mathcal{F}\) is the set of declared functions and \(F(x)\) the
selected call. GPT-4 {[}3{]}, PaLM {[}2{]}, and open models such as
LLaMA {[}4{]} expose this capability with provider-specific schemas.
AgentISA does not modify this layer; it treats any such interface as a
\emph{backend} to be targeted by a common instruction set, in the same
way that a compiler targets multiple processor backends {[}33{]}.

The cost structure of this layer motivates our work. If each call
carries latency \(\tau_i\) plus a context-switching overhead
\(\delta_i\) (prompt reconstruction, serialization, cache misses), then
\(n\) similar calls cost:

\[
C(n) = \sum_{i=1}^{n} (\tau_i + \delta_i)
\]

\textbf{Definition 2.1} (Function Call Overhead): The overhead of
executing \(n\) function calls is \(C(n)\), the sum of per-call
latencies and per-call context reconstruction costs. When successive
calls are structurally identical, \(\delta_i\) is pure waste---which is
precisely the waste AgentISA's caching and fusion are designed to
remove.

\subsection{Reasoning and Agent
Paradigms}\label{reasoning-and-agent-paradigms}

A second line of work enhances LLM reasoning at prompt time.
Chain-of-thought prompting {[}7{]} and zero-shot reasoning {[}8{]}
improve multi-step behavior by eliciting intermediate steps. ReAct
interleaves reasoning traces with actions {[}9{]}; Reflexion adds verbal
self-critique across episodes {[}10{]}; Tree of Thoughts explores
deliberative search over thought trees {[}11{]}; and Voyager
demonstrates open-ended skill acquisition in an embodied environment
{[}12{]}. These paradigms define \emph{what} an agent should do at the
cognitive level. AgentISA is complementary: it defines \emph{how} the
resulting behaviors are represented, compiled, and executed as
instructions. A ReAct loop, for instance, can be expressed as an
AgentISA instruction sequence whose tool invocations become fused,
cacheable agentic calls.

\subsection{Tool Calling and Interface
Standardization}\label{tool-calling-and-interface-standardization}

Toolformer trains models to interleave tool calls with text {[}13{]};
Gorilla connects models to large API corpora {[}14{]}; ToolLLM scales
tool coverage to 16,000+ real-world APIs {[}15{]}; and HuggingGPT
orchestrates model hubs for task solving {[}16{]}. On the
standardization side, the Model Context Protocol defines an open
specification for exposing tools and context to LLM applications
{[}18{]}, and the Berkeley Function Calling Leaderboard provides a
systematic cross-model evaluation of function-calling accuracy {[}17{]}.

These efforts standardize the \emph{interface}. AgentISA standardizes
the \emph{execution model above the interface}: it compiles a
provider-independent instruction stream down to whatever interface a
backend exposes. This distinction matters for portability---an AgentISA
program compiled for two providers differs only in the final translation
step (Section 3.2.3)---and for optimization, because interface-level
standards alone cannot fuse or eliminate calls.

\subsection{Multi-Agent Frameworks}\label{multi-agent-frameworks}

AutoGen frames agent applications as multi-agent conversations {[}19{]};
MetaGPT assigns standardized roles and workflows to agents {[}20{]};
AgentVerse facilitates multi-agent collaboration and studies emergent
behaviors {[}21{]}; ChatDev organizes agents as a software-development
organization {[}22{]}; CAMEL studies communicative agent societies
{[}23{]}; and AutoGPT popularized autonomous goal-driven agents
{[}24{]}.

AgentISA contributes a different artifact to this space: not a framework
or orchestration philosophy, but an instruction-level
substrate---capability profiles, coordination instructions with barrier
semantics, and a security monitor---that any such framework could
target. Concretely, our multi-agent layer (Section 3.5, Section 5.6)
provides capability-based agent selection, execution planning with
per-stage fallback strategies, and policy enforcement for
authentication, authorization, resource access, and data sensitivity.

\subsection{Prompt Compilation and Cost
Optimization}\label{prompt-compilation-and-cost-optimization}

Closest to our compilation perspective is DSPy, which compiles
declarative prompt programs into optimized pipelines via prompt search
and fine-tuning {[}25{]}. LangChain {[}26{]} and LlamaIndex {[}27{]}
provide library-level abstractions for chaining LLM calls and indexing
context. FrugalGPT reduces cost through model cascades---answering with
cheaper models when possible {[}28{]}.

AgentISA differs in the level at which optimization operates. DSPy
optimizes \emph{prompts}; FrugalGPT optimizes \emph{model selection};
AgentISA optimizes \emph{instruction streams}: instruction selection by
dynamic programming over pattern covers, fusion, dead-code elimination,
pipeline scheduling, result caching, and dynamic hot-path specialization
(Sections 3.4 and 4). These are classical compiler transformations
{[}33{]} applied to a new artifact, and they compose with---rather than
replace---prompt-level and model-level optimization.

\subsection{Benchmarks for Agent
Systems}\label{benchmarks-for-agent-systems}

AgentBench evaluates LLMs as agents across diverse environments
{[}29{]}; GAIA tests general assistant abilities {[}30{]}; PlanBench
probes planning and reasoning about change {[}31{]}; and SWE-bench
measures resolution of real-world GitHub issues {[}32{]}. These
benchmarks evaluate \emph{end-to-end capability}. AgentISA's evaluation
instead measures \emph{subsystem behavior under controlled
conditions}---API-call reduction under synthetic Zipf workloads,
instruction-count reduction from compilation, and trace shrinkage from
dynamic optimization (Section 5). We view the two as complementary:
instruction-level metrics can attribute end-to-end gains to specific
mechanisms when such gains are measured, and are reproducible without
live model access.

\subsection{Classical Compiler and Architecture
Techniques}\label{classical-compiler-and-architecture-techniques}

AgentISA's optimization machinery is deliberately classical. Instruction
selection by tree-pattern matching with dynamic programming, peephole
optimization, and data-flow-based dead-code elimination are standard
compiler techniques {[}33{]}. Pipelining, hazard detection, and
resource-constrained scheduling follow the classical architecture
literature {[}34{]}; the RISC-V project demonstrates the value of open,
well-specified instruction sets {[}35{]}. Type safety via
progress-and-preservation is the standard technique of
programming-language theory {[}36{]}, and CompCert establishes that
compiler correctness itself can be formally verified {[}37{]}. Our
contribution is not a new compiler technique but the demonstration that
this machinery transfers to LLM agent workloads, together with the
semantic-preservation arguments adapted to instructions with
pre/post-conditions (Appendix C).

\subsection{LLM Serving Systems}\label{llm-serving-systems}

Below the API boundary, the serving community has made inference
dramatically cheaper: PagedAttention manages KV memory like virtual
memory {[}38{]}; Orca introduces continuous batching for transformer
serving {[}39{]}; FlashAttention redesigns attention for IO-awareness
{[}40{]}; and Mooncake proposes a KVCache-centric disaggregated
architecture {[}41{]}. Energy analyses quantify the inference cost of
large models {[}42{]}. This line of work and AgentISA are orthogonal
layers of the same stack: serving systems make each call cheaper;
AgentISA reduces how many calls an agent makes and how much redundant
work each carries. The two compound multiplicatively.

\subsection{Research Gaps and Our
Contributions}\label{research-gaps-and-our-contributions}

In summary, the literature leaves four gaps that AgentISA addresses:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{No instruction-level contract for agent behavior.} Interfaces
  are standardized {[}13, 14, 18{]}, and frameworks are numerous {[}19,
  20, 21, 22, 23, 24{]}, but no shared instruction set spans providers
  and frameworks.
\item
  \textbf{No compiler for agent behavior.} Prompt-level compilation
  exists {[}25{]} and model-level cost reduction exists {[}28{]}, and
  \emph{caching itself is well-trodden ground}---at the response level
  (GPTCache {[}46{]}), at the KV-prefix level (RadixAttention/SGLang
  {[}47{]}), and at the provider prompt-caching level. What none of
  these layers expose is an \emph{instruction-level} contract: caching
  there is an optimization of model serving---invisible to the agent
  program's structure, and without effect on it. Instruction-level
  fusion, elimination, and scheduling---with cacheability as a declared
  property of the instruction set---have not, to our knowledge, been
  demonstrated.
\item
  \textbf{No semantics-preserving account of agent optimization.}
  Serving work verifies kernels and schedulers, not agent-level
  transformations; we provide progress-and-preservation-style arguments
  for ours (Theorems 3.2, 3.4, 3.5, 3.6).
\item
  \textbf{No reproducible instruction-level evaluation.} Existing
  benchmarks measure end-to-end capability {[}29, 30, 31, 32{]}; we
  contribute a seed-controlled evaluation: a microbenchmark suite with
  fully disclosed synthetic workloads and mock-backend instrumentation,
  extended by real-gateway and system-level validations (Section 5).
\end{enumerate}

Our work addresses these gaps through: (1) the formal instruction set
with the Agentic Calling abstraction (Sections 3.1--3.2), (2)
pattern-based instruction optimization (Section 3.4), (3)
semantic-preservation arguments for our transformations (Theorems 3.2,
3.4--3.6; Appendices B--C), (4) automated instruction learning from
execution traces (Section 3.3), and (5) a reproducible evaluation
spanning synthetic microbenchmarks, real-gateway validation, and a
system-level workload characterization (Sections 5.2--5.8).

\section{AgentISA Design}\label{agentisa-design}

Building upon the foundations established in Sections 1 and 2, we
present AgentISA, a comprehensive instruction set architecture designed
specifically for LLM-powered AI agents. This section details the core
architecture, the Agentic Calling framework, the automatic instruction
learning system, instruction organization and optimization, and the
capability-assessment layer.

\subsection{Core Architecture}\label{core-architecture}

\subsubsection{Instruction Set
Specification}\label{instruction-set-specification}

The AgentISA instruction set is formally defined as a tuple:

\textbf{Definition 3.1} (AgentISA Core): \[
\text{AgentISA} = (I, T, \Sigma, \Delta, \Phi)
\]

where:

\begin{itemize}
\tightlist
\item
  \(I\) is the set of instructions
\item
  \(T\) is the type system
\item
  \(\Sigma\) is the state space
\item
  \(\Delta\) is the transition function set
\item
  \(\Phi\) is the verification function set
\end{itemize}

Following the conventions of classical instruction set design {[}33, 34,
35{]}, we define the basic instruction format:

\begin{verbatim}
INSTRUCTION = {
    opcode: OPCODE,
    args: ARGS[],
    precondition: PRED,
    postcondition: PRED,
    context: CONTEXT
}
\end{verbatim}

The instruction set is categorized into four fundamental classes:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Control Flow Instructions}:
  \[\mathcal{C} = \{seq, branch, loop, call\}\]
\item
  \textbf{State Management Instructions}:
  \[\mathcal{S} = \{load, store, update, cache\}\]
\item
  \textbf{LLM Interaction Instructions}:
  \[\mathcal{L} = \{query, response, context\}\]
\item
  \textbf{Resource Management Instructions}:
  \[\mathcal{R} = \{allocate, free, monitor\}\]
\end{enumerate}

Two sanity results anchor the instruction-set definition. Neither
introduces new machinery---the simulation technique from the compiler
literature {[}33{]}, the type-safety technique from the semantics
literature {[}36{]}---and we state them for the roles they play in the
architecture: Theorem 3.1 certifies that the instruction set does not
artificially constrain what agent programs can express, and Theorem 3.2
fixes the well-formedness obligation that the offline bounded checker
discharges for pure instructions (Section 3.3.3) and that the runtime
brackets with pre-dispatch context validation (Section 3.2.3).

\textbf{Theorem 3.1} (Turing Completeness): The AgentISA instruction set
is Turing complete.

\emph{Proof sketch}: We exhibit a translation from WHILE
programs---already known to be Turing equivalent---to AgentISA
instruction sequences, using a sufficiency (simulation) argument over
instruction classes: state management instructions encode an unbounded
store, and control-flow instructions encode sequential composition,
conditional branching, and iteration. The full construction and
simulation argument are given in Appendix A, following standard
simulation techniques from the compiler literature {[}33{]} and the
operational-semantics framework of Pierce {[}36{]}.

\subsubsection{Type System and
Semantics}\label{type-system-and-semantics}

The type system T extends the simply-typed discipline of Pierce {[}36{]}
with dependent-type constructions (\(\Pi\), \(\Sigma\), \(\mu\)):

\textbf{Definition 3.2} (AgentISA Type System): \[
T ::= \text{Base} \mid \Pi(x:T_1).T_2 \mid \Sigma(x:T_1).T_2 \mid \mu X.T
\]

where:

\begin{itemize}
\tightlist
\item
  Base types include \{Bool, Int, String, Float\}
\item
  \(\Pi\) represents dependent function types
\item
  \(\Sigma\) represents dependent pair types
\item
  \(\mu\) represents recursive types
\end{itemize}

The semantic rules follow operational semantics:

\[
\frac{e_1 \rightarrow e_1'}{E[e_1] \rightarrow E[e_1']} \text{ (Context)} \quad
\frac{}{(\lambda x.e)v \rightarrow e[x:=v]} \text{ ($\beta$-reduction)}
\]

The pure core carries a standard type-safety argument---progress and
preservation, in the style of Pierce {[}36{]}---discharging the
well-formedness role fixed in Section 3.1 and extended to the shipped
instruction set by the bounded checker of Section 3.3.3:

\textbf{Theorem 3.2} (Type Safety for the Pure Core): Well-typed
programs in the pure core calculus of Appendix B---the
\(\lambda\)-fragment (base types, dependent \(\Pi\)/\(\Sigma\) types,
recursion) plus the composition operators applied to instructions
carrying typed pre/post-conditions---cannot ``go wrong'', under the
per-instruction validity obligation of Definition 3.5 (stated in Section
3.3.3 below; pre/post-conditions), with transition functions assumed
total on precondition-satisfying states (Appendix B.7). Effectful
instruction classes are embedded via their typed pre/post-conditions and
covered to the extent their preconditions are checkable.

\emph{Proof sketch}: By the standard two-lemma technique---progress and
preservation---as presented in Pierce {[}36{]}:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Progress:
  \(\forall e, T.\ \vdash e : T \implies \mathrm{value}(e) \lor \exists e'.\ e \to e'\)
\item
  Preservation:
  \(\forall e, e', T.\ \vdash e : T \land e \to e' \implies \vdash e' : T\)
\end{enumerate}

Both lemmas are proved by induction over the derivations of the merged
judgment system of Appendix B (term typing plus contracted instruction
typing), with a joint argument for the composition cases. For
instruction steps, progress follows from the Definition 3.5 validity
obligation plus the standing totality assumption, and preservation from
the postcondition typing; composition operators are handled by the
chained invariant \(post(i_1) \Rightarrow pre(i_2)\) (Appendix B).

\subsubsection{LLM Integration
Interface}\label{llm-integration-interface}

The LLM integration interface is defined through a protocol, playing the
same role for agent backends that the Model Context Protocol plays for
tool exposure {[}18{]}. Its components correspond to the interface
conventions of modern function-calling providers {[}3, 18{]} as
follows---\(\mathcal{P}_{LLM} = (Q, R, C, \psi)\) with
\(Q \leftrightarrow\) QueryFormat (query space, JSON Schema),
\(R \leftrightarrow\) ResponseFormat (response space, JSON Schema),
\(C\) the context-management functions (whose implementation surface
today exposes the context window size, ContextWindow: Integer), and
\(\psi \leftrightarrow\) StateMapping: Map\textless AgentState,
LLMContext\textgreater{} (state transformation functions):

\begin{verbatim}
Protocol LLMInterface {
    QueryFormat: JSON Schema
    ResponseFormat: JSON Schema
    ContextWindow: Integer
    StateMapping: Map<AgentState, LLMContext>
}
\end{verbatim}

\subsection{Agentic Calling Framework}\label{agentic-calling-framework}

\subsubsection{Function Calling to Agentic Calling
Transformation}\label{function-calling-to-agentic-calling-transformation}

The transformation from function calling to Agentic Calling is
formalized as:

\textbf{Definition 3.3} (Agentic Transformation): \[
\mathcal{T}: F \rightarrow A
\]

where \(F\) is the function call space and \(A\) is the agent
instruction space.

\(\mathcal{T}\) is required to preserve call semantics, and this holds
by construction for the three-step process below: the synthesized
instruction records the function signature verbatim, embeds the context
verbatim (Theorem 3.3), and delegates execution to the original call. We
therefore state preservation as a property of the construction rather
than a separately proved theorem:

\[
\forall f \in F: \text{sem}(\mathcal{T}(f)) \equiv \text{sem}(f)
\]

The transformation process follows three steps, mirroring the
signature-to-call conventions of function-calling interfaces {[}13,
14{]}:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Function signature analysis
\item
  Context embedding
\item
  Instruction synthesis
\end{enumerate}

\subsubsection{Context Preservation and State
Management}\label{context-preservation-and-state-management}

State management in AgentISA follows a formal state machine model:

\[
M = (S, s_0, \delta, F)
\]

where:

\begin{itemize}
\tightlist
\item
  S: Set of states
\item
  s\(_{0}\): Initial state
\item
  \(\delta\): State transition function
\item
  F: Set of final states
\end{itemize}

Extraction-time context preservation is guaranteed by construction
(Theorem 3.3); at runtime it is only monitored:

\textbf{Theorem 3.3} (Context Preservation): Let \(\phi\) be the context
interpretation function (defined compositionally over context
\emph{contents}---the keys and values the context carries), and \(t\)
the extraction transformation that embeds a context \(c\) verbatim into
an instruction's \texttt{context} field. Then, for every \(c \in C\):

\[
\phi(t(c)) = \phi(c)
\]

\emph{Proof}: By the definition of \(t\), the extracted instruction
carries a verbatim copy of the source context; since \(\phi\) is defined
over context contents and the copy is content-identical,
\(\phi(t(c)) = \phi(c)\) holds by construction. This is a \emph{design
invariant of the extraction pipeline}: it holds because the
implementation copies rather than re-encodes. At runtime the shipped
checks are constraint-based and bracket the transition:
\texttt{AgenticTransformer.validate\_context} checks the registered
context constraints pre-dispatch, and
\texttt{verify\_context\_preservation(before,\ after)} re-checks them
pairwise across the executed transition and reports violations
(mechanics in Section 3.2.3); neither performs structural validation of
the carried context. Theorem 3.3's extraction-time preservation is
discharged by the copy construction; preservation across an executed
transition is \emph{monitored, not guaranteed}, by the runtime checks.
\(\blacksquare\)

\subsubsection{Cross-model
Compatibility}\label{cross-model-compatibility}

Cross-model compatibility is achieved through an abstract interface
layer:

\begin{verbatim}
Interface ModelAdapter {
    translate: AgentInstruction → ModelSpecificCall      // shipped: translate_instruction
    normalize: ModelSpecificResponse → AgentResponse    // shipped: normalize_response
    validateContext: Context → Boolean                  // shipped: AgenticTransformer.validate_context
}
\end{verbatim}

All three interface operations ship. \texttt{translate} is
\texttt{ModelAdapter.translate\_instruction} (with registered type
transformations). \texttt{normalize} is
\texttt{ModelAdapter.normalize\_response}, which folds the two dominant
wire shapes---the Anthropic protocol (typed \texttt{content} blocks with
\texttt{usage.input\_tokens}/\texttt{output\_tokens}) and the OpenAI
protocol (\texttt{choices{[}0{]}.message} with
\texttt{usage.prompt\_tokens}/\texttt{completion\_tokens})---into a
canonical \texttt{AgentResponse} envelope (content, tool calls, usage,
model, raw), so downstream instruction code never branches on provider
syntax. \texttt{validateContext} is
\texttt{AgenticTransformer.validate\_context}, the pre-execution
complement of the shipped post-hoc
\texttt{verify\_context\_preservation(before,\ after)}: it evaluates the
registered context constraints against a single state before dispatch,
applying two-argument pairwise predicates reflexively, \((v, v)\)
(single-argument predicates apply directly), and leaving constraints
over absent keys vacuously satisfied in line with the preservation
semantics---so key \emph{deletion} goes unreported, a blind spot
analogous to the non-reflexive constraints below. Constraints that are
non-reflexive by design, e.g.~strict growth, are not detectable
pre-execution.

Motivated by the observation of cross-model function-calling studies
{[}17{]} and open protocol efforts {[}18{]}---providers differ in
surface syntax but can agree on semantics---we require the following of
the \emph{adapter layer} (not of the models themselves; taking
\(m_1 = m_2\) would demand determinism, which no LLM provides), for
\(\mathbb{M}\) the set of provider adapters:

\[
\forall m_1, m_2 \in \mathbb{M}: \text{out}(m_1) \equiv \text{out}(m_2) \text{ when } \text{in}(m_1) \equiv \text{in}(m_2)
\]

\subsection{Automatic Instruction
Learning}\label{automatic-instruction-learning}

\subsubsection{Dialogue Pattern
Recognition}\label{dialogue-pattern-recognition}

Pattern recognition in AgentISA is frequency-based and deterministic
(action-signature grouping) rather than grammatical; it is implemented
in \texttt{agentflow.core.isa.pattern\_mining} and
\texttt{agentflow.core.isa.instruction\_learning}.

\textbf{Definition 3.4} (Instruction Sequence Pattern): A pattern \(p\)
over the instruction alphabet \(I\) is a non-empty contiguous sequence
\(p = (i_1, \dots, i_k) \in I^k\) together with two frequency
statistics:

\begin{itemize}
\tightlist
\item
  \textbf{Support}:
  \(sup(p) = P(p \text{ occurs as a contiguous subsequence in a randomly drawn trace})\)
\item
  \textbf{Confidence}:
  \(conf(p \Rightarrow j) = P(i_{t+1} = j \mid (i_{t-k+1}, \dots, i_t) = p)\)
\end{itemize}

A pattern is \emph{frequent} if \(sup(p) \geq \sigma_{min}\) and
\emph{predictive} if \(\max_j conf(p \Rightarrow j) \geq \gamma_{min}\),
for thresholds \(\sigma_{min}, \gamma_{min} \in (0, 1]\).

Pattern recognition proceeds in three stages:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Frequent-sequence mining.} Candidate subsequences are
  enumerated from execution traces together with their occurrence
  counts; successor statistics are accumulated alongside, and sequences
  below \(\sigma_{min}\) are pruned together with their statistics---so
  confidence is estimated only over frequent sequences. The output is
  the set of frequent, predictive patterns.
\item
  \textbf{Behavior grouping.} The shipped \texttt{PatternRecognizer}
  groups dialogues deterministically by \emph{action signature}---the
  sorted set of system-turn contents---and promotes each signature
  bucket with sufficient support into a pattern---and, for
  dialogue-derived buckets, an acceptable success rate. An earlier
  prototype used TF-IDF embeddings with density-based clustering
  (DBSCAN) and k-means over instruction-trace feature vectors; we
  abandoned it for production use because it was non-deterministic
  across library versions and degenerate on the small, short samples
  that agent traces actually provide. (A k-means view over
  instruction-trace features remains available in
  \texttt{pattern\_mining}, with fixed \texttt{random\_state} for
  reproducibility.) Each signature bucket groups same-kinded behaviors
  by construction (identical action \emph{sets}; argument values and
  turn counts may differ). Promotions split by source: trace-mined
  promotions execute by \textbf{composite replay} rather than as
  placeholders---the mined pattern carries its constituent instruction
  sequence together with the dataflow edges between its members, and the
  learned instruction's \texttt{execute} body re-runs that sequence in
  mined order against a shared context built from its inputs, merging
  each constituent's outputs and returning the keys its
  \texttt{produces\_X} postconditions declare; dialogue-mined templates,
  which carry no recorded instruction body, raise
  \texttt{NotImplementedError} rather than silently no-opping. Promotion
  is deterministic: pattern identity is derived from the mined
  instruction-id sequence, so the same traces promote the same
  instructions, in the same order, across runs. Replay semantics are
  plain sequential composition---nothing smarter---so a learned
  instruction reproduces the outputs of its recorded subsequence on the
  same inputs but does not generalize to unseen parameter values; no
  automated mining-to-optimization decision path exists yet (promotion
  is a developer decision).
\item
  \textbf{Pattern validation.} Each candidate pattern is checked for
  significance---support above \(\sigma_{min}\) (the frequency threshold
  of stage 1) and, for dialogue-derived patterns, an acceptable success
  rate among the dialogues exhibiting it---before it is promoted to a
  candidate instruction.
\end{enumerate}

This design is deliberately statistical: agent traces are short and
noisy, and frequency statistics degrade gracefully where grammar
induction would overfit. It also composes with the compiler---a
frequent, verified pattern is exactly the candidate for promotion to a
fused instruction (Section 3.4.4).

\subsubsection{Instruction Extraction
Pipeline}\label{instruction-extraction-pipeline}

The instruction extraction process is the three-stage pipeline of
Section 3.3.1, instantiated as shipped (stage names from Section 3.3.1
in parentheses):

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Pattern Detection} (frequent-sequence mining):
  frequent-sequence mining over execution traces, accumulating support
  and confidence statistics; sequences below the support threshold are
  pruned.
\item
  \textbf{Instruction Formation} (behavior grouping): deterministic
  action-signature grouping promotes validated patterns into
  composite-replay candidates; the extracted template carries the
  recorded constituent sequence and its dataflow edges.
\item
  \textbf{Optimization and Validation} (pattern validation and
  optimization): threshold and success-rate checks gate promotion, and
  the standard optimization passes of Section 3.4 apply to any resulting
  stream.
\end{enumerate}

\subsubsection{Instruction Optimization and
Verification}\label{instruction-optimization-and-verification}

Optimization is coupled to verification: where verified-compilation
efforts such as {[}37{]} verify the transformations of a whole compiler,
AgentISA's verification targets a different granularity---the validity
of individual instructions and the obligations of individual rewrites:

\textbf{Definition 3.5} (Instruction Verification): An instruction i is
valid if: \[
\forall s \in S: \text{pre}(i,s) \implies \text{post}(i,\text{exec}(i,s))
\]

For pure instructions with finite, small state spaces, the shipped
checker (\texttt{agentflow.core.isa.bounded\_checker}) enumerates the
candidate input states derived from the declared parameter constraints
--- exhaustively for finite domains such as \texttt{bool} and enum
parameters --- and checks the implication on each state; for larger or
non-enumerable spaces it probes a bounded, deterministically sampled set
of states (default cap 256), which makes it a \emph{bounded}
verification procedure rather than a complete one. We state the
implementation status plainly: Definition 3.5 defines validity, and the
bounded checker is now \textbf{shipped code}: for every pure
(side-effect-free) instruction the checker generates the bounded state
space, filters it by well-typedness and by the declared preconditions,
executes the instruction, and evaluates three obligations on each
surviving state --- progress (execution must not raise where the
precondition holds), preservation (declared outputs must be present and
well-typed), and the postcondition itself. Side-effectful instructions
are never executed by the checker and are reported as out of scope, so
their validity obligation is not mechanically checked; it is delegated
to authoring-time unit tests and review. Theorem 3.2 is stated
conditionally on this obligation, and Theorems 3.4--3.6 carry the
separate rewrite obligations of Appendix C.7; for state spaces beyond
the enumeration bound the condition remains substantive rather than
discharged (Appendices B.7 and C.7):

\[
\forall s \in S_{bounded} \subseteq S: \text{pre}(i,s) \implies \text{post}(i,\text{exec}(i,s))
\]

where \(S_{bounded}\) is the explored subset. Completeness of the check
is traded for tractability---the standard bounded-exploration
compromise; the operational-semantics treatment of instruction meaning
itself follows {[}36{]}.

\textbf{Theorem 3.4} (Optimization Soundness): Every atomic rewrite of
the pass pipeline---fusion (Appendix C.2's rule, applied by the
combining pass), dead-code elimination, and instruction combining
(Section 3.4.4)---preserves the denotation of the instruction sequence
it transforms: \(\text{sem}(r(i)) \equiv \text{sem}(i)\), read as the
partial equivalence of C.1.

\emph{Proof sketch}: By structural induction on instruction composition.
The base case shows each atomic rewrite (fusion, elimination, combining)
preserves the denotation of a single instruction; the inductive step
lifts preservation through each composition operator of Definition 3.6.
The full proof, including the per-rewrite case analysis, is given in
Appendix C.

The shipped checker
(\texttt{agentflow.core.isa.bounded\_checker.verify\_instruction})
implements Definition 3.5 on the bounded state space exactly as
described above (enumerate, filter by preconditions, execute only pure
instructions); it reports violations structurally:

\subsection{Instruction Organization and
Optimization}\label{instruction-organization-and-optimization}

\subsubsection{Instruction Composition}\label{instruction-composition}

The AgentISA supports hierarchical instruction composition through a
formal composition algebra:

\textbf{Definition 3.6} (Instruction Composition): Given instructions
\(i_1, i_2 \in I\), we define composition operators:

\begin{align*}
&\text{Sequential}: i_1 \circ i_2 \\
&\text{Parallel}: i_1 \parallel i_2 \\
&\text{Conditional}: i_1 \triangleright i_2 \\
&\text{Iterative}: i_1^* \\
\end{align*}

Their denotations (sequential execution; parallel interleaving under
disjoint state footprints; guarded execution of \(i_2\) on \(i_1\)'s
triggering outcome; zero-or-more iterations of \(i_1\)) are fixed in
Appendix C.1.

Composition follows algebraic properties. Properties 1 and 3 hold for
all instructions; Property 2 requires a stronger restriction than
side-effect-freeness alone:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Associativity} (all instructions, up to denotation):
  \[(i_1 \circ i_2) \circ i_3 = i_1 \circ (i_2 \circ i_3)\]
\item
  \textbf{Distributivity} (only for pure instructions with pairwise
  disjoint state footprints): Let \(i_1, i_2, i_3\) be side-effect-free
  instructions whose denotations act on pairwise disjoint state
  components (declared outputs distinct and read sets disjoint from the
  other members' writes). Their updates are then independent state
  writes: re-applying \(i_1\) overwrites its own cells with the same
  values (the double application is idempotent in effect), and updates
  to disjoint cells commute, so both sides of
  \[i_1 \parallel (i_2 \circ i_3) = (i_1 \parallel i_2) \circ (i_1 \parallel i_3)\]
  denote the same net state transformation. \emph{The disjointness
  restriction is necessary}: purity alone does not imply idempotence. A
  pure \texttt{update(+1)} instruction applied twice increments twice
  (pure here means free of \emph{external} side effects; writes to
  declared state cells are permitted), so for instructions sharing a
  state component the law fails (see the Remark below).
\item
  \textbf{Identity}: \[i \circ \epsilon = \epsilon \circ i = i\]
\end{enumerate}

where \(\epsilon\) is the empty (identity) instruction.

\textbf{Remark} (necessity of the restriction): distributivity also
fails for side-effectful instructions---re-applying a state-mutating
\(i_1\) (with \(i_2 = i_3 = \epsilon\)) executes it once on the left and
twice on the right, so the two programs differ in the resulting state.
Accordingly, the shipped compiler gates parallel grouping on purity plus
disjoint dependencies and disjoint outputs, excludes
\texttt{side\_effects=True} instructions from all such rewrites, and
applies no general distributivity-based simplification.

\subsubsection{Instruction Pipeline
Design}\label{instruction-pipeline-design}

We formalize the instruction pipeline as a directed acyclic graph (DAG):

\textbf{Definition 3.7} (Pipeline DAG): \[
P = (V, E, \lambda, \delta)
\]

where:

\begin{itemize}
\tightlist
\item
  V: Pipeline stages
\item
  E: Dependencies between stages
\item
  \(\lambda\): Stage latency function
\item
  \(\delta\): Data transfer function
\end{itemize}

Pipeline stages are organized as:

\begin{verbatim}
Pipeline {
    FETCH → DECODE → SCHEDULE → EXECUTE → COMMIT
    with
        hazard_detection: HazardGraph
        dependency_tracking: DependencyMatrix
        resource_allocation: ResourceMap
}
\end{verbatim}

\textbf{Theorem 3.5} (Pipeline Correctness): For any valid instruction
sequence \(s\) and any schedule \(S\) satisfying conditions S1-S4 of
Appendix C.5---each instruction dispatched exactly once, dependencies
respected, dispatch groups pairwise non-interfering, commit in program
order---pipeline execution preserves program semantics.

\emph{Proof}: By induction over the dispatch groups of \(S\) in commit
order, under the invariant that the architectural state after committing
each prefix of groups equals the sequential state after the same
instructions; S1--S4 supply exactly-once dispatch, dependency order,
group commutativity, and in-order commit (details in Appendix C.5).

\subsubsection{Instruction Selection and
Scheduling}\label{instruction-selection-and-scheduling}

Instruction selection follows a tree-pattern matching approach:

\textbf{Definition 3.8} (Selection Pattern): \[
\pi = (\tau, C, \text{cost}, \text{code})
\]

where:

\begin{itemize}
\tightlist
\item
  \(\tau\): a tree pattern over the IR (unrelated to the type-system
  symbol \(T\) of Definition 3.2)
\item
  \(C\): context constraints on the surrounding state
\item
  cost: Cost function
\item
  code: Generated code
\end{itemize}

Given an IR tree \(t\) to cover, the selection process is formalized as:

\[
\text{Select}(t) = \argmin_{\pi \in \Pi} \{\text{cost}(\pi) \mid \text{matches}(\pi.\tau, t) \land \text{satisfies}(t, \pi.C)\}
\]

Scheduling optimization problem (with \(\text{delay}(i)\) the incurred
stall of \(i\), \(\text{active}(t)\) the instructions running at time
\(t\), \(\text{res}(i)\) the resource demand of \(i\), and Capacity the
resource bound):

\begin{align*}
&\text{minimize} \sum_{i \in I} \text{delay}(i) \\
&\text{subject to:} \\
&\quad \forall (i_1, i_2) \in \text{Deps}: \text{start}(i_2) \geq \text{end}(i_1) \\
&\quad \forall t: \sum_{i \in \text{active}(t)} \text{res}(i) \leq \text{Capacity}
\end{align*}

\subsubsection{Static and Dynamic
Optimization}\label{static-and-dynamic-optimization}

\paragraph{Static Optimization}\label{static-optimization}

Static optimization employs several techniques:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Peephole Optimization}: \[
  \text{PH}(i_1,...,i_n) = \begin{cases}
  \text{opt}(i_1,...,i_n) & \text{if pattern exists} \\
  i_1,...,i_n & \text{otherwise}
  \end{cases}
  \]
\item
  \textbf{Dead Code Elimination}: \[
  \text{Live}(i) = \text{Use}(i) \cup (\text{Live}_{\text{out}}(i) - \text{Def}(i))
  \] The two shipped passes approximate this fixpoint at different
  conservatism levels. The \emph{compiler} pass (formal streams) removes
  a side-effect-free instruction when no live consumer depends on its id
  or any declared output---so a pure instruction whose outputs nobody
  consumes is removed. The \emph{trace optimizer} pass (executable
  instructions) is more conservative: any instruction declaring at least
  one output is kept, because executable traces lack the formal
  dependency annotations that make output-consumption analysis exact.
  The compiler experiments (Section 5.3) exercise the former; the
  dynamic hot-path machinery (Section 5.4) the latter.
\item
  \textbf{Instruction Combining} (the named candidate rules below are
  specified and not registered---Section 4.1.3; the shipped optimizer's
  built-in pairwise compatibility combining is active, and it is this
  built-in combining that the hot-path trace re-optimization of Section
  5.4 applies):

\begin{verbatim}
Combine Rules {
  // LOAD/STORE/MOVE are textbook mnemonics, illustrative
  // only; they are not shipped opcode names
  LOAD followed by STORE → MOVE
  Multiple CONTEXT_UPDATE → Single UPDATE
  Sequential QUERY → Batch QUERY
}
\end{verbatim}
\end{enumerate}

\paragraph{Dynamic Optimization}\label{dynamic-optimization}

Dynamic optimization in the shipped runtime is
\textbf{repetition-triggered and threshold-based}; it does not (yet)
respond to load or performance signals. Its actual mechanism:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Hot Path Detection} (implemented): the
  \texttt{DynamicOptimizer} keeps a monotone counter per exact
  instruction sequence (\texttt{path\_id} = the ordered join of
  instruction ids); a path is flagged hot when its count exceeds a
  configurable threshold \emph{and} its most recent recorded success
  rate is at least a stability bound (0.9 by default). There is no
  windowing and no load signal: \[
  \text{Hot}(p) = \text{count}(p) > \theta \land \text{success}(p) \geq \alpha
  \]
\item
  \textbf{Trace Optimization} (implemented): once hot, the cached
  sequence is re-optimized by the static pass machinery---peephole,
  dead-code elimination, instruction combining---bounded to a fixed
  number of passes; the runtime then serves the shrunken form for
  subsequent executions (demonstrated end-to-end in Section 5.8).
\item
  \textbf{Trace Formation and Adaptive Recompilation} (specified, not
  implemented): sub-trace extraction from observed frequency profiles,
  and performance-triggered recompilation (\texttt{should\_recompile}:
  execution count above threshold \emph{and} observed performance below
  expectation) remain design-level. The shipped runtime re-optimizes the
  whole cached sequence once per recording after the threshold is
  crossed, with no performance feedback loop.
\end{enumerate}

Two known consequences of the shipped design are worth stating: because
\texttt{path\_id} requires exact sequence identity, trace diversity
(similar-but-not-identical sequences) never accumulates counts and the
mechanism stays cold; and hot-path state (sequences, counters,
statistics) is unbounded. Both are discussed with their remedies in
Section 6.1.

\subsubsection{Verification and
Analysis}\label{verification-and-analysis}

Optimization correctness is argued through:

\textbf{Theorem 3.6} (Pass-Pipeline Soundness, extending Theorem 3.4):
For any optimization transform T composed of the pass pipeline's
rewrites, \[
\forall p \in \text{Program}: \text{sem}(T(p)) \equiv \text{sem}(p)
\]

\textbf{Proof Sketch}:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Show semantic preservation for each atomic transformation (the
  atomic-rewrite lemma, Appendix C.2)
\item
  Prove composition of transformations preserves semantics (the
  compositionality lemma, Appendix C.3)
\item
  Note that hazard-free pipeline execution is \emph{not} part of this
  theorem---it is Theorem 3.5 (Appendix C.5), invoked separately; this
  theorem's contribution is the rewrite layer (steps 1--2).
\end{enumerate}

\textbf{Performance Model} (specified; the benchmarks of Section 5
measure latency and token counts directly and do not evaluate it): \[
\text{Perf}(p) = \sum_{i \in p} (\text{base\_cost}(i) + \text{overhead}(i) - \text{optimization\_gain}(i))
\]

where optimization\_gain is calculated as: \[
\text{optimization\_gain}(i) = \sum_{o \in \text{Opts}} \text{benefit}(o,i) \times \text{application\_rate}(o,i)
\]

\subsection{Capability Assessment}\label{capability-assessment}

Agents are heterogeneous: an agent (or the model behind it) may be
strong at reasoning but weak at tool use, or vice versa. To make such
differences explicit---and to give the multi-agent coordinator of
Section 5.6 a principled basis for agent selection---AgentISA includes a
capability assessment subsystem, implemented as
\texttt{CapabilityProfile} in \texttt{agentflow.core.isa.capability}.

\textbf{Definition 3.9} (Capability Profile): A capability profile of an
agent \(a\) maps each capability domain \(D\) (the shipped enum carries
eight domains: reasoning, memory, generation, optimization,
specialization, coordination, security, robustness) to a score--weight
pair: \[
\text{Cap}(a) = \{(\text{dom}_k, s_k, w_k) \mid \text{dom}_k \in D\}
\]

where each domain carries a score \(s_k \in [0, 1]\) and a weight
\(w_k \geq 0\) reflecting the domain's importance in the current
deployment context.

\textbf{Implementation status.} The aggregation and selection mechanisms
ship (\texttt{CapabilityProfile}, \texttt{get\_overall\_score}, and the
coordinator's threshold selection) and are functionally tested in
Section 5.6; the instruction-level metric extraction is a specified
stub---the seventeen \texttt{\_measure\_*} functions currently return
0.0---so \texttt{assess\_capabilities} has no production call site yet,
and the tests of Section 5.6 inject \texttt{DomainScore} values directly
rather than deriving them through this pipeline. One consequence is a
known wart of the shipped aggregation: because domain weights enter both
the per-domain score and the overall mean, an end-to-end assessment
would double-count weights and cap the overall score well below the
coordinator's 0.7 threshold; the injected-score tests bypass this, and
the wart is recorded here rather than hidden.

Assessment proceeds in three steps:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Domain metric computation.} For each domain,
  \texttt{assess\_capabilities} is \emph{specified} to compute a set of
  \texttt{CapabilityMetric} values from the agent's instruction
  set---e.g., for the reasoning domain, metrics derived from the
  prevalence and complexity of reasoning-type instructions. As stated
  above, this extraction is a specified stub in the shipped code (the
  \texttt{\_measure\_*} functions return 0.0), so exercised assessments
  derive domain scores from injected metrics.
\item
  \textbf{Domain aggregation.} Metrics are aggregated into a per-domain
  \texttt{DomainScore}, matching the shipped
  \texttt{\_compute\_weighted\_score}: \[
  s_k = w_k \cdot \frac{\sum_{m \in M_k} v_m \cdot \text{conf}_m}{|M_k|}
  \]
\end{enumerate}

where \(M_k\) is the metric set of domain \(k\), \(v_m\) the metric
value, \(\text{conf}_m\) its confidence, and \(w_k\) the domain weight;
an empty metric set scores \(0\). (Note that the shipped form folds the
domain weight into \(s_k\) and the top-level
\texttt{get\_overall\_score} multiplies by the weights again---the
double-counting recorded above.)

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\setcounter{enumi}{2}
\tightlist
\item
  \textbf{Overall score.} \texttt{get\_overall\_score} computes the
  weighted mean across assessed domains: \[
  S(a) = \frac{\sum_{k} w_k \, s_k}{\sum_{k} w_k}
  \]
\end{enumerate}

with \(S(a)\) falling back to the unweighted mean when all weights are
zero.

Three properties of this design deserve emphasis. First, it is
\textbf{static rather than live-probing}: assessment is designed to be
cheap, deterministic, and side-effect-free, though the shipped metric
extraction is the stub disclosed above and exercised scores are
injected. Second, it is \textbf{compositional}: because scores summarize
instructions, fusing or eliminating instructions during compilation
(Section 3.4) changes the profile predictably, and a production
deployment would re-assess after optimization (the shipped coordinator
does not yet do so). Third, it directly serves coordination: the
agent-selection predicate in Section 5.6 chooses the highest-scoring
agent above a capability threshold for each task, subject to the
security policies of the \texttt{SecurityMonitor}---with the tests
injecting scores directly, as disclosed above.

We state the scope of this subsystem honestly:
\texttt{CapabilityProfile} assesses \emph{declared instruction-level
capability}, which correlates with---but does not measure---end-to-end
task performance. Cross-model behavioral comparison at benchmark level
is the domain of evaluation suites such as BFCL {[}17{]} and AgentBench
{[}29{]}; the two views are complementary.

We state the optimality property of the specified algorithm, for
patterns whose context constraints are \emph{local} (a pattern's
feasibility depends only on the node and its immediate operands):

\textbf{Theorem 4.1} (Selection Optimality, specified algorithm): Given
a set of context-local patterns P and an IR tree T, the MATCH-TREE
algorithm computes the minimal covering cost; the covering itself is
read off the \texttt{selected} table afterwards, by walking from the
root and skipping subtrees spanned by the chosen pattern.

\emph{Proof}: By induction on tree height, assuming a covering of T
exists (if no pattern matches a node its cost is \(\infty\) and no
covering exists):

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  Base case (a leaf has no children): the recurrence degenerates to a
  plain argmin over the patterns matching the leaf, which is optimal for
  a single node.
\item
  Inductive step: For a node \(v\) with children \(c_1, \dots, c_k\): \[
  \text{cost}(v) = \min_{p \in P} \left\{p.\text{cost} + \sum_{\substack{c \in \text{children}(v) \\ c \notin \text{covered}(p)}} \text{cost}(c)\right\}
  \]

  By the induction hypothesis, each \(\text{cost}(c)\) is the minimal
  covering cost of the corresponding subtree; the recurrence takes each
  candidate pattern's cost plus the (already optimal) costs of the
  children the candidate does not span, so the minimum over candidate
  patterns is the minimal covering cost at \(v\)---the minimum over
  disjoint pattern choices is optimal.
\end{enumerate}

The recurrence sums only over children not covered by the candidate
pattern \(p\)---summing over all children would double-count the cost of
subtrees the pattern spans. Section 3.4.3's per-node argmin is therefore
exact for single-node patterns; multi-node patterns require this
covering recurrence.

The recurrence requires that a pattern's feasibility at a node not
depend on the covers chosen for other subtrees; context constraints that
couple sibling subtrees break this optimal-substructure property, which
is why the statement restricts to context-local patterns. This theorem
is a property of the specified algorithm, not of the shipped heuristic
selector; no optimality claim is made for the implementation.

\subsection{Methodology}\label{methodology}

\subsubsection{Instrumentation: Mock LLM
Backend}\label{instrumentation-mock-llm-backend}

All experiments route model inference through a \texttt{MockLLMBackend}
that (1) counts each \texttt{infer} call as one simulated LLM API round
trip, and (2) charges a fixed 80 ms simulated latency per call to a
simulated clock. The backend never sleeps and never contacts a live
model, which makes every ``API call'' observable, deterministic given a
seed, and reproducible without network access or inference spend.
Crucially, everything \emph{around} the backend is real: the cache,
compiler, and optimizer are the production \texttt{agentflow.core.isa}
implementations (\texttt{InstructionCache},
\texttt{InstructionCompiler}, \texttt{OptimizationManager}), exercised
through the same code paths a deployment would use.

\subsubsection{Workloads}\label{workloads}

Workloads are synthetic and seed-controlled:

\begin{itemize}
\tightlist
\item
  \textbf{Caching}: 2,000 tasks drawn from a discrete distribution over
  50 instruction templates \(\times\) 20 parameter values, with task
  popularity following a Zipf distribution with exponent
  \(s \in \{0.5, 1.0, 1.5\}\). Increasing \(s\) concentrates popularity
  on fewer tasks, increasing reuse potential.
\item
  \textbf{Static compilation}: random instruction sequences of length
  50, 200, and 1,000 (each slot dead with probability 0.25, pure with
  probability 0.55, side-effectful otherwise; a final side-effectful
  sink consumes all pure outputs), compiled at optimization levels NONE,
  BASIC, ADVANCED, and AGGRESSIVE. The planted dead/pure structure is
  what gives DCE and fusion targets to find; the measured reductions are
  properties of this workload family.
\item
  \textbf{Dynamic optimization}: instruction traces of length 100
  recorded for up to 200 iterations per seed, with hot-path detection
  active (threshold 50 recordings). The recording loop terminates at the
  hot-path trigger---iteration 50 in all seeds---so each seed
  contributes exactly 51 recordings (the 50 that build the count plus
  the triggering one).
\item
  \textbf{Ablation}: an independent workload draw with the same
  distribution parameters as the static-compilation experiment (length
  200, 5 seeds, dead 0.25 / pure 0.55, but seed base 4,000 rather than
  2,000), with the fusion and dead-code-elimination passes enabled
  individually and jointly. Because the draw is independent, the
  all-passes total (35.0\%) is a replication of the 34.2\% headline of
  Section 5.3, not a decomposition of that exact number.
\end{itemize}

\subsubsection{Protocol and Statistics}\label{protocol-and-statistics}

Each synthetic-workload configuration (Sections 5.2--5.5) is run with 5
random seeds; we report mean \(\pm\) sample standard deviation across
seeds. These are \textbf{descriptive statistics only}: we make no
hypothesis-test claims (no p-values, no significance tests) anywhere in
this paper. The seed count suffices to show that the effects are stable
across workload instantiations---the standard deviations are small
relative to the means---but a formal inferential comparison against
other systems is out of scope, because there is no baseline system that
shares the mock-backend instrumentation.

\subsection{Multi-Agent Coordination: Functional
Validation}\label{multi-agent-coordination-functional-validation}

The multi-agent layer---\texttt{AgentCoordinator},
\texttt{SecurityMonitor}, and the collaborative instruction set---is
validated functionally by 43 tests, all passing. We present this as
\textbf{qualitative functional validation}: the tests verify that the
coordination behaviors exist and are correct, not that they are fast. No
performance number should be inferred from this subsection.

The coordination flow implemented by \texttt{AgentCoordinator}:

\begin{verbatim}
Input: Agent set A, Task list τs
Output: Coordinated solutions S

function COORDINATE-AGENTS(A, τs)
    for each task T in τs do
        AUTHENTICATE(task issuer)              // SecurityMonitor
        AUTHORIZE(task, role policy)           // SecurityMonitor
        ag ← SELECT-BY-CAPABILITY(A, T)        // CapabilityProfile (Section 3.5)
        plan ← BUILD-EXECUTION-PLAN(T)         // stages + coordination rules
        task-outcome ← success
        for each stage in plan do
            stage-outcome ← EXECUTE-STAGE(stage, ag)
            if stage-outcome failed and fallback(stage) exists then
                stage-outcome ← EXECUTE-FALLBACK(stage)
            end if
            if stage-outcome failed then
                task-outcome ← failed
                break
            end if
        end for
        RECORD-HISTORY(T, task-outcome)
    end for
end function
\end{verbatim}

What the 43 tests verify, grouped by subsystem:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Agent registration and role policies} (registration creates
  policies; permissions differ by role; security requirements differ by
  role; trust levels are bounded and reward declared specializations).
\item
  \textbf{Task coordination} (successful coordination produces a
  solution; failed tasks are recorded in history; missing authentication
  and missing authorization raise; absence of suitable agents raises;
  agent selection respects a capability threshold; the selected
  coordinator is the highest-scoring agent).
\item
  \textbf{Execution planning} (plans have stage structure with
  coordination rules; every stage has fallback keys; fallback strategies
  are differentiated; a fallback actually executes on stage failure;
  validators are reasoning-heavy non-coordinator agents).
\item
  \textbf{SecurityMonitor} (valid tasks pass; missing authentication
  fails; missing authorization fails; violations are recorded with
  timestamps; declared data sensitivity is enforced; sensitive
  categories infer a high sensitivity level; benign categories pass at
  medium; resource access is open by default and restrictable by
  configuration).
\item
  \textbf{Collaborative instructions} (barrier synchronization waits for
  the declared number of participants and times out when a peer is
  missing; width-one barriers resolve immediately; resource-allocation
  instructions reject over-allocation and serialize concurrent requests;
  the workflow state machine accepts valid actions, rejects invalid ones
  and double starts; a multi-agent research-team scenario runs end to
  end).
\end{enumerate}

These tests exercise the same production modules used elsewhere in the
system and are fully deterministic (no LLM calls). They establish
correctness of the coordination machinery under the tested conditions.
What they do not establish is scalability under contention, crash
recovery, or adversarial inputs beyond the policy checks above---all are
future work (Section 6).

\subsection{Real-LLM End-to-End Validation of Result
Caching}\label{real-llm-end-to-end-validation-of-result-caching}

\textbf{Research question.} Does the caching mechanism behave
identically when the ``model'' is a real LLM behind a live gateway, and
how much \emph{measured} wall-clock time and token usage does it save?

\textbf{Setup.} We replace the mock backend with a real model served by
a local Anthropic-protocol gateway (TLS with an internal CA; alias
\texttt{claude-glm-5.3-flash}, a hosted reasoning-capable GLM model;
\texttt{max\_tokens=64}). Requests are sequential HTTP calls (httpx, no
proxy, 90 s timeout), with three bounded retries for transient failures
--- none occurred. Every other component is the production code path:
the same \texttt{InstructionCache} protocol, the same instruction
objects, the same workload generator and the same instruction pool (50
templates) and parameter space (20 values) as Section 5.2.

\textbf{Scale.} Because each real round trip costs \textasciitilde2.2 s,
we reduce scale from 2,000 tasks \(\times\) 5 seeds to \textbf{200 tasks
\(\times\) 1 seed} per Zipf level (s in \{0.5, 1.0, 1.5\}); the whole
run is 1,040 measured experiment round trips (plus one preflight round
trip that validates connectivity before timing begins) in 39.4 minutes.
The seed pins the task sequence exactly, so the workload is the same one
the expectation below is computed from.

\textbf{An exactness property.} A cache hit depends only on the
(instruction, params) pair seen so far --- not on what the model
returns. The production \texttt{InstructionCache} is LRU with a TTL, so
in general a hit also depends on wall-clock time and capacity; under
this benchmark's configuration none of that can bind: \texttt{max\_size}
= 100,000 with at most 200 distinct keys per arm, \texttt{ttl} = 3,600 s
with every cache-enabled arm completing in under seven minutes (the
no-cache arms run to 7.9 minutes and never consult a cache), a fresh
cache per arm, and failed calls never cached. Hit/miss decisions are
therefore a pure function of the (instruction, params) sequence, and the
hit/miss sequence for a fixed workload is \emph{computable without any
backend}. If the mechanism is correct, the real run must reproduce that
sequence exactly; at the granularity the artifact records --- per-arm
hit rates and call counts --- it does:

\subsubsection{Real-Gateway Validation of Compilation and Hot-Path
Optimization}\label{real-gateway-validation-of-compilation-and-hot-path-optimization}

\textbf{Research question.} Do static compilation and closed-loop
hot-path adoption preserve the observable semantics of an instruction
stream when the stream's LLM step is served by a real model --- and what
do the mechanisms measurably save on a live gateway?

\textbf{Setup.} A dedicated harness
(\texttt{examples/paper\_real\_llm\_compiler\_test.py}; tests in
\texttt{tests/system/test\_real\_llm\_compiler\_test.py}) reuses the
gateway configuration of Section 5.7 (same base URL, internal-CA TLS,
alias \texttt{claude-glm-5.3-flash}, sequential httpx, 90 s timeout,
three bounded retries) but raises \texttt{max\_tokens} to 512 (Section
5.7 used 64) so that completions dominate the priced comparison; replies
still bind at the cap, as below. The harness runs behind a pluggable
backend: the real gateway when reachable, and otherwise a deterministic
mock with the same protocol that counts calls, accounts tokens from
template sizes, and charges the constant 80 ms simulated call
latency---so the identical validation runs offline and online. The task
is the service-log triage shape of Section 5.8: a seven-instruction
stream with one cacheable LLM-type step (\texttt{classify\_signature},
one model call per distinct incident-signature batch) and the same kind
of planted dead guard (\texttt{check\_format}), executed over repeated
realizations drawn from a seeded truncated-Zipf distribution over a
fixed universe of 40 task instances.

\textbf{Arms and protocol.} Arm (a) is the unoptimized authored stream.
Arm (b) drives the \emph{same} stream through the production machinery:
the closed loop of \texttt{OptimizationManager} /
\texttt{optimize\_hot\_path} records each realization and adopts the
shrunken trace once the path goes hot, and the static
\texttt{InstructionCompiler} compiles the stream at NONE vs AGGRESSIVE
with the dataflow-preservation assertion. Arm (a) runs first, cold, and
performs every live round trip; arm (b) then executes the same draws
against the result cache that arm (a) warmed. The classify step's cache
key is the sha256 of exactly the input dictionary its prompt is built
from, so arm (b) issuing \emph{zero} new gateway calls proves it
computed identical keys --- hence constructed identical prompts and
consumed identical values --- and its final artifacts must come out
byte-for-byte equal; any perturbation of the LLM step's inputs by the
optimization would surface as a cache miss (a live call) and/or artifact
divergence.

\textbf{Scale.} Tiny scale: 50 task realizations \(\times\) 1 seed
\(\times\) Zipf s = 1.0. The workload contains 22 distinct signature
batches, so the entire run is 23 gateway round trips (one preflight plus
22 live calls, all issued by arm (a)) in 4.4 minutes of wall time --- a
bounded validation run, not the 200 \(\times\) 3-skew sweep of Section
5.7.

\textbf{Results.} All checks pass. Arm (a) --- the live reference run
--- made exactly the 22 first-occurrence calls the backend-free
computation predicts and served the other 28 realizations from the
result cache (hit rate 56.0\%), consuming 4,027 prompt and 11,264
gateway-reported completion tokens in 260.2 s of measured call latency.
Arm (b) --- compiled, hot-path-adopted --- made zero new gateway calls
(all 50 realizations hit the warmed keys) and reproduced every artifact
byte-for-byte. The hot path was adopted at realization 7 (threshold 5;
adoption lands two realizations past the threshold because the counter
must strictly exceed it and recording follows execution, as in Section
5.8): realizations 1--6 executed the full seven-instruction stream,
realizations 7--50 the shrunken six-instruction form with
\texttt{check\_format} absorbed into its successor by fusion --- 306
instruction executions against arm (a)`s 350, a 12.6\% reduction in
executed instructions attributable to the adopted shrunken trace (the
per-stream shrink is 14.3\%, 7 \(\rightarrow\) 6; the realized saving is
diluted by the six full-form realizations before adoption; the static
compiler alone reproduces the 7 \(\rightarrow\) 6 shrink at AGGRESSIVE,
so the two mechanisms' contributions are not separated) and reported
separately from the cache's call savings. Static compilation of the same
stream: NONE 7 \(\rightarrow\) AGGRESSIVE 6 effective instructions,
dataflow preserved.

\textbf{What this does and does not show.} The byte-identity property is
cache-mediated by design: the cached classification values entered the
artifacts once, through arm (a) --- values that on this alias are
fallback-derived, as explained below --- and arm (b) is proven to
compute the same keys and consume the same values. This validates the
stream transformation, not model determinism, which is not guaranteed at
temperature 0 and is not claimed. On this gateway alias the reasoning
model's replies bind at \texttt{max\_tokens} in every call --- as
Section 5.7 reported at \texttt{max\_tokens=64}, and as a diagnostic
call at 1,500 tokens still did --- so the classify step's severity
values come from its deterministic fallback; what is validated against
the live model is the mechanism chain (key computation, cache decisions,
call and token accounting, artifact identity), not classification
quality. The run covers one gateway, one model, one seed, one skew
level, sequential requests, no streaming; multi-model, multi-seed, and
real-deployment behavior remain untested.

\subsection{System-Level Workload
Characterization}\label{system-level-workload-characterization}

The experiments above measure individual mechanisms on synthetic
sequences. To make the mechanisms' composition---and the implemented
closed-loop optimization claims of Section 3.4.4---checkable rather than
aspirational, we provide a seed-controlled workload characterization
(\texttt{examples/system\_task\_workload.py},
\texttt{tests/system/test\_system\_task\_workload.py}; the original
single-task demonstration lives on as
\texttt{examples/system\_task\_demo.py}) built from \textbf{four tasks
with genuinely different dependency shapes}, each realized end-to-end
against sandbox-resident files:

\begin{itemize}
\tightlist
\item
  the original \textbf{service-log triage}: a seven-instruction linear
  stream, described below in full;
\item
  \textbf{csv-etl-anomaly}: an eight-instruction fan-out pipeline
  (ingest CSV shards, schema guard, parse, per-column statistics,
  per-row signature construction, per-row anomaly triage, aggregate,
  write);
\item
  \textbf{report-merge}: a seven-instruction wide-fan-in task (ingest
  five markdown reports, header guard, dedupe, per-line signatures,
  cacheable cross-report consistency check, merge, write);
\item
  \textbf{regression-diff}: an eight-instruction two-branch convergence
  task (parallel baseline/candidate log ingests, guard, normalize, diff,
  classify hunks, aggregate, write).
\end{itemize}

The full characterization of all four tasks follows the detailed
walk-through of the triage task.

\textbf{The triage task's instruction stream} (seven instructions over
sandbox-resident files):

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \texttt{ingest\_logs} --- read six 400-line log files from the sandbox
  workspace (sandbox I/O, side-effectful);
\item
  \texttt{check\_syntax} --- a defensive guard that validates the
  ingested format; on this workload it never rejects (a \emph{planted
  dead guard}, standing in for the belt-and-braces checks real pipelines
  carry);
\item
  \texttt{normalize\_entries} --- parse and normalize lines;
\item
  \texttt{extract\_incidents} --- lift normalized entries into incident
  records;
\item
  \texttt{classify\_signature} --- triage-classify each incident
  (LLM-type, cacheable, backed by a deterministic rule-based stand-in
  that counts simulated model calls);
\item
  \texttt{aggregate\_triage} --- summarize by severity class;
\item
  \texttt{write\_report} --- write the triage report to the sandbox
  (side-effectful).
\end{enumerate}

\textbf{Configuration.} Seed 42; 6 files \(\times\) 400 lines; 12
repeated realizations of the task; hot-path threshold 5. Every phase is
deterministic and re-runnable from the repository (Artifact
Availability).

\textbf{What the triage walk-through shows.}

\begin{itemize}
\tightlist
\item
  \textbf{Static compilation with structural validation.} NONE compiles
  to 7 effective instructions / 7 dispatches; AGGRESSIVE compiles to 6 /
  6 (14.3\% reduction): the dead guard fuses with the following pure
  step rather than being dropped outright. Crucially, this walk-through
  \emph{asserts the compiled stream's dataflow validity}---every step
  whose output is consumed downstream must survive compilation, and the
  only eliminable step is the guard---so the reported shrinkage cannot
  silently come from dropping live producers.
\item
  \textbf{Reuse across repeated realizations.} The first realization
  makes 50 (simulated) model calls; all eleven subsequent realizations
  make zero (result cache hit rate 91.7\% on the classification step).
  All 12 reports are byte-identical.
\item
  \textbf{Closed-loop hot-path adoption.} The repeated stream crosses
  the hot-path threshold at the sixth recording (the counter must
  strictly exceed the threshold, and recording follows execution, so
  adoption lands at realization threshold+2); the runtime then
  \emph{adopts} the optimized form automatically, and repeats 7--12
  execute the shrunken 6-instruction stream (instruction executions per
  repeat: \texttt{{[}7,7,7,7,7,7,6,6,6,6,6,6{]}}). Executed on a fresh
  workspace, the optimized form reproduces the report
  byte-for-byte---the optimization is semantics-preserving on the real
  task, not only on synthetic sequences.
\item
  \textbf{Full-stack determinism.} A completely fresh stack---new
  instructions, new cache, new workspace, same seed---reproduces the
  report byte-for-byte (SHA-256 equality).
\end{itemize}

\textbf{Calibrating the synthetic headline.} The dynamic hot-path
experiment of Section 5.4 reports 65.8\% trace shrinkage on synthetic
traces with planted dead instructions; the four realistic tasks show
\textbf{12.5--25.0\%} (one planted guard in a seven- or
eight-instruction stream, plus one additional live-pure fusion pair in
csv-etl-anomaly). We state both figures rather than privilege either:
the 12.5--25.0\% number reflects the dead-check density we planted (one
guard per seven- to eight-instruction stream), so it calibrates the
shrink to a stated density assumption, not to observed ordinary-pipeline
waste; the synthetic figure is an upper bound under the skew/planting
parameters we control, not a typical-case estimate. Developing this
demonstration also served its audit purpose: constructing a realistic
(non-synthetic) dependency shape exposed two grouping/fusion soundness
gaps in the compiler---side-effectful instructions opening dispatch
groups, and fused instructions losing their external
dependencies---which are now fixed with regression tests; the
dispatch-folding numbers of Section 5.3 reflect the corrected (more
conservative) grouping.

\subsection{Limitations and Threats to
Validity}\label{limitations-and-threats-to-validity}

We enumerate the limitations of the evaluation explicitly:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Mock backend, not a live LLM.} The mock charges a constant 80
  ms per simulated call and returns deterministic responses; the
  real-gateway experiments address the mechanism-transfer part of this
  threat at reduced scale. Section 5.7 shows the
  \emph{mechanism-transfer} part of this threat at reduced scale:
  against a live gateway, the cache reproduces the recorded hit/miss
  statistics, and avoided calls convert to measured time and tokens.
  Section 5.7.1 extends real-gateway coverage to compilation and
  hot-path adoption: over 50 realizations, the compiled,
  hot-path-adopted stream issued zero new gateway calls against the
  result cache warmed by the unoptimized stream (identical cache keys,
  hence identical prompts) and reproduced every artifact byte-for-byte
  --- a cache-mediated identity that validates the stream
  transformation, not model determinism. The system-level
  characterization of Section 5.8 composes the mechanisms on four
  realistic tasks, but each task's classification-type step is backed by
  a deterministic rule-based stand-in that only counts (simulated) model
  calls---it is not evidence about live-model behavior. What remains
  untested across Sections 5.7, 5.7.1, and 5.8 is multi-model and
  multi-seed behavior, real deployment, caching under real model
  nondeterminism \emph{across prompt variations}, streaming responses,
  and provider rate limits.
\item
  \textbf{Synthetic workloads.} Zipf-distributed synthetic tasks are a
  reasonable model of skewed agent workloads, but they are a model, and
  the task-level characterization of Section 5.8 only partially
  addresses this. The cache-reduction figures (59.5--79.6\%) are exact
  for these workload families and should be read as
  \emph{skew-sensitivity curves}, not as universal savings. A deployment
  with uniformly novel tasks would see near-zero cache benefit. Section
  5.8 adds a four-task, four-shape system-level characterization
  (linear, fan-out, wide-fan-in, and two-branch convergence streams);
  its 12.5--25.0\% per-task compile shrink calibrates the 65.8\%
  synthetic headline downward, and its uniform reuse and closed-loop
  adoption under the fixed protocol (12 seeded realizations, threshold
  5) show the composition behavior is not an artifact of one stream's
  structure---but the four tasks remain seed-controlled,
  hand-constructed characterization streams, not a production workload
  study.
\item
  \textbf{No production end-to-end evaluation.} We have not deployed
  AgentISA in a production setting. Consequently this paper contains no
  latency-under-load, throughput, availability, or dollar-cost
  measurements, and we make no such claims.
\item
  \textbf{No real cost data (token usage measured; pricing now MODELED
  on measured tokens).} All latency figures in Sections 5.2--5.5 are
  simulated (avoided calls \(\times\) 80 ms). Section 5.7 measures real
  wall-clock time and gateway-reported token usage at reduced scale, and
  Section 5.7.1 prices its own measured tokens (its 22-call reference
  run) under three modes --- no optimization, AgentISA result caching,
  and a modeled provider prompt cache with a parameterized cache-read
  discount (default 0.1, after Anthropic's published prompt-caching
  economics). The resulting costs are MODELED-on-measured: token counts
  are measurements, prices are configurable list-price stand-ins (the
  serving gateway's actual pricing is unknown), and no dollar-savings
  claim is made. A head-to-head against a production external cache
  (GPTCache --- explicitly out of scope this pass) and a priced
  deployment study under real provider pricing remain future work.
\item
  \textbf{Program-size metrics, not wall-clock time.}
  Effective-instruction reduction and dispatch-count reduction are
  structural metrics. They correlate with---but do not
  equal---wall-clock improvements, which depend on per-instruction cost,
  parallelism available in the runtime, and dispatch overhead.
\item
  \textbf{Descriptive statistics only.} Five seeds per configuration in
  the synthetic experiments (Sections 5.2--5.5); the real-gateway and
  system-level runs are single-seed by design. No hypothesis tests,
  confidence intervals, or significance claims are made. The standard
  deviations indicate stability across seeds, nothing more.
\item
  \textbf{Functional, not performance, validation of coordination.} The
  43 multi-agent tests verify behavioral correctness under deterministic
  conditions, not throughput or scalability.
\end{enumerate}

Despite these limitations, the evaluation achieves its purpose: it
demonstrates, under fully disclosed and reproducible conditions, that
each optimization mechanism is implemented, active, and produces the
claimed structural effects on workloads designed to expose them.

\section{Discussion}\label{discussion}

\subsection{System Limitations and
Challenges}\label{system-limitations-and-challenges}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Instruction-set coverage}

  \begin{itemize}
  \tightlist
  \item
    Certain complex reasoning patterns are not yet naturally
    expressible; domain-specific instruction extensions are likely
    needed
  \item
    Maintaining consistency of pre/post-conditions and typing rules
    across extensions remains an open engineering challenge
  \end{itemize}
\item
  \textbf{Evaluation Scope}

  \begin{itemize}
  \tightlist
  \item
    As detailed in Section 5.9, our quantitative evidence is primarily
    microbenchmark-based (Sections 5.2--5.5), supplemented by
    real-gateway spot checks (Sections 5.7 and 5.7.1) and a
    seed-controlled four-task characterization (Section 5.8)
  \item
    Production end-to-end evaluation---including real provider pricing,
    rate limits, and failure modes---is required before any deployment
    claim
  \end{itemize}
\item
  \textbf{Performance Bottlenecks}

  \begin{itemize}
  \tightlist
  \item
    Cache memory consumption under large instruction universes
  \item
    Synchronization overhead in barrier-coordinated multi-agent
    execution
  \item
    Recompilation cost when hot-path thresholds are misconfigured
  \item
    The shipped hot-path detector keys on exact sequence identity, so
    trace diversity (similar-but-not-identical sequences) never
    accumulates counts; the EMA-based windowed detector specified in
    Section 4.2.2 is the designed remedy
  \item
    Hot-path state (cached sequences, counters, statistics) is currently
    unbounded; production use needs an eviction policy and a cap on
    tracked paths
  \end{itemize}
\item
  \textbf{Integration Challenges}

  \begin{itemize}
  \tightlist
  \item
    Adapter maintenance as provider function-calling surfaces evolve
  \item
    Version management of learned instructions across LLM updates
  \end{itemize}
\end{enumerate}

\subsection{Security and Privacy
Considerations}\label{security-and-privacy-considerations}

AgentISA's implemented security layer is the \texttt{SecurityMonitor} of
Section 5.6, which enforces task-level authentication, role-based
authorization, data-sensitivity classification, and configurable
resource-access policies; the coordinator consults it before every
assignment, and violations are recorded with timestamps. Beyond what is
implemented, we identify the following as design considerations for
hardening the architecture---not as claims about the current system:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Data privacy}: instruction-level access control exists via
  authorization policies; end-to-end data-flow tracking and
  privacy-preserving computation remain future work (Section 6.3.6).
\item
  \textbf{System security}: instruction pre/post-condition verification
  (Section 3.3.3) checks pure instructions' contracts against bounded
  state spaces, reducing mis-execution risk there; secure multi-agent
  communication channels and audit-log integrity are not yet addressed.
\item
  \textbf{Compliance}: deployments in regulated domains will require
  externally audited controls; the current system provides enforcement
  hooks, not certification.
\end{enumerate}

\subsection{Future Research
Directions}\label{future-research-directions}

\subsubsection{Theoretical Foundations}\label{theoretical-foundations}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Formal Semantics of Agent Instructions}

  Consolidating Section 3.1 and Appendix B into a single standalone
  semantics document---one formal framework covering the instruction
  language, state space, reduction rules, and type system---is the
  foundational next step; nothing in it is new machinery, and the
  composition here is what a journal-length treatment would spell out.
\item
  \textbf{Compositional Reasoning}

  Development of compositional proof systems for agent behaviors:

  \[
  \frac{\{P_1\}S_1\{Q_1\} \quad \{P_2\}S_2\{Q_2\} \quad \text{disjoint}(S_1, S_2)}{\{P_1 \land P_2\}S_1 \parallel S_2\{Q_1 \land Q_2\}}
  \]

  The disjointness side condition mirrors the \(\parallel\)-typing rule
  of Definition 3.6; without it the conjunction of preconditions does
  not guarantee either component's precondition during interleaving.
  This enables formal verification of complex agent systems through:

  \begin{itemize}
  \tightlist
  \item
    Modular verification
  \item
    Parallel composition rules
  \item
    Temporal property preservation
  \end{itemize}
\item
  \textbf{Type Theory for Agent Capabilities}

  A capability-based type system:

\begin{verbatim}
Type Capability = {
  Basic: {Perception, Action, Memory}
  Composite: Basic → Basic
  Emergent: P(Composite)
}
\end{verbatim}

  With typing rules: \[
  \frac{\Gamma \vdash a : \text{cap}_1 \quad \Gamma \vdash b : \text{cap}_2}
       {\Gamma \vdash a \circ b : \text{cap}_1 \otimes \text{cap}_2}
  \]
\end{enumerate}

\subsubsection{Advanced Instruction Set
Evolution}\label{advanced-instruction-set-evolution}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Self-Modifying Instructions}

  Formal model for instruction evolution (f is left abstract---the
  sketch names the inputs, not a concrete update rule):

  \[
  I_{t+1} = f(I_t, \text{Performance}_t, \text{Context}_t)
  \]

  With constraints:

  \begin{itemize}
  \tightlist
  \item
    Semantic preservation
  \item
    Performance monotonicity
  \item
    Safety guarantees
  \end{itemize}
\item
  \textbf{Context-Aware Optimization}

  Programmatic sketch (primitives like the performance model and variant
  generator are future work, not implemented machinery):

  \textbf{Context-aware optimization} --- for each observed context,
  predict the current instruction set's performance against a threshold,
  and if it falls short, select a best rewrite variant for that context
  and accumulate it into the set, returning the accumulated set:

\begin{verbatim}
function OPTIMIZE-CONTEXT(I, C)
    Let M be a context-performance model, R the rewrite rules
    for each context c in C do
        if PREDICT-PERFORMANCE(M, I, c) < THRESHOLD then
            candidates ← GENERATE-VARIANTS(I, R)
            I ← SELECT-BEST(candidates, c)
            UPDATE-MODEL(M, I, c)
        end if
    end for
    return I
end function
\end{verbatim}
\item
  \textbf{Cross-Model Instruction Mapping}

  Universal mapping framework: \[
  \phi_{A \rightarrow B}: I_A \rightarrow I_B
  \]

  Target properties (stated as goals, not delivered guarantees):

  \begin{itemize}
  \tightlist
  \item
    Semantic preservation
  \item
    Performance bounds
  \item
    Capability awareness
  \end{itemize}
\end{enumerate}

\subsubsection{Theoretical Performance
Bounds}\label{theoretical-performance-bounds}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Asymptotic Analysis}

  A natural next step is deriving cost bounds per composition
  operator---e.g., when does iterative composition \(i_1^*\) admit a
  closed-form cost model, and under what reuse structure does caching
  yield amortized \(O(1)\) effective cost per task? Our microbenchmarks
  (Section 5) measure the constants empirically; the corresponding
  asymptotic theory remains open.
\item
  \textbf{Resource Consumption Models}

  A calibrated resource model: \[
  R(i) = \alpha C_{cpu}(i) + \beta C_{mem}(i) + \gamma C_{io}(i)
  \]

  where \(\alpha, \beta, \gamma\) are platform-specific coefficients
  that should be fitted against real deployments rather than assumed.
\end{enumerate}

\subsubsection{Capability Assessment:
Extensions}\label{capability-assessment-extensions}

The instruction-level capability assessment subsystem
(\texttt{CapabilityProfile}, Section 3.5) ships in part---aggregation
and the coordinator's threshold selection are implemented and used,
while instruction-level metric extraction remains a specified stub. Two
extensions remain future work:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Benchmark-calibrated metrics}: correlating static,
  instruction-derived domain scores with end-to-end benchmark
  performance, in the manner of function-calling evaluations {[}17{]}
  and agent benchmarks {[}29{]}, so that weights \(w_k\) are empirically
  grounded rather than configured by hand.
\item
  \textbf{Cross-model comparison matrices}: extending the per-agent
  profile to a pairwise comparison framework \(\Delta(M_1, M_2)\) over
  capability dimensions, supporting systematic model selection for a
  given instruction workload.
\end{enumerate}

\subsubsection{Emergent Behavior
Analysis}\label{emergent-behavior-analysis}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Collective Intelligence Modeling}

  The open question is a formal metric for when multi-agent composition
  exceeds the sum of its members' capabilities---what emergence would
  have to mean measurably, rather than an appeal to an undefined
  \(\varphi\) over unioned capability sets.
\item
  \textbf{Learning Transfer Mechanisms}

  Knowledge transfer across agents composes the
  mining-extraction-validation pipeline of Section 3.3 rather than
  introducing new machinery: patterns mined from a source agent's traces
  would be adapted to a target agent's instruction set and re-validated
  (threshold and success-rate checks) before promotion. What Section 3.3
  does within one agent's traces, this direction would do across agents;
  the validation obligation transfers unchanged.
\end{enumerate}

\subsubsection{Security and Privacy
Extensions}\label{security-and-privacy-extensions}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Information Flow Control}

  Formal security model:

  \[
  \text{Secure}(P) \iff \forall s_1, s_2: L(s_1) = L(s_2) \implies L(\llbracket P \rrbracket s_1) = L(\llbracket P \rrbracket s_2)
  \]

  where \(L\) assigns security levels to states and outputs---the
  classical noninterference property, stated here for terminating runs
  (divergence and channel leakage out of scope).
\item
  \textbf{Privacy-Preserving Computation}

  Privacy guarantee framework:

  \[
  \text{PrivacyLoss}(M) \leq \epsilon + \sum_{i=1}^n \delta_i
  \]

  where:

  \begin{itemize}
  \tightlist
  \item
    \(\varepsilon\): the overall privacy budget
  \item
    \(\delta\)\(_{i}\): the per-operation privacy-loss parameter---this
    is the shape of differential-privacy composition theorems;
    identifying concrete mechanisms (hence concrete \(\delta\) values)
    is future work
  \end{itemize}
\end{enumerate}

These directions form a roadmap for moving AgentISA from
controlled-setting-validated infrastructure to a deployable, formally
verified agent platform. None of the frameworks above is implemented
today; Sections 6.3.3 and 6.3.4 are stated precisely enough to be
falsifiable, while the remaining sketches are programmatic and guide
subsequent work.

\section{Conclusion}\label{conclusion}

This paper presented AgentISA, an instruction set architecture that
treats LLM agent behavior as a first-class compilable artifact. Our
contributions are:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  A formal instruction set with compositional semantics, a type system,
  and pre/post-conditions, with sanity results stated as design
  rationale (Turing completeness as negative certification, Theorem 3.1;
  pure-core type safety, Theorem 3.2; extraction-time context
  preservation, Theorem 3.3) and semantic-preservation arguments for the
  optimization and scheduling transformations (Theorems 3.4--3.6).
\item
  Agentic Calling, which lifts provider-specific function calling into
  reusable, portable, cacheable agent instructions.
\item
  Automatic instruction learning based on frequency mining and
  deterministic action-signature grouping of execution traces.
\item
  A compiler and runtime applying classical optimizations---fusion,
  dead-code elimination, scheduling, and dynamic hot-path
  specialization---to agent instruction streams.
\item
  A multi-agent coordination layer with capability-based selection and a
  security monitor enforcing authentication, authorization, and
  data-sensitivity policies.
\end{enumerate}

The evaluation shows the optimizations are real and measurable under
controlled conditions: 59.5--79.6\% simulated-call reduction from
caching, 34.2\% instruction-count reduction from static compilation,
65.8\% trace shrinkage from hot-path optimization (Sections 5.2--5.5),
real-gateway validations of the cache and the compiled pipeline
(Sections 5.7 and 5.7.1), a four-task system-level characterization
(Section 5.8), and 43 functional tests for the multi-agent layer. These
are microbenchmark and controlled-setting results, not production
end-to-end measurements; the threats to validity of Section 5.9 stand.

AgentISA's longer-term significance is architectural: by giving agent
behavior an instruction-level contract, it makes agent systems amenable
to the same discipline that transformed hardware and compiler
engineering---precise specification, portability across backends, and
semantics-preserving optimization. Establishing the corresponding gains
on production workloads, and hardening the conditional sanity results
and semantic-preservation arguments into mechanically verified
implementations, is the immediate next step.

\section{Proof of Theorem 3.1 (Turing
Completeness)}\label{proof-of-theorem-3.1-turing-completeness}

\subsection{Strategy}\label{strategy}

We prove that AgentISA can simulate any program in the WHILE language
over the natural numbers. WHILE programs compute exactly the partial
recursive functions---WHILE is Turing equivalent {[}43, 44{]}---so a
sound simulation of WHILE by AgentISA establishes Turing completeness.
The argument is a sufficiency (simulation) argument over instruction
classes: the instruction classes of Definition 3.1 must jointly provide
unbounded storage, sequential composition, conditional branching, and
unbounded iteration. We show the control-flow class \(\mathcal{C}\) and
the state-management class \(\mathcal{S}\) suffice; neither effectful
class (the LLM-interaction class \(\mathcal{L}\) nor the resource class
\(\mathcal{R}\)) is needed, making the result conservative with respect
to the full instruction set.

\subsection{Source Language}\label{source-language}

Let WHILE be the language

\[
P ::= x := x+1 \mid x := x-1 \mid x := y \mid \texttt{skip} \mid \texttt{if } x = 0 \texttt{ then } P_1 \texttt{ else } P_2 \mid \texttt{while } x \neq 0 \texttt{ do } P \mid P_1 ; P_2
\]

over variables ranging over \(\mathbb{N}\) (with predecessor cut off at
0), with the standard small-step semantics. Configurations are pairs
\(\langle P, \sigma \rangle\) with store
\(\sigma : Var \to \mathbb{N}\).

\subsection{Encoding}\label{encoding}

\textbf{(i) Store.} A WHILE store \(\sigma\) is represented by the
AgentISA state \(s_\sigma \in \Sigma\), in the component managed by the
state-management instructions. Each variable \(x\) occupies a dedicated
cell; cells hold unbounded naturals, so \(\Sigma\) provides an unbounded
store---the crucial ingredient of the sufficiency argument.

\textbf{(ii) Instruction semantics (as used here).} The state-management
component of \(\Sigma\) carries, alongside the variable cells, an
\textbf{evaluation stack}; the five encoding instructions below operate
on that stack. Five instructions suffice for the encoding, with the
following operational meaning:

\begin{itemize}
\tightlist
\item
  \texttt{load} \(x\): pushes the contents of the cell for \(x\) onto
  the evaluation stack;
\item
  \texttt{store} \(x\): pops the top of the evaluation stack into the
  cell for \(x\);
\item
  \texttt{update} \((f)\): pops the top of the stack, applies the unary
  arithmetic function \(f\), and pushes the result;
  \texttt{update}\((-1)\) denotes the \emph{truncated predecessor}
  \(\lambda n.\,\max(n-1, 0)\), matching WHILE's cutoff semantics on
  \(\mathbb{N}\);
\item
  \texttt{branch} \((b, Q_1, Q_2)\): pops the top of the stack; if
  predicate \(b\) holds, execute \(Q_1\), else execute \(Q_2\);
\item
  \texttt{loop} \((Q)\): execute \(Q\); if its final \texttt{branch}
  returns to the loop head, repeat, else exit---that is, \texttt{loop}
  repeats its body for as long as the body's trailing test succeeds.
\end{itemize}

\textbf{(iii) Statements.}

{\def\LTcaptype{none} % do not increment counter

where \(\hat{P}\) denotes the compilation of \(P\). The no-op
\texttt{skip} compiles to the identity instruction \(\epsilon\); the
\texttt{while} row's trailing \texttt{branch} exits to \(\epsilon\) when
the guard fails, which is exactly the unfolding identity below.

\subsection{Simulation Lemma}\label{simulation-lemma}

\textbf{Lemma A.1.} For every WHILE configuration
\(\langle P, \sigma \rangle\) and its encoded AgentISA instruction
sequence \(\hat{P}\) started in state \(s_\sigma\):

\begin{enumerate}
\def\labelenumi{(\alph{enumi})}
\item
  if \(\langle P, \sigma \rangle \to \langle P', \sigma' \rangle\), then
  the AgentISA machine, started at configuration \((\hat{P}, s_\sigma)\)
  (remaining instruction sequence, \(\Sigma\)-state), reaches the
  configuration \((\hat{P}', s_{\sigma'})\)---remaining sequence
  \(\hat{P}'\) the encoding of the residual program \(P'\), state
  \(s_{\sigma'}\) the encoding of \(\sigma'\)---in finitely many steps;
  and
\item
  if \(P = \texttt{skip}\) (terminal), then \(\hat{P}\) terminates.
\end{enumerate}

\emph{Proof.} By structural induction on \(P\):

\begin{itemize}
\item
  \textbf{Assignments} (base cases). Each compiled sequence performs
  exactly the corresponding store update; (a) holds by executing the two
  or three instructions in order, (b) trivially.
\item
  \textbf{Conditional.} The \texttt{branch} instruction evaluates the
  zero test on the loaded value and transfers control to one of the
  compiled branch bodies. By the induction hypothesis applied to \(P_1\)
  and \(P_2\), each branch simulates its WHILE counterpart.
\item
  \textbf{Loop.} The WHILE unfolding identity
  \texttt{while\ x\ ≠\ 0\ do\ P\ ≡\ if\ x\ =\ 0\ then\ skip\ else\ (P\ ;\ while\ x\ ≠\ 0\ do\ P)}
  is simulated by the \texttt{loop} instruction's iteration: each
  iteration loads \(x\) and executes the trailing \texttt{branch}, which
  dispatches to \(\hat{P}\) when \(x \neq 0\) and to \(\epsilon\) (loop
  exit) when \(x = 0\). By an outer induction on the number of executed
  iterations (in addition to the structural induction on \(P\) announced
  above---the induction hypothesis applied to \(P\) covers each body
  execution, and the trailing branch discharges the loop
  condition)---the \(k\)-th WHILE iteration is matched by the \(k\)-th
  \texttt{loop} iteration.
\item
  \textbf{Sequence.} \(\hat{P}_1 \circ \hat{P}_2\) executes
  \(\hat{P}_1\) to completion, then \(\hat{P}_2\); both simulations
  compose by the induction hypothesis.
\end{itemize}

The case arguments above are the substantive reduction steps; expanding
each into a fully formal induction over the small-step rules (matching
each WHILE step against the transition functions \(\delta \in \Delta\)
of the corresponding AgentISA instructions) is mechanical and follows
the template of textbook simulation arguments {[}33, 43{]}. We mark
those expansions as routine and leave them to the reader.
\(\blacksquare\)

\subsection{Conclusion}\label{conclusion-1}

By Lemma A.1, every WHILE-computable function is AgentISA-computable.
Since WHILE is Turing equivalent---a classical result of computability
theory, with WHILE serving as the standard imperative model in semantics
texts such as {[}43{]}---AgentISA is Turing complete. \(\blacksquare\)

\subsection{Scope Remark}\label{scope-remark}

Turing completeness is a deliberately weak property---any language with
unbounded storage, branching, and unbounded iteration attains it. Its
role here is negative certification: the instruction set does not
artificially constrain what agent programs can express, so no
expressiveness objection can be raised against the architecture. The
claim says nothing about efficiency, and it is established without the
LLM-interaction class \(\mathcal{L}\), so it is conservative with
respect to the full instruction set of Definition 3.1.

\section{Proof of Theorem 3.2 (Type
Safety)}\label{proof-of-theorem-3.2-type-safety}

We prove type safety for the pure core by progress and preservation, in
the style of Pierce {[}36{]}. The proof runs over a \textbf{merged
judgment system}: the term typing judgment \(\vdash e : T\) for
\(\lambda\)-terms, and the instruction judgment
\(\vdash i\ \mathit{ok}[pre(i), post(i)]\) for instructions and their
compositions (both defined in B.1). Progress and preservation are each
proved by induction over the derivations of this merged system: the
\(\lambda\)-cases are the standard TAPL argument on term derivations;
the instruction cases are discharged by the standing totality assumption
and the per-operator premises of B.1(ii), with a joint runtime invariant
threaded through the composition cases.

\subsection{Core Calculus}\label{core-calculus}

Restrict attention to the pure core of the instruction language:
expressions over base types, dependent \(\Pi/\Sigma\) pairs, recursion
(\(\mu\)), \(\lambda\)-abstraction and application (whose
\(\beta\)-reduction rule appears in Section 3.1.2), and the composition
operators of Definition 3.6 applied to instructions carrying typed
pre/post-conditions. The small-step relation \(\rightarrow\) is
generated by \(\beta\)-reduction, the context rule
\(E[e_1] \rightarrow E[e_1']\), and, for each instruction \(i\), its
\textbf{fixed per-instruction} transition function \(\delta_i\).
Effectful instructions are treated in B.7.

The two judgment forms:

\begin{enumerate}
\def\labelenumi{(\roman{enumi})}
\item
  \textbf{Term typing} \(\vdash e : T\) --- the usual rules over base
  types, extended with the dependent \(\Pi/\Sigma\) introduction forms
  of Definition 3.2.
\item
  \textbf{Instruction typing} \(\vdash i\ \mathit{ok}[pre(i), post(i)]\)
  --- read ``\(i\) is a well-contracted state transformer'': \(pre(i)\)
  and \(post(i)\) are well-typed predicates over the state type, and the
  Definition 3.5 obligation
  \(\forall s \models pre(i): \delta_i(s) \models post(i)\) is
  discharged per instruction, offline, by the bounded verification of
  Section 3.3.3. Instructions are \textbf{not values and never stuck}:
  totality on precondition-satisfying states is a standing assumption
  --- for each instruction \(i\) with its transition function
  \(\delta_i\), \(\delta_i(s)\) is defined whenever
  \(s \models pre(i)\).
\end{enumerate}

Composition rules, for instructions \(i_1, i_2\) carrying contracts:

\[\frac{\vdash i_1\ \mathit{ok} \qquad \vdash i_2\ \mathit{ok} \qquad post(i_1) \Rightarrow pre(i_2)}{\vdash i_1 \circ i_2\ \mathit{ok}[pre(i_1),\, post(i_2)]}\]

\[\frac{\vdash i_1\ \mathit{ok} \qquad \vdash i_2\ \mathit{ok} \qquad pre(i_1) \Leftrightarrow pre(i_2) \quad \text{disjoint state footprints}}{\vdash i_1 \parallel i_2\ \mathit{ok}[pre(i_1),\, post(i_1) \wedge post(i_2)]}\]

\[\frac{\vdash i_1\ \mathit{ok} \qquad \vdash i_2\ \mathit{ok} \qquad post(i_1)\big|_{\text{trigger}} \Rightarrow pre(i_2)}{\vdash i_1 \triangleright i_2\ \mathit{ok}[pre(i_1),\, post(i_1) \wedge (\text{trigger} \Rightarrow post(i_2))]}\]

\[\frac{\vdash i\ \mathit{ok} \qquad \text{guard closed under } post(i) \qquad \text{guard} \Rightarrow pre(i)}{\vdash i^*\ \mathit{ok}[\text{guard},\, post(i)]}\]

Two premises deserve note. The \(\triangleright\) premise is evaluated
\textbf{on the outcome of \(i_1\) that triggers \(i_2\)}: \(i_1\)'s
execution can otherwise destroy \(pre(i_2)\), so the implication the
runtime invariant needs is \(post(i_1)\) restricted to the triggering
outcome, not \(pre(i_1) \Rightarrow pre(i_2)\) on the initial state. The
\(i^*\) premise adds \(\text{guard} \Rightarrow pre(i)\) because the
loop body re-enters: on every re-iteration the guard holds, so the
body's precondition must hold whenever the loop has not terminated.
These rules are generated from---do not add to---the semantics of
Definition 3.6.

\subsection{Canonical Forms}\label{canonical-forms}

If \(\vdash v : T\) and \(v\) is a value, then:

\begin{itemize}
\tightlist
\item
  \(T \in \{Bool, Int, String, Float\}\) implies \(v\) is a literal of
  that type;
\item
  \(T = \Pi(x:T_1).T_2\) implies \(v = \lambda x{:}T_1.\,e\) with
  \(\Gamma, x{:}T_1 \vdash e : T_2\);
\item
  \(T = \Sigma(x:T_1).T_2\) implies \(v = (v_1, v_2)\) with the
  components typed at the corresponding dependent types;
\item
  \(T = \mu X.T\) implies \(v\) is a rolled recursive value;
\item
  no instruction or instruction composition is a value (B.1(ii)):
  instructions are contracted state transformers, not term-level values.
\end{itemize}

\emph{Proof.} By inspection of the typing rules: each type has exactly
one value form, and the syntax of values is defined per type, so the
case analysis is exhaustive. This is the standard canonical-forms lemma
{[}36{]}. \(\blacksquare\)

\subsection{Lemma (Substitution)}\label{lemma-substitution}

If \(\Gamma, x{:}T' \vdash e : T\) and \(\vdash v : T'\), then
\(\Gamma \vdash e[x := v] : T\).

\emph{Proof.} By induction on the derivation of
\(\Gamma, x{:}T' \vdash e : T\). The non-dependent cases are the case
analysis of Pierce {[}36{]}, which we do not duplicate. The dependent
\(\Pi/\Sigma\) cases additionally require synchronizing the substitution
into the second component's type (\(T_2[x := v]\)), as in the
\(\beta\)-case of B.5 --- the standard dependent-type substitution
bookkeeping, not covered by the non-dependent treatment in {[}36{]}.
\(\blacksquare\)

\subsection{Lemma (Progress)}\label{lemma-progress}

If \(\vdash e : T\), then \(e\) is a value or there exists \(e'\) with
\(e \rightarrow e'\).

\emph{Proof.} By induction on the derivation. The \(\lambda\)-term
cases:

\begin{itemize}
\tightlist
\item
  \textbf{Literals and \(\lambda\)} are values.
\item
  \textbf{Application} \(e_1\,e_2\) with \(e_1 : \Pi(x:T_1).T_2\) and
  \(e_2 : T_1\): by the induction hypothesis, either \(e_1\) steps (then
  the context rule applies) or \(e_1\) is a value, in which case B.2
  gives \(e_1 = \lambda x.\,e\); similarly \(e_2\) either steps or is a
  value; when both are values, \(\beta\)-reduction applies. There is no
  stuck case, because the \(\Pi\)-type of \(e_1\) and B.2 jointly
  guarantee a \(\lambda\) in value position.
\end{itemize}

The instruction cases admit no stuck state by construction. Instructions
step by the standing totality assumption of B.1(ii) whenever their
precondition holds. Compositions maintain the runtime invariant
\textbf{each reached component's precondition holds}, per operator:

\begin{itemize}
\tightlist
\item
  \textbf{Sequencing \(\circ\):} \(pre(i_1)\) holds initially (the
  composition's contract); after \(i_1\) executes,
  \(post(i_1) \Rightarrow pre(i_2)\) re-establishes the invariant for
  \(i_2\).
\item
  \textbf{Parallel \(\parallel\):} disjoint state footprints keep each
  component's precondition valid throughout the interleaving --- neither
  component writes what the other's precondition or postcondition reads.
\item
  \textbf{Guarded \(\triangleright\):} on the triggering outcome of
  \(i_1\), the strengthened premise
  \(post(i_1)\big|_{\text{trigger}} \Rightarrow pre(i_2)\)
  re-establishes \(pre(i_2)\); on the non-triggering outcome, \(i_2\)
  does not run.
\item
  \textbf{Iteration \(i^*\):} the body re-enters only while the guard
  holds, and the premise \(\text{guard} \Rightarrow pre(i)\) makes each
  re-entry legitimate; when the guard fails, the loop is terminal.
\end{itemize}

The invariant is threaded jointly with B.5: each individual step
preserves the invariant by the per-operator argument above. For
iteration, either the guard is false (terminal) or the body's
precondition holds by \(\text{guard} \Rightarrow pre(i)\), and the body
steps by the induction hypothesis on the component derivation.
\(\blacksquare\)

\subsection{Lemma (Preservation)}\label{lemma-preservation}

If \(\vdash e : T\) and \(e \rightarrow e'\), then \(\vdash e' : T\).

\emph{Proof.} By induction on the derivation, with case analysis on the
step:

\begin{itemize}
\tightlist
\item
  \textbf{\(\beta\):} \((\lambda x.\,e)\,v \rightarrow e[x := v]\). The
  application rule types the redex at \(T_2[x := v]\); by B.3, the
  substituted term \(e[x := v]\) types at \(T_2[x := v]\), which is
  exactly the type the application rule assigned (the dependent-type
  bookkeeping; when \(x\) does not occur in \(T_2\) this degenerates to
  the usual \(T_2 = T\)).
\item
  \textbf{Context:} \(E[e_1] \rightarrow E[e_1']\) with
  \(e_1 \rightarrow e_1'\). By the induction hypothesis \(e_1' : T_1\);
  an induction on the structure of \(E\) re-types \(E[e_1']\) at the
  original type.
\item
  \textbf{Instruction transitions:} the instruction's \(\mathit{ok}\)
  judgment (B.1(ii)) certifies that \(\delta_i\) establishes \(post(i)\)
  from any \(pre(i)\)-satisfying state (discharged offline by the
  bounded verification of Section 3.3.3), so the reduct re-types at the
  postcondition.
\item
  \textbf{Composition operators:} each operator's step is typed by its
  B.1(ii) rule; the reduct's contract follows from the operator's stated
  conclusion (for \(\circ\), \(post(i_2)\); for \(\parallel\), the
  conjunction; for \(\triangleright\), the trigger-restricted
  conjunction; for \(i^*\), \(post(i)\)), by the induction hypothesis on
  the component derivations.
\end{itemize}

The remaining instruction-class cases repeat this pattern with
class-specific invariants; they are routine and omitted (the template is
the standard preservation argument for the corresponding constructs
{[}36{]}). \(\blacksquare\)

\subsection{Theorem 3.2}\label{theorem-3.2}

By B.4, a well-typed closed term is a value or takes a step; by B.5,
every step preserves typing. Hence no well-typed term reaches a stuck
state: well-typed programs in the pure core cannot go wrong.
\(\blacksquare\)

\subsection{Scope Remarks}\label{scope-remarks}

Two caveats state the theorem's boundaries honestly. First, B.4's appeal
to totality of transition functions on precondition-satisfying states is
an assumption about instruction \emph{implementations}, not something
the type system alone discharges. The per-instruction mechanism intended
to discharge it is the bounded verification of Section 3.3.3, which is
now shipped code: the checker mechanically discharges the obligation for
pure instructions on the state spaces it can enumerate --- exhaustively
for small enumerable domains, by deterministic bounded sampling beyond
--- while side-effectful instructions and state spaces beyond the
enumeration bound remain covered by hand argument and unit tests rather
than by the mechanical check. The theorem is conditional on the
obligation being (or becoming) true of each instruction, to the extent
stated. Second, effectful instructions (LLM calls, resource allocation)
can fail at runtime for reasons outside the type system (network errors,
exhausted capacity); Theorem 3.2 covers the pure core and effectful
instructions with checkable preconditions. Runtime failure handling for
the remaining cases is the responsibility of the fallback machinery of
Section 5.6, not of types.

\section{Proofs of Theorems 3.4 and
3.5}\label{proofs-of-theorems-3.4-and-3.5}

\subsection{Denotational Setup}\label{denotational-setup}

Fix the state space \(\Sigma\) (Definition 3.1's state space---not the
dependent-type constructor \(\Sigma\) of Definition 3.2). For a pure
instruction \(i\), let
\(\llbracket i \rrbracket : \Sigma \rightharpoonup \Sigma\) denote its
denotation, a partial function total on states satisfying \(pre(i)\).
Program denotation is defined by structural recursion on the composition
algebra of Definition 3.6:

\begin{itemize}
\tightlist
\item
  \(\llbracket i \rrbracket\) for atomic instructions (given);
\item
  \(\llbracket p_1 \circ p_2 \rrbracket = \llbracket p_2 \rrbracket \circ \llbracket p_1 \rrbracket\)
  (note the order: \(p_1\) executes first);
\item
  \(\llbracket p_1 \parallel p_2 \rrbracket(\sigma) = \llbracket p_2 \rrbracket(\llbracket p_1 \rrbracket(\sigma))\)
  for pure \(p_1, p_2\) with disjoint state footprints (as the
  \(\parallel\)-typing rule requires)---the order is immaterial because
  updates to disjoint cells commute on their domains;
\item
  \(\llbracket p_1 \triangleright p_2 \rrbracket(\sigma) = \llbracket p_2 \rrbracket(\llbracket p_1 \rrbracket(\sigma))\)
  when \(p_1\)'s outcome at \(\sigma\) is the trigger, and
  \(\llbracket p_1 \rrbracket(\sigma)\) otherwise (the denotation is
  defined on \(\Sigma + \text{outcome}\), with \(p_2\) applied
  conditionally on the trigger tag);
\item
  \(\llbracket p^* \rrbracket\) is the least fixed point of the
  corresponding functional.
\end{itemize}

Write \(p \equiv q\) iff
\(\llbracket p \rrbracket = \llbracket q \rrbracket\) on all states
where both are defined.

\subsection{Lemma (Atomic Rewrite
Soundness)}\label{lemma-atomic-rewrite-soundness}

Each rewrite rule implemented by the optimizer (Section 3.4.4) preserves
denotation.

\textbf{(i) Fusion.} \(i_1 \circ i_2 \rightarrow i_{12}\), with
\(pre(i_{12}) = pre(i_1)\), \(post(i_{12}) = post(i_2)\), and
\(i_{12}\)'s body stipulated to compute
\(\llbracket i_2 \rrbracket \circ \llbracket i_1 \rrbracket\)
(intermediate bindings named, so the composition is explicit). The
denotational claim is then an instance of the definition of \(\circ\)
(C.1): a body computing
\(\llbracket i_2 \rrbracket \circ \llbracket i_1 \rrbracket\) denotes
exactly \(\llbracket i_1 \circ i_2 \rrbracket\) (the associativity of
function composition is what fuses \emph{three or more} consecutive
instructions). \textbf{Two honest boundaries.} First, this is an
equality \emph{of the rewrite algebra}: it holds of the fused form whose
body computes the composite. The shipped compiler produces a formal
fused \emph{node} (merged metadata and dependencies) without generating
an executable composite body---code generation for fused nodes is not
implemented---so what the benchmarks measure is the structural fusion of
the formal stream, and the executable-fusion claim would additionally
require the codegen step. Second, the compiler applies fusion only when
output types of \(i_1\) match input types of \(i_2\) and both members
are pure, since denotational equality of the fused form presupposes
order-insensitivity of intermediate effects, and the shipped gate
achieves it via purity (the pure or order-insensitive alternative is
specified, not implemented).

\textbf{(ii) Dead-code elimination.} Instruction \(i\) is removed from
\(p\) when \(Def(i) \cap Live_{out}(i) = \emptyset\), with liveness the
standard fixpoint of
\(Live_{in}(i) = Use(i) \cup (Live_{out}(i) - Def(i))\) {[}33{]}. Claim:
if \(i\) is dead and side-effect-free, then
\(p \equiv p \setminus \{i\}\). Proof sketch: by induction on the suffix
program following \(i\), its denotation depends only on the live
variables at \(i\)'s position; \(i\) writes none of them, so removing
\(i\) cannot change any value subsequently read. The
side-effect-freeness gate matches the purity restriction of Definition
3.6 (Property 2 and the Remark following it)---instructions declared
\texttt{side\_effects=True} are never eliminated.

\textbf{(iii) Peephole combining.} Each rule
\((s_1, \dots, s_k) \rightarrow s'\) carries the verification obligation
\(\forall \sigma: \llbracket s_1 \circ \dots \circ s_k \rrbracket(\sigma) = \llbracket s' \rrbracket(\sigma)\),
to be discharged at rule-definition time (Section 4.1.3). Candidate
instances, \emph{illustrative only---the shipped optimizer registers
none of them}: \texttt{LOAD\ A;\ STORE\ B} composes to
\texttt{MOVE\ A→B} (degenerate to the identity when A = B, since the
value read is the value written; the general rule of Section 3.4.4);
consecutive \texttt{QUERY} instructions with identical (instruction,
params) pairs collapse to one query whose result is reused (the
batch-QUERY rule of Section 3.4.4, specialized to identical pairs) (an
obligation about a \emph{compile-time} rewrite; the caching measured in
Section 5.2 is a different, \emph{runtime} mechanism---a result cache
consulted at execution time---and its numbers do not evidence this
rule); consecutive \texttt{CONTEXT\_UPDATE}s compose to a single update
by associativity of the update function.

\emph{Proof.} Each case reduces to the construction of the rewritten
instruction and the definition of liveness. The inner inductions---on
the pair of bodies for (i), on suffix programs for (ii)---are routine
and left to the reader. \(\blacksquare\)

\subsection{Lemma (Compositionality)}\label{lemma-compositionality}

Let \(T\) be a program transform with
\(\llbracket T(p) \rrbracket = \llbracket p \rrbracket\) for all \(p\).
Then for any context \(C[\cdot]\) built from the composition operators,
\(\llbracket C[T(p)] \rrbracket = \llbracket C[p] \rrbracket\).

\emph{Proof.} By structural induction on \(C\). Each operator's
denotation (C.1) is defined compositionally in its constituents'
denotations, so substituting a denotationally equal constituent leaves
the whole unchanged. The parallel case uses the disjoint-footprint
hypothesis of the \(\parallel\)-typing rule (updates to disjoint cells
commute). The iteration case uses the defining property of least fixed
points: if the functionals induced by \(p\) and \(T(p)\) are equal, then
all finite approximants are equal (by the induction hypothesis), so
their suprema---the least fixed points---are equal. \(\blacksquare\)

\subsection{Theorem 3.4 (Optimization
Soundness)}\label{theorem-3.4-optimization-soundness}

\emph{Proof.} Read all equalities below as the partial-equivalence
\(\equiv\) of C.1 (equality on all states where both sides are defined),
since the DCE rule preserves denotation only on the defined domain and
can strictly enlarge it. The compiler applies a finite sequence of
rewrites \(O = R_k \circ \dots \circ R_1\) (finiteness follows from
compilation terminating; each pass is a bounded traversal). By induction
on \(k\): \(k = 0\) is trivial. For the step, write \(O = R \circ O'\).
By the induction hypothesis
\(\llbracket O'(p) \rrbracket \equiv \llbracket p \rrbracket\). Two
routes, by rule kind. \textbf{Fusion and peephole} are local subprogram
rewrites: the atomic-rewrite lemma (C.2) preserves the denotation of the
subprogram it rewrites, and the compositionality lemma (C.3) lifts the
preservation through any surrounding composition context.
\textbf{Dead-code elimination} is not local---liveness is computed over
the whole surrounding program---so it is handled at pass level directly
by C.2(ii)'s whole-program argument (\(p \equiv p \setminus \{i\}\)),
not through the lifting template. Hence
\(\llbracket R(O'(p)) \rrbracket \equiv \llbracket O'(p) \rrbracket \equiv \llbracket p \rrbracket\).
\(\blacksquare\)

\subsection{Theorem 3.5 (Pipeline
Correctness)}\label{theorem-3.5-pipeline-correctness}

Let \(s\) be a valid instruction sequence and \(S\) a schedule
satisfying:

\begin{itemize}
\tightlist
\item
  \textbf{(S1)} every instruction is dispatched exactly once;
\item
  \textbf{(S2)} for every dependency \((i_1, i_2) \in Deps\):
  \(start(i_2) \geq end(i_1)\) (the constraint of Section 3.4.3);
\item
  \textbf{(S3)} instructions sharing a parallel dispatch group are
  pairwise non-interfering (no data hazard, no resource conflict);
\item
  \textbf{(S4)} commit is in program order.
\end{itemize}

Then executing \(s\) under \(S\) yields the same final state as
sequential execution:
\(\llbracket s \rrbracket_S = \llbracket s \rrbracket_{seq}\).

\emph{Proof.} Let \(g_1, \dots, g_m\) be the dispatch groups of \(S\) in
commit order. By S4, groups commit in program order and group commits do
not interleave, so the union \(\bigcup_{j \leq t} g_j\) of committed
groups is always a program-order prefix---``executing all instructions
in those groups'' below means executing that prefix sequentially. We
show the invariant

\[\begin{gathered} I(t): \text{after committing } g_1, \dots, g_t,\\ \text{the architectural state equals the sequential state after}\\ \text{executing all instructions in those groups.}\end{gathered}\]

\begin{itemize}
\tightlist
\item
  \textbf{Base} (\(t = 0\)): both sides are the initial state.
\item
  \textbf{Step}: assume \(I(t)\). Every instruction in \(g_{t+1}\) has
  its dependencies in earlier groups (by S2, since it is scheduled after
  them), which by \(I(t)\) have completed and committed. Within the
  group, S3 gives pairwise non-interference: no instruction reads
  another group-member's output, and no two write the same location or
  resource. Hence the group's updates commute---for pure updates this is
  the diamond property, and for effectful instructions, S3's exclusion
  of shared resources makes their effects independent, so the combined
  effect is unique regardless of interleaving. The state after
  \(g_{t+1}\) is therefore independent of the group's internal
  interleaving and equals the sequential execution of the same
  instructions from the state at \(I(t)\).
\item
  By induction, \(I(m)\) holds; by S1 no instruction was skipped or
  duplicated.
\end{itemize}

This completes the induction over all dispatch groups, hence the proof.
\(\blacksquare\)

\textbf{Corollary (dispatch folding).} The ADVANCED and AGGRESSIVE
levels fold instructions into shared dispatches (Section 5.3). A folded
group satisfies S3 by construction: the grouping check admits only
side-effect-free instructions whose dependencies and declared outputs
are pairwise disjoint, so the group's members act on disjoint state
components and their updates commute (Definition 3.6, Property 2). By
Theorem 3.5 the fold changes the \emph{dispatch count} but neither the
semantics nor---consistent with the measurement of Section 5.3---the
effective instruction count.

\subsection{Theorem 3.6 (Pass-Pipeline
Soundness)}\label{theorem-3.6-pass-pipeline-soundness}

Every optimization in the pass pipeline is a finite composition of
rewrites covered by the atomic-rewrite lemma (C.2) or by the
dispatch-folding corollary of Theorem 3.5 (C.5)---the grouping pass is a
fold, not a local rewrite---and the argument of C.4 applies verbatim to
each rewrite layer. \(\blacksquare\)

\subsection{Scope Remark}\label{scope-remark-1}

Theorems 3.4--3.6 are \emph{conditional}: they hold of transformations
whose verification obligations (Sections 4.1.3 and 4.3.1) are
discharged. As stated there, those obligations are \textbf{specified but
not yet mechanically discharged}---the shipped optimizer registers no
peephole rules (the peephole obligation is dormant, and the
fusion/DCE/grouping passes are argued directly in C.2 and C.5 rather
than through the symbolic-execution checker), and the symbolic-execution
equivalence checker itself is a specification (Section 4.3.1). Where an
obligation is discharged only on bounded state spaces (Section 3.3.3),
the guarantee is correspondingly bounded: rewrites verified on the
explored subset are sound there. No such rewrite is registered today;
when one is, its application must be restricted to the explored subset
(that restriction is a dormant obligation of the future rule set, not
shipped behavior). What the shipped implementation does provide is
empirical semantics-preservation at task level: the system-level
demonstration of Section 5.8 re-executes an optimized stream and checks
byte-identical output.
