\begin{abstract}
Large Language Models increasingly run as autonomous agents, yet ad hoc
prompt engineering and per-provider function calling leave behavior hard
to specify, analyze, and optimize. We present AgentISA, an instruction
set architecture making agent behavior a first-class compilable
artifact: (1) a formal instruction set with compositional semantics, a
type system, and pre/post-conditions, bracketed at runtime by
pre-dispatch validation; a shipped bounded verifier for pure
instructions is unit-tested but not exercised by the benchmarks; (2)
Agentic Calling, lifting provider function calling into reusable,
cacheable instructions; (3) instruction learning mining recurring trace
patterns into developer-gated composite replays; (4) a compiler and
runtime applying classical optimizations---fusion, dead-code
elimination, pipeline scheduling, hot-path specialization---to
instruction streams.

A reproducible mock-backend microbenchmark drives the real
implementation: result caching cuts simulated API calls by 59.5--79.6\%
on synthetic Zipf workloads (2,000 tasks, 5 seeds); static compilation
removes 34.2\% of effective instructions (35.4\% at length 1,000) on
planted optimization targets at disclosed rates (Section 5.1.2); dynamic
hot-path optimization shrinks repeated traces by 65.8\%. A plain
exact-response cache matches this reduction to the digit; its distinct
value is reducing the program before any request is issued. Live-gateway
conformance checks across four model aliases confirm the implementation
matches its backend-free specification---cache statistics equal the
computed expectation on the two caching-protocol aliases; the compiled,
hot-path-adopted stream issues zero new gateway calls with
byte-identical artifacts (live-model-checked in one rerun); they test
the implementation, not model variation. A four-task characterization
bounds them at 12.5--25.0\% per-task compile shrink; a 100-trace census
characterizes generator-produced traces (Section 5.10; it does not
establish realism); 43 multi-agent tests provide functional validation.
These are controlled-setting results, not production end-to-end
measurements. Result caching, the benchmark-exercised static passes,
trace re-optimization, and six opt-in mechanisms ship; specified-only
components carry no claim (Section 5.11).
\end{abstract}

\section{Introduction}\label{introduction}

Recent advances in Large Language Models (LLMs) have produced systems
with strong understanding, generation, and---through instruction tuning
and human feedback---instruction-following capabilities {[}1, 2, 3, 4,
5, 6{]}, and a rapidly growing body of work couples them with tools,
memory, and control loops to build autonomous agents {[}9, 10, 11,
12{]}. Yet the engineering substrate beneath these agents remains ad
hoc: behaviors are specified as prompts and provider-specific
function-calling schemas---difficult to specify precisely, analyze
formally, or optimize systematically.

\subsection{Background and Motivation}\label{background-and-motivation}

Function calling---selecting an API from a declared tool set and
emitting structured arguments---has become the dominant interface
between LLMs and external systems {[}13, 14, 15{]}, consolidated by
standardization efforts such as the Model Context Protocol {[}18{]} and
measured by harnesses such as the Berkeley Function Calling Leaderboard
{[}17{]}. However, the unit of interaction remains the individual API
call: each call is dispatched, priced, and forgotten independently, even
when an agent repeatedly executes structurally identical work.

This per-call statelessness contrasts with how computing systems
historically handle repetitive execution: classical compilers and
hardware translate recurring patterns into cheaper forms---instruction
fusion, dead-code elimination, caching, trace-based dynamic optimization
{[}33, 34, 45{]}. Our motivating hypothesis is that these techniques
apply to LLM agent workloads: if agent behavior is expressed as an
explicit instruction stream rather than opaque prompts, recurring
patterns become visible to a compiler and optimizable with
well-understood, semantics-preserving transformations.

\subsection{Challenges in Current LLM-based Agent
Systems}\label{challenges-in-current-llm-based-agent-systems}

Five structural challenges motivate AgentISA:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Per-call statelessness of tool interfaces.} Mainstream
  function-calling protocols treat each call as an isolated event {[}13,
  14, 18{]}: the provider has no notion of a \emph{program} being
  executed, repeated identical work incurs repeated cost, and caching,
  where present, is an afterthought rather than a property of the
  execution model.
\item
  \textbf{Experience that does not accumulate as compiler-visible
  instruction structure.} Paradigms such as Reflexion {[}10{]} and
  Voyager {[}12{]} accumulate experience as verbal reflections or
  inference-time skill libraries---not reified as reusable, statically
  optimizable instructions a compiler can fuse, schedule, or eliminate.
\item
  \textbf{Absence of a shared behavioral contract.} Each multi-agent
  framework defines its own abstractions for roles, messages, and
  workflows {[}19, 20, 21, 22, 23, 24{]}; no instruction-level contract
  spans frameworks, fragmenting tooling and cross-framework analysis.
\item
  \textbf{Cost pressure at the wrong layer.} FrugalGPT {[}28{]} shows
  LLM inference cost is a first-order concern, and serving systems
  attack it below the API boundary {[}38, 39, 40, 41{]}; what is missing
  is the complementary, above-the-API layer that reduces the
  \emph{number and size} of calls an agent issues in the first place.
\item
  \textbf{Integration complexity across providers.} Portability is
  handled at the library level {[}26, 27{]}: logic written against one
  provider's function-calling surface does not transfer cleanly to
  another, and capability differences are hard to reason about
  systematically {[}17{]}.
\end{enumerate}

\subsection{Research Objectives and
Contributions}\label{research-objectives-and-contributions}

This paper introduces AgentISA, which addresses these challenges by
making agent behavior a first-class compilable artifact. Our
contributions are:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{A formal instruction set} for LLM agents with compositional
  semantics, a type system, and pre/post-conditions on every instruction
  (Section 3.1). Two deliberately modest sanity results serve as design
  rationale: Turing completeness (Theorem 3.1---a sanity check that the
  instruction set does not constrain expressiveness; it equally entails
  undecidability of static properties in general, which is why the
  Section 3.3.2 checker is bounded) and type safety for the pure core
  (Theorem 3.2), fixing the well-formedness obligation the offline
  bounded checker discharges for pure instructions (Section 3.3.2) and
  the runtime brackets with pre-dispatch validation.
\item
  \textbf{Agentic Calling}, a mechanism lifting provider-specific
  function calling into reusable, cacheable, semantically specified
  agent instructions, with a model-adapter layer for cross-provider
  portability (Section 3.2).
\item
  \textbf{Trace-based instruction learning}, which mines recurring
  instruction patterns from interaction traces and promotes validated
  recurring patterns into candidate instructions whose \texttt{execute}
  bodies replay the mined constituent subsequence by sequential
  composition over a shared context (Section 3.3; replay reproduces the
  recorded subsequence's outputs on the recorded inputs and, via shipped
  schema-checked binding, on unseen parameter values---constructor-baked
  parameters excepted, as the section states; the generalization is
  quantified: 1,050/1,050 unseen-parameter replays match the oracle
  exactly, Section 5.11).
\item
  \textbf{A compiler and runtime} implementing fusion, dead-code
  elimination, parallel-grouped scheduling, and dynamic hot-path
  specialization for agent instruction streams (Sections 3.4 and 4),
  together with an opt-in tree-pattern instruction selector (shipped,
  Section 4.1.1; benchmarked in Section 5.11: covering cost at or below
  the default heuristic's on 20/20 random IR trees, mean ratio 0.361,
  the gap synthetic-pricing-dependent) and cycle-accurate pipeline
  scheduling (specified, Section 4.1.2), with semantic-preservation
  arguments for the implemented rewrites (Theorems 3.4--3.6, proofs in
  Appendix C).
\item
  \textbf{An empirical evaluation} of the implemented system, with full
  methodology disclosure. On synthetic Zipf workloads (5 random seeds
  each), caching reduces simulated API calls by 59.5--79.6\% depending
  on skew, static compilation reduces the effective instruction count by
  34.2\% \(\pm\) 1.8\% (length 200), and dynamic optimization shrinks
  repeatedly executed traces by 65.8\% \(\pm\) 4.6\%; real-gateway
  experiments (Sections 5.7--5.7.1) validate the cache and compiled
  pipeline on a live gateway, a four-task characterization (Section 5.8)
  composes the mechanisms on realistic streams, a 100-trace vocabulary
  census (Section 5.10) documents the cross-task reuse structure of
  generator-produced traces, and six mechanism experiments (Section
  5.11) exercise the shipped opt-in components.
\item
  \textbf{Multi-agent coordination infrastructure} with
  capability-threshold agent selection (exercised with injected scores;
  the static metric extractor ships unwired, Section 3.5), execution
  planning, fallback strategies, and a security monitor enforcing
  authentication, authorization, resource-access, and data-sensitivity
  policies (Sections 3.5 and 5.6), validated by 43 passing functional
  tests; an opt-in fail-closed security mode now also ships, and its
  paired posture matrix (1,000 evaluation tasks per mode) shows it
  denying the 400 policy-gap tasks the fail-open default admits with
  zero false denials on well-specified tasks (Section 5.11).
\end{enumerate}

Our empirical claims are scoped accordingly: Sections 5.2--5.5 exercise
the real \texttt{agentflow.core.isa} implementation against a mock LLM
backend on synthetic workloads; Sections 5.7--5.8 extend the validation
at reduced scale on realistic streams; Section 5.10's census covers
generator-produced traces, Section 5.11's mechanism experiments run on
declaration-injection pools and synthetic trees, and Section 5.12
replays 1,960 recorded model trajectories---still no production
end-to-end measurements (threats to validity in Section 5.9).

\section{Related Work}\label{related-work}

\subsection{Foundation LLMs and Function
Calling}\label{foundation-llms-and-function-calling}

Modern LLMs are autoregressive transformers trained at large scale {[}1,
2, 3, 4{]}, with instruction tuning and reinforcement learning from
human feedback making them reliable instruction followers {[}5, 6{]}.
Function calling constrains their output distribution to a structured
output space,
\(F(x) = \text{argmax}_{f \in \mathcal{F}} P(f|x, \mathcal{F})\), where
\(\mathcal{F}\) is the set of declared functions and \(F(x)\) the
selected call. Frontier and open models alike expose this capability
with provider-specific schemas {[}2, 3, 4{]}; AgentISA does not modify
this layer but treats any such interface as a \emph{backend} targeted by
a common instruction set, as a compiler targets multiple processor
backends {[}33{]}.

The cost structure of this layer motivates our work. If each call
carries latency \(\tau_i\) plus a context-switching overhead
\(\omega_i\) (prompt reconstruction, serialization, cache misses; the
symbol \(\delta\) is reused in Appendix B for per-instruction transition
functions---the two are unrelated), then \(n\) similar calls cost
\(C(n) = \sum_{i=1}^{n} (\tau_i + \omega_i)\).

\textbf{Definition 2.1} (Function Call Overhead): The overhead of
executing \(n\) function calls is \(C(n)\), the sum of per-call
latencies and per-call context reconstruction costs. When repeated calls
carry identical semantic inputs and satisfy the cache-validity
conditions of Section 3.2, the repeated context-construction cost
\(\omega_i\) is avoidable---which is precisely the cost AgentISA's
caching and fusion are designed to remove. Structural similarity alone
does not make a re-invocation waste: if an input's dependencies have
changed or the call probes external state, re-execution has semantic
meaning; the cache-validity conditions, not structural identity, license
reuse. Under the result cache, the measured quantity is
\(C_{cached}(n) = \sum_{i \in miss}(\tau_i + \omega_i)\) and Section 5.2
reports \(|miss|/n\) as the call-reduction rate.

\subsection{Reasoning and Agent
Paradigms}\label{reasoning-and-agent-paradigms}

A second line enhances reasoning at prompt time: chain-of-thought
{[}7{]} and zero-shot reasoning {[}8{]}; ReAct's interleaved reasoning
and action {[}9{]}; Reflexion's verbal self-critique {[}10{]}; Tree of
Thoughts' deliberative search {[}11{]}; Voyager's open-ended skill
acquisition {[}12{]}. These paradigms define \emph{what} an agent should
do at the cognitive level; AgentISA defines \emph{how} the resulting
behaviors are represented, compiled, and executed as instructions---a
ReAct loop becomes an instruction sequence whose tool invocations are
fused, cacheable agentic calls.

\subsection{Tool Calling and Interface
Standardization}\label{tool-calling-and-interface-standardization}

Toolformer trains models to interleave tool calls with text {[}13{]};
Gorilla connects models to large API corpora {[}14{]}; ToolLLM scales
tool coverage to 16,000+ real-world APIs {[}15{]}; HuggingGPT
orchestrates model hubs {[}16{]}. On the standardization side, the Model
Context Protocol specifies how tools and context are exposed {[}18{]},
and the Berkeley Function Calling Leaderboard evaluates function-calling
accuracy cross-model {[}17{]}. These efforts standardize the
\emph{interface}; AgentISA standardizes the \emph{execution model above
it}: an AgentISA program compiled for two providers differs only in the
final translation step (Section 3.2.3), and interface-level standards
alone cannot fuse or eliminate calls.

\subsection{Multi-Agent Frameworks}\label{multi-agent-frameworks}

AutoGen frames agent applications as multi-agent conversations {[}19{]};
MetaGPT assigns standardized roles and workflows {[}20{]}; AgentVerse
facilitates multi-agent collaboration and studies emergent behaviors
{[}21{]}; ChatDev organizes agents as a software-development
organization {[}22{]}; CAMEL studies communicative agent societies
{[}23{]}; AutoGPT popularized autonomous goal-driven agents {[}24{]}.
AgentISA contributes a different artifact to this space: not a framework
or orchestration philosophy but an instruction-level
substrate---capability profiles, coordination instructions with barrier
semantics, and a security monitor providing capability-based agent
selection, per-stage fallback planning, and policy enforcement---that
any such framework could target (Section 3.5, Section 5.6).

\subsection{Prompt Compilation and Cost
Optimization}\label{prompt-compilation-and-cost-optimization}

Closest to our compilation perspective is DSPy, which compiles
declarative prompt programs into optimized pipelines via prompt search
and fine-tuning {[}25{]}; LangChain {[}26{]} and LlamaIndex {[}27{]}
provide library-level chaining and indexing abstractions; FrugalGPT
reduces cost through model cascades {[}28{]}. AgentISA differs in the
level at which optimization operates---DSPy optimizes \emph{prompts},
FrugalGPT \emph{model selection}, AgentISA \emph{instruction streams}:
fusion, dead-code elimination, parallel grouping (the shipped pipeline
scheduling), result caching, and hot-path specialization---implemented
and measured (Sections 3.4, 4, and 5)---plus opt-in tree-pattern
selection (Section 4.1.1) and specified cycle-accurate scheduling. These
transformations {[}33{]} compose with, rather than replace, prompt- and
model-level optimization.

\subsection{Benchmarks for Agent
Systems}\label{benchmarks-for-agent-systems}

AgentBench evaluates LLMs as agents across diverse environments
{[}29{]}; GAIA tests general assistant abilities {[}30{]}; PlanBench
probes planning and reasoning about change {[}31{]}; SWE-bench measures
resolution of real-world GitHub issues {[}32{]}. These benchmarks
evaluate \emph{end-to-end capability}; AgentISA's evaluation measures
\emph{subsystem behavior under controlled conditions}---call reduction,
instruction-count reduction, trace shrinkage (Section 5). The two are
complementary: instruction-level metrics can attribute end-to-end gains
to specific mechanisms when such gains are measured, and are
reproducible without live model access.

\subsection{Classical Compiler and Architecture
Techniques}\label{classical-compiler-and-architecture-techniques}

AgentISA's optimization machinery is deliberately classical:
tree-pattern instruction selection with dynamic programming, peephole
optimization, and data-flow-based dead-code elimination {[}33{]};
pipelining, hazard detection, and resource-constrained scheduling
{[}34{]}; the open, well-specified instruction-set discipline of RISC-V
{[}35{]}; type safety via progress-and-preservation {[}36{]}; formally
verified compiler correctness in the CompCert tradition {[}37{]}. Our
contribution is not a new technique but the demonstration that this
machinery transfers to LLM agent workloads, with the
semantic-preservation arguments adapted to instructions with
pre/post-conditions (Appendix C).

\subsection{LLM Serving Systems}\label{llm-serving-systems}

Below the API boundary, the serving community has made inference
dramatically cheaper: PagedAttention {[}38{]}; Orca's continuous
batching {[}39{]}; FlashAttention's IO-aware attention {[}40{]};
Mooncake's KVCache-centric disaggregation {[}41{]}; inference-cost
energy analyses {[}42{]}. This line and AgentISA are orthogonal layers
of the same stack: serving systems make each call cheaper; AgentISA
reduces how many calls an agent makes and how much redundant work each
carries---the two compose (whether they multiply is unmeasured).

\subsection{Research Gaps and Our
Contributions}\label{research-gaps-and-our-contributions}

In summary, the literature leaves four gaps that AgentISA addresses:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{No instruction-level contract for agent behavior.} Interfaces
  are standardized {[}13, 14, 18{]} and frameworks numerous {[}19, 20,
  21, 22, 23, 24{]}, but no shared instruction set spans providers and
  frameworks.
\item
  \textbf{No compiler for agent behavior.} Prompt-level compilation
  exists {[}25{]} and model-level cost reduction exists {[}28{]}, and
  \emph{caching itself is well-trodden ground}---at the response level
  (GPTCache {[}46{]}), the KV-prefix level (RadixAttention/SGLang
  {[}47{]}), and the provider prompt-caching level. None of these layers
  expose an \emph{instruction-level} contract: caching there optimizes
  model serving---invisible to the agent program's structure, without
  effect on it. Instruction-level fusion, elimination, and
  scheduling---with cacheability a declared property of the instruction
  set---have not, to our knowledge, been demonstrated.
\item
  \textbf{No semantics-preserving account of agent optimization.}
  Serving work verifies kernels and schedulers, not agent-level
  transformations; we provide progress-and-preservation-style arguments
  for ours (Theorems 3.2, 3.4, 3.5, 3.6).
\item
  \textbf{No reproducible instruction-level evaluation.} Existing
  benchmarks measure end-to-end capability {[}29, 30, 31, 32{]}; we
  contribute a seed-controlled evaluation: a microbenchmark suite with
  fully disclosed synthetic workloads and mock-backend instrumentation,
  extended by real-gateway and system-level validations (Section 5).
\end{enumerate}

\subsubsection{Instruction Set
Specification}\label{instruction-set-specification}

The AgentISA instruction set is formally defined as a tuple:

\textbf{Definition 3.1} (AgentISA Core):
\(\text{AgentISA} = (I, T, \Sigma, \Delta, \Phi)\), where \(I\) is the
set of instructions, \(T\) the type system, \(\Sigma\) the state space,
\(\Delta\) the transition function set, and \(\Phi\) the verification
function set.

Following the conventions of classical instruction set design {[}33, 34,
35{]}, we define the basic instruction format:

\begin{verbatim}
INSTRUCTION = {
    opcode: OPCODE,
    args: ARGS[],
    precondition: PRED,
    postcondition: PRED,
    context: CONTEXT
}
\end{verbatim}

The instruction set is categorized into four fundamental classes:
\textbf{control flow} (\(\mathcal{C} = \{seq, branch, loop, call\}\)),
\textbf{state management}
(\(\mathcal{S} = \{load, store, update, cache\}\)), \textbf{LLM
interaction} (\(\mathcal{L} = \{query, response, context\}\)), and
\textbf{resource management}
(\(\mathcal{R} = \{allocate, free, monitor\}\)).

Two sanity results anchor the definition; neither introduces new
machinery {[}33, 36{]}---Theorem 3.1 certifies that the instruction set
does not constrain what agent programs can express, and Theorem 3.2
fixes the well-formedness obligation discharged by the offline bounded
checker for pure instructions (Section 3.3.2) and bracketed at runtime
by pre-dispatch context validation (Section 3.2.3).

\textbf{Theorem 3.1} (Turing Completeness): The AgentISA instruction set
is Turing complete.

\emph{Proof sketch}: a translation from WHILE programs---known Turing
equivalent {[}44{]}---to instruction sequences, by simulation: state
management instructions encode an unbounded store, control-flow
instructions encode composition, branching, and iteration. The full
construction is in Appendix A.

\subsubsection{Type System and
Semantics}\label{type-system-and-semantics}

The type system T extends the simply-typed discipline of Pierce {[}36{]}
with dependent-type constructions (\(\Pi\), \(\Sigma\), \(\mu\)):

\textbf{Definition 3.2} (AgentISA Type System): \[
T ::= \text{Base} \mid \Pi(x:T_1).T_2 \mid \Sigma(x:T_1).T_2 \mid \mu X.T
\]

where Base types include \{Bool, Int, String, Float\},
\(\Pi\)/\(\Sigma\) represent dependent function/pair types, and \(\mu\)
recursive types. The semantic rules follow standard operational
semantics {[}43{]} (a context rule and \(\beta\)-reduction).

The pure core carries a standard type-safety argument---progress and
preservation, in the style of Pierce {[}36{]}---discharging the
well-formedness role fixed in Section 3.1 and extended to the shipped
instruction set by the bounded checker of Section 3.3.2:

\textbf{Theorem 3.2} (Type Safety for the Pure Core): Well-typed
programs in the pure core calculus of Appendix B---the
\(\lambda\)-fragment (base types, dependent \(\Pi\)/\(\Sigma\) types,
recursion) plus the composition operators applied to instructions
carrying typed pre/post-conditions---cannot ``go wrong'', under the
per-instruction validity obligation of Definition 3.5 (stated in Section
3.3.2 below; pre/post-conditions), with transition functions assumed
total on precondition-satisfying states (Appendix B.7). Effectful
instruction classes are embedded via their typed pre/post-conditions and
covered to the extent their preconditions are checkable.

\emph{Proof sketch}: By the standard two-lemma technique---progress
(\(\forall e, T.\ \vdash e : T \implies \mathrm{value}(e) \lor \exists e'.\ e \to e'\))
and preservation
(\(\forall e, e', T.\ \vdash e : T \land e \to e' \implies \vdash e' : T\))---as
presented in Pierce {[}36{]}, both proved by induction over Appendix B's
merged judgment system, with a joint argument for the composition cases:
progress from the Definition 3.5 obligation plus totality, preservation
from postcondition typing, composition via the chained invariant
\(post(i_1) \Rightarrow pre(i_2)\) (Appendix B).

\textbf{Scope of the totality premise.} Totality rules out exactly the
failure modes that dominate live LLM calls---timeouts, refusals,
malformed replies, and \texttt{max\_tokens} truncation (the Section
5.7.1 census records ceiling-binding on 22/22 calls at the 512 budget on
the reasoning alias). Theorem 3.2 therefore constrains the composition
and dataflow layer only; an error-value semantics (\(\delta\) returning
a typed Err, progress weakened to ``value, Err, or reducible'') that
would make totality constructive remains future work (the premise is
recorded in Appendix B.7).

\subsubsection{LLM Integration
Interface}\label{llm-integration-interface}

The LLM integration interface is a protocol playing the same role for
agent backends that the Model Context Protocol plays for tool exposure
{[}18{]}: \(\mathcal{P}_{LLM} = (Q, R, C, \psi)\), where \(Q\) is the
query space (JSON Schema), \(R\) the response space (JSON Schema), \(C\)
the context-management surface (today the context-window size), and
\(\psi\) the state mapping Map\textless AgentState,
LLMContext\textgreater---corresponding to the interface conventions of
modern function-calling providers {[}3, 18{]}.

\subsection{Agentic Calling Framework}\label{agentic-calling-framework}

\subsubsection{Function Calling to Agentic Calling
Transformation}\label{function-calling-to-agentic-calling-transformation}

The transformation from function calling to Agentic Calling is
formalized as \textbf{Definition 3.3} (Agentic Transformation):
\(\mathcal{T}: F \rightarrow A\), where \(F\) is the function call space
and \(A\) the agent instruction space.

\(\mathcal{T}\) preserves call semantics \textbf{on the dispatch path}
by construction: the synthesized instruction records the function
signature verbatim and delegates execution to the original call, so
\(\text{sem}(\mathcal{T}(f)) \equiv \text{sem}(f)\) whenever the cache
is bypassed. \textbf{On the cached path} preservation holds only under
Section 2.1's cache-validity conditions (determinism, no external-state
probing, unchanged dependencies); outside them the cache is an
intentional semantic change---the mechanism's benefit. Context embedding
is content-preserving by the copy construction (Theorem 3.3); that
theorem covers the context field only, not call semantics.

The three steps---function signature analysis, context embedding,
instruction synthesis---mirror the signature-to-call conventions of
function-calling interfaces {[}13, 14{]}.

\subsubsection{Context Preservation and State
Management}\label{context-preservation-and-state-management}

State management in AgentISA follows a formal state machine model,
\(M = (S, s_0, \delta, F)\): states \(S\) with initial state \(s_0\),
transition function \(\delta\), and final states \(F\).

Extraction-time context preservation is guaranteed by construction
(Theorem 3.3); at runtime it is only monitored:

\textbf{Theorem 3.3} (Context Preservation): Let \(\phi\) be the context
interpretation function (defined compositionally over context
\emph{contents}---the keys and values the context carries), and \(t\)
the extraction transformation that embeds a context \(c\) verbatim into
an instruction's \texttt{context} field. Then, for every \(c \in C\):
\(\phi(t(c)) = \phi(c)\).

\emph{Proof}: By the definition of \(t\), the extracted instruction
carries a verbatim copy of \(c\); since \(\phi\) is defined over context
contents and the copy is content-identical, \(\phi(t(c)) = \phi(c)\)
holds by construction---a \emph{design invariant of the extraction
pipeline} (the implementation copies rather than re-encodes). At runtime
the shipped checks are constraint-based and bracket the
transition---\texttt{AgenticTransformer.validate\_context} checks the
registered context constraints pre-dispatch,
\texttt{verify\_context\_preservation(before,\ after)} re-checks them
pairwise across the executed transition (mechanics in Section
3.2.3)---and perform no structural validation of the carried context.
Extraction-time preservation is discharged by the copy construction;
preservation across an executed transition is \emph{monitored, not
guaranteed}, by the runtime checks. \(\blacksquare\)

\subsubsection{Cross-model
Compatibility}\label{cross-model-compatibility}

Cross-model \emph{protocol} compatibility---not behavioral equivalence
of models---is achieved through an abstract interface layer
(provider-independent instruction representation with provider-specific
adapters):

\begin{verbatim}
Interface ModelAdapter {
    translate: AgentInstruction → ModelSpecificCall      // shipped: translate_instruction
    normalize: ModelSpecificResponse → AgentResponse    // shipped: normalize_response
    validateContext: Context → Boolean                  // shipped: AgenticTransformer.validate_context
}
\end{verbatim}

All three operations ship: \texttt{translate} is
\texttt{ModelAdapter.translate\_instruction} (with registered type
transformations); \texttt{normalize} is
\texttt{ModelAdapter.normalize\_response}, folding the two dominant wire
shapes---Anthropic (typed \texttt{content} blocks,
\texttt{usage.input\_tokens}/\texttt{output\_tokens}) and OpenAI
(\texttt{choices{[}0{]}.message},
\texttt{usage.prompt\_tokens}/\texttt{completion\_tokens})---into a
canonical \texttt{AgentResponse} envelope (content, tool calls, usage,
model, raw), so downstream code never branches on provider syntax; and
\texttt{validateContext} is
\texttt{AgenticTransformer.validate\_context}, the pre-execution
complement of the shipped post-hoc
\texttt{verify\_context\_preservation(before,\ after)}---it evaluates
the registered context constraints against a single state before
dispatch, applying two-argument predicates reflexively \((v, v)\)
(single-argument ones directly) and leaving constraints over absent keys
vacuously satisfied, so key \emph{deletion} goes unreported---a blind
spot analogous to non-reflexive constraints (e.g.~strict growth), which
are not detectable pre-execution.

Motivated by cross-model function-calling studies {[}17{]} and open
protocol efforts {[}18{]}---providers differ in surface syntax but can
agree on \emph{protocol shape}---the requirement is a
\textbf{protocol-level contract on the adapter layer}: each adapter
\(m\)'s request and response normalizers, \(\text{norm}_{in}(m)\) and
\(\text{norm}_{out}(m)\), are total on the supported request and
response classes, mapping every supported raw request and response into
the unified schemas, with declared types preserved and errors classified
into a common taxonomy. This is deliberately weaker than semantic-output
equivalence---\(m_1 = m_2\) would already demand determinism, which no
LLM provides---and cross-model \emph{behavioral} comparison is an
empirical question at benchmark level (Section 3.5, {[}17, 29{]}).

\subsection{Trace-Based Instruction
Learning}\label{trace-based-instruction-learning}

\subsubsection{Dialogue Pattern
Recognition}\label{dialogue-pattern-recognition}

Pattern recognition in AgentISA is frequency-based and deterministic
(action-signature grouping) rather than grammatical; it is implemented
in \texttt{agentflow.core.isa.pattern\_mining} and
\texttt{agentflow.core.isa.instruction\_learning}. To prevent
over-reading: the subsystem is a \textbf{discovery-and-replay pipeline,
not an autonomous learning loop}. Its five stages are (i) trace-derived
pattern mining (this section), (ii) dialogue-derived template extraction
(§3.3.2), (iii) candidate validation (support and success-rate
thresholds), (iv) \emph{gate-controlled} promotion
(\texttt{agentflow.core.isa.auto\_promotion} edits the optimizer's rule
set only through an approval gate; opt-in \texttt{auto\_approve} removes
the human step), and (v) parameterized composite replay. Stages (i)--(v)
ship; the stage-(iv) gate defaults to approval.

\textbf{Definition 3.4} (Instruction Sequence Pattern): A pattern \(p\)
over the instruction alphabet \(I\) is a non-empty contiguous sequence
\(p = (i_1, \dots, i_k) \in I^k\) together with two frequency
statistics:

\begin{itemize}
\tightlist
\item
  \textbf{Support}:
  \(sup(p) = P(p \text{ occurs as a contiguous subsequence in a randomly drawn trace})\)
\item
  \textbf{Confidence}:
  \(conf(p \Rightarrow j) = P(i_{t+1} = j \mid (i_{t-k+1}, \dots, i_t) = p)\)
\end{itemize}

A pattern is \emph{frequent} if \(sup(p) \geq \sigma_{min}\) and
\emph{predictive} if \(\max_j conf(p \Rightarrow j) \geq \gamma_{min}\),
for thresholds \(\sigma_{min}, \gamma_{min} \in (0, 1]\).

Pattern recognition proceeds in three stages:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Frequent-sequence mining.} Candidate subsequences are
  enumerated from execution traces with occurrence counts; successor
  statistics are accumulated alongside, and sequences below
  \(\sigma_{min}\) are pruned together with their statistics---so
  confidence is estimated only over frequent sequences. The output is
  the set of frequent, predictive patterns.
\item
  \textbf{Behavior grouping.} The shipped \texttt{PatternRecognizer}
  groups dialogues deterministically by \emph{action signature}---the
  sorted set of system-turn contents---and promotes each sufficiently
  supported bucket into a pattern. (An earlier prototype and why it was
  abandoned: artifact notes, supplementary F.8.) Promotions split by
  source: trace-mined promotions execute by \textbf{composite
  replay}---the \texttt{execute} body re-runs the recorded constituent
  sequence, with its dataflow edges, in mined order against a shared
  context, merging outputs and returning the keys its
  \texttt{produces\_X} postconditions declare---while dialogue-mined
  templates run an attached \texttt{executor} if one exists (dict
  results checked against the declared \texttt{produces\_X}
  postconditions) and otherwise raise \texttt{NotImplementedError}
  rather than silently no-opping. Promotion is deterministic (pattern
  identity derives from the mined instruction-id sequence), and replay
  is plain sequential composition, so a learned instruction reproduces
  its recorded subsequence's outputs on the recorded inputs; on unseen
  parameter values the binding above re-runs the recorded operator
  \emph{instances}, so parameters baked into an operator's constructed
  state cannot be rebound, and the schema is observational---mixed or
  unseen types fall back to \texttt{object}. The mining-to-optimization
  path now exists: an approved proposal registers the fused instruction
  and installs a name-level peephole rule into the optimizer's rule set,
  gated by default on a developer's approval.
\item
  \textbf{Pattern validation.} Each candidate is checked for
  significance---support above \(\sigma_{min}\) and, for
  dialogue-derived patterns, an acceptable success rate---before
  promotion to a candidate instruction.
\end{enumerate}

The design is deliberately statistical---agent traces are short and
noisy, and frequency statistics degrade gracefully where grammar
induction would overfit---and it composes with the compiler: a frequent,
verified pattern is exactly the promotion candidate of Section 3.4.4.

\subsubsection{Instruction Optimization and
Verification}\label{instruction-optimization-and-verification}

Optimization is coupled to verification: where verified-compilation
efforts such as {[}37{]} verify the transformations of a whole compiler,
AgentISA's verification targets a different granularity---the validity
of individual instructions and the obligations of individual rewrites:

\textbf{Definition 3.5} (Instruction Verification): An instruction \(i\)
is valid if
\(\forall s \in S: \text{pre}(i,s) \implies \text{post}(i,\text{exec}(i,s))\).

The shipped checker (\texttt{agentflow.core.isa.bounded\_checker})
enumerates the candidate input states derived from the declared
parameter constraints---exhaustively for finite domains such as
\texttt{bool} and enum parameters, and as a bounded, deterministically
sampled set (cap 256) otherwise---making it \emph{bounded}, not
complete. For every pure instruction it filters states by well-typedness
and preconditions, executes it, and evaluates three obligations per
surviving state---progress, preservation (declared outputs present and
well-typed), and the postcondition itself. Side-effectful instructions
are never executed and are reported out of scope; their obligation is
delegated to authoring-time tests and review. Theorem 3.2 is conditional
on this obligation, Theorems 3.4--3.6 carry the separate rewrite
obligations of Appendix C.7, and beyond the enumeration bound the
condition remains substantive rather than discharged (Appendices B.7 and
C.7)---formally, the checker establishes
\(\forall s \in S_{bounded} \subseteq S: \text{pre}(i,s) \implies \text{post}(i,\text{exec}(i,s))\),
where \(S_{bounded}\) is the explored subset; completeness is traded for
tractability---the standard bounded-exploration compromise, with the
operational-semantics treatment of instruction meaning following
{[}36{]}.

The guarantee therefore comes in two explicitly separate layers.
\textbf{Layer 1 (theory, conditional):} Theorem 3.2 and the type-safety
results of Appendix B hold for every program whose instructions satisfy
Definition 3.5 \emph{on all of \(S\)}, under the total-definedness
premise of Appendix B.7---a mathematical statement about a proof
obligation, not about the checker. \textbf{Layer 2 (implemented
verification):} the shipped checker discharges that obligation only on
\(S_{bounded}\) and only for pure instructions, as described above.
Success of the bounded check is evidence toward, not a proof of, Layer
1's premise; no claim in this paper equates the two.

\textbf{Theorem 3.4} (Optimization Soundness): Every atomic rewrite of
the pass pipeline---fusion (Appendix C.2's rule, applied by the
combining pass), dead-code elimination, and instruction combining
(Section 3.4.4)---preserves the denotation of the instruction sequence
it transforms: \(\text{sem}(r(i)) \equiv \text{sem}(i)\), read as the
partial equivalence of C.1.

\emph{Proof sketch}: By structural induction on instruction composition.
The base case shows each atomic rewrite preserves the denotation of a
single instruction; the inductive step lifts preservation through each
composition operator of Definition 3.6. The full proof, with the
per-rewrite case analysis, is in Appendix C.

The shipped checker
(\texttt{agentflow.core.isa.bounded\_checker.verify\_instruction})
implements Definition 3.5 on the bounded state space and reports
violations structurally (listing in Appendix D.11 of the supplementary
material).

\subsection{Instruction Organization and
Optimization}\label{instruction-organization-and-optimization}

\subsubsection{Instruction Composition}\label{instruction-composition}

AgentISA supports hierarchical instruction composition through a formal
composition algebra:

\textbf{Definition 3.6} (Instruction Composition): Given instructions
\(i_1, i_2 \in I\), we define four composition operators---Sequential
\(i_1 \circ i_2\), Parallel \(i_1 \parallel i_2\), Conditional
\(i_1 \triangleright i_2\), and Iterative \(i_1^*\)---whose denotations
(sequential execution; parallel interleaving under disjoint state
footprints; guarded execution of \(i_2\) on \(i_1\)'s triggering
outcome; zero-or-more iterations of \(i_1\)) are fixed in Appendix C.1.

Composition follows algebraic properties. Properties 1 and 3 hold for
all instructions; Property 2 is a \emph{conditional} law---purity and
pairwise footprint disjointness together do \emph{not} suffice, and
idempotence of \(i_1\) must be assumed separately:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Associativity} (all instructions, up to denotation):
  \((i_1 \circ i_2) \circ i_3 = i_1 \circ (i_2 \circ i_3)\).
\item
  \textbf{Distributivity} (conditional on idempotent \(i_1\) and
  pairwise-disjoint footprints): the law
  \(i_1 \parallel (i_2 \circ i_3) = (i_1 \parallel i_2) \circ (i_1 \parallel i_3)\)
  holds under two premises---\textbf{(a)} idempotence of \(i_1\) on
  precondition-satisfying states and \textbf{(b)} pairwise footprint
  disjointness---neither of which follows from purity (necessity
  arguments and counterexamples: supplementary C.3). The shipped
  compiler does not rely on the law; it is stated for the algebra's
  completeness.
\item
  \textbf{Identity}: \(i \circ \epsilon = \epsilon \circ i = i\).

  where \(\epsilon\) is the empty (identity) instruction.
\end{enumerate}

\textbf{Remark} (implementation consequence): distributivity also fails
for side-effectful instructions, for the same double-execution reason.
Accordingly, parallel grouping is gated on purity plus disjoint
dependencies and disjoint outputs, and \texttt{side\_effects=True}
instructions are excluded from all such rewrites.

\subsubsection{Instruction Pipeline
Design}\label{instruction-pipeline-design}

We formalize the instruction pipeline as a directed acyclic graph (DAG):

\textbf{Definition 3.7} (Pipeline DAG): \(P = (V, E, \lambda, \delta)\),
where \(V\) are the pipeline stages, \(E\) the dependencies between
stages, \(\lambda\) the stage latency function, and \(\delta\) the data
transfer function.

The pipeline's stages (FETCH \(\rightarrow\) DECODE \(\rightarrow\)
SCHEDULE \(\rightarrow\) EXECUTE \(\rightarrow\) COMMIT, with hazard
detection, dependency tracking, and resource allocation maps; listings
in Appendices D.2--D.3 of the supplementary material) are organized
around this DAG.

\textbf{Theorem 3.5} (Pipeline Correctness): For any valid instruction
sequence \(s\) and any schedule \(S\) satisfying conditions S1-S4 of
Appendix C.5---each instruction dispatched exactly once, dependencies
respected, dispatch groups pairwise non-interfering, commit in program
order---pipeline execution preserves program semantics.

The shipped dispatch implements the unit-slot case of S1--S4; the
multi-period schedule remains conditional on the stated premise.

\emph{Proof}: By induction over the dispatch groups of \(S\) in commit
order, under the invariant that the architectural state after committing
each prefix of groups equals the sequential state after the same
instructions; S1--S4 supply exactly-once dispatch, dependency order,
group commutativity, and in-order commit (details in Appendix C.5).

\subsubsection{Instruction Selection and
Scheduling}\label{instruction-selection-and-scheduling}

Instruction selection follows a tree-pattern matching approach:

\textbf{Definition 3.8} (Selection Pattern):
\(\pi = (\tau, C, \text{cost}, \text{code})\), where \(\tau\) is a tree
pattern over the IR (unrelated to the type-system symbol \(T\) of
Definition 3.2), \(C\) the context constraints on the surrounding state,
and cost/code the cost function and generated code.

Given an IR tree \(t\) to cover, the selection process is formalized as
\(\text{Select}(t) = \argmin_{\pi \in \Pi} \{\text{cost}(\pi) \mid \text{matches}(\pi.\tau, t) \land \text{satisfies}(t, \pi.C)\}\).

Definition 3.8's optimal selection ships as the opt-in DP selector of
Section 4.1.1; the default remains the heuristic matcher run by Section
5's benchmarks.

Scheduling is formalized as the classical delay-minimization problem
under dependency and capacity constraints: minimize the total stall
subject to dependency order (\(\text{start}(i_2) \geq \text{end}(i_1)\)
for every dependency pair) and to capacity at every time (formulation in
Appendix E.1 of the supplementary material)---the specified, not
shipped, scheduler's objective.

\subsubsection{Static and Dynamic
Optimization}\label{static-and-dynamic-optimization}

\textbf{Static optimization.} Static optimization employs several
techniques:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Peephole Optimization}: \(\text{PH}(i_1, \dots, i_n)\) returns
  \(\text{opt}(i_1, \dots, i_n)\) if a matching pattern exists,
  otherwise the window is left unchanged.
\item
  \textbf{Dead Code Elimination}:
  \(\text{Live}(i) = \text{Use}(i) \cup (\text{Live}_{\text{out}}(i) - \text{Def}(i))\).
  The two shipped passes approximate this fixpoint at different
  conservatism levels: the \emph{compiler} pass (formal streams) removes
  a side-effect-free instruction when no live consumer depends on its id
  or any declared output, while the \emph{trace optimizer} pass
  (executable instructions) keeps any instruction declaring at least one
  output---executable traces lack the formal dependency annotations that
  make output-consumption analysis exact. Section 5.3 exercises the
  former; Section 5.4 the latter.
\item
  \textbf{Instruction Combining} (the named candidate rules---textbook
  mnemonics, illustrative only, not shipped opcode names; listed in
  Appendix D.10 of the supplementary material---are specified and not
  registered: Section 4.1.3's only shipped write path into the rule set
  is the promotion gate of Section 3.3.1; the built-in pairwise
  compatibility combining is active, and it is what the hot-path trace
  re-optimization of Section 5.4 applies).
\end{enumerate}

\textbf{Dynamic optimization.} Dynamic optimization in the shipped
runtime is \textbf{repetition-triggered and threshold-based}; it does
not (yet) respond to load or performance signals:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Hot Path Detection} (implemented, two shipped modes): the
  default \texttt{exact} mode keeps a monotone counter per exact
  instruction sequence (\texttt{path\_id} = the ordered join of
  instruction ids) and flags a path hot when its count exceeds a
  configurable threshold \emph{and} its most recent recorded success
  rate is at least a stability bound (0.9 by default),
  \(\text{Hot}(p) \iff \text{count}(p) > \theta \land \text{success}(p) \geq \alpha\)---no
  windowing, no load signal.

  The opt-in \texttt{ema} mode instead triggers on recent execution
  share, over bounded per-path state (Section 4.2.2).
\item
  \textbf{Trace Optimization} (implemented): once hot, the cached
  sequence is re-optimized by the static pass machinery---peephole,
  dead-code elimination, instruction combining---bounded to a fixed
  number of passes; the runtime then serves the shrunken form for
  subsequent executions (demonstrated end-to-end in Section 5.8).
\item
  \textbf{Trace Formation and Adaptive Recompilation} (specified, not
  implemented): sub-trace extraction from observed frequency profiles,
  and performance-triggered recompilation (\texttt{should\_recompile}:
  execution count above threshold \emph{and} observed performance below
  expectation) remain design-level. The shipped runtime re-optimizes the
  whole cached sequence once per recording after the threshold is
  crossed, with no performance feedback loop.
\end{enumerate}

Two consequences of the shipped design now have shipped remedies the
default does not enable: exact keying means trace diversity
(similar-but-not-identical sequences) never accumulates a shared
count---the \texttt{ema} trigger relaxes the threshold to recent share
but stays per-path keyed (residuals in Sections 4.2.2 and 6.1)---and
hot-path state, formerly unbounded, is bounded by an LRU cap on tracked
paths (\texttt{max\_tracked\_paths}, 1,000 by default) that evicts
least-recently-recorded paths, hot ones included.

\subsubsection{Verification and
Analysis}\label{verification-and-analysis}

Optimization correctness is argued through:

\textbf{Theorem 3.6} (Pass-Pipeline Soundness, extending Theorem 3.4):
For any optimization transform T composed of the pass pipeline's
rewrites,
\(\forall p \in \text{Program}: \text{sem}(T(p)) \equiv \text{sem}(p)\).

\emph{Proof sketch}: semantic preservation for each atomic
transformation (the atomic-rewrite lemma, Appendix C.2) composes across
transformations by the compositionality lemma (Appendix C.3);
hazard-free pipeline execution is \emph{not} part of this theorem---it
is Theorem 3.5 (Appendix C.5), invoked separately; this theorem's
contribution is the rewrite layer.

\textbf{Performance Model} (specified; the benchmarks of Section 5
measure latency and token counts directly and do not evaluate it): the
modeled cost of a program sums, per instruction, base cost plus overhead
minus an optimization gain that aggregates each optimization's benefit
weighted by its application rate (both formulas in Appendix E.1 of the
supplementary material).

\subsection{Capability Assessment}\label{capability-assessment}

Agents are heterogeneous: an agent may be strong at reasoning but weak
at tool use, or vice versa. To make such differences explicit---and to
give the multi-agent coordinator of Section 5.6 a principled basis for
agent selection---AgentISA includes a capability assessment subsystem,
implemented as \texttt{CapabilityProfile} in
\texttt{agentflow.core.isa.capability}.

\textbf{Definition 3.9} (Capability Profile): A capability profile of an
agent \(a\) maps each capability domain \(D\) (the shipped enum carries
eight domains: reasoning, memory, generation, optimization,
specialization, coordination, security, robustness) to a score--weight
pair,
\(\text{Cap}(a) = \{(\text{dom}_k, s_k, w_k) \mid \text{dom}_k \in D\}\):

where each domain carries a score \(s_k \in [0, 1]\) and a weight
\(w_k \geq 0\) reflecting the domain's importance in the current
deployment context.

\textbf{Implementation status.} All three layers ship: the aggregation
and selection mechanisms (\texttt{CapabilityProfile},
\texttt{get\_overall\_score}, and the coordinator's threshold selection)
and---replacing the former stub---the instruction-level metric
extraction itself. The seventeen \texttt{\_measure\_*} functions of
\texttt{agentflow.core.isa.capability} extract signals statically from
\texttt{FormalInstruction} declared metadata: category labels,
dependency edges, parameter schemas, pre/postconditions, and declared
outputs; working-memory complexity as the largest declared input arity
(saturating at four); and resource economy as the inverse of the
declared footprint. Extraction is deterministic, side-effect-free, and
conservative: absent declarations score zero. The mechanics are pinned
by unit tests (\texttt{tests/core/isa/test\_capability\_metrics.py},
\texttt{test\_capability\_pipeline.py}), including the double-weighting
guard. One wiring gap remains, disclosed: \texttt{assess\_capabilities}
still has no production call site---the coordinator's selection path
receives injected \texttt{DomainScore} values (Section 5.6's tests
inject them directly).

Assessment proceeds in three steps:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Domain metric computation.} For each domain,
  \texttt{assess\_capabilities} computes a set of
  \texttt{CapabilityMetric} values from the agent's instruction set by
  static extraction, reading declared metadata only: no execution, no
  live probing.
\item
  \textbf{Domain aggregation.} Metrics are aggregated into a per-domain
  \texttt{DomainScore} as a confidence-weighted mean, matching the
  shipped \texttt{\_compute\_weighted\_score}:
  \(s_k = \frac{\sum_{m \in M_k} v_m \cdot \text{conf}_m}{\sum_{m \in M_k} \text{conf}_m}\),
  where \(M_k\) is the metric set of domain \(k\), \(v_m\) the metric
  value, and \(\text{conf}_m\) its confidence; an empty metric set
  scores \(0\), and zero total confidence degenerates to the unweighted
  mean. The domain weight \(w_k\) is deliberately absent here---it
  enters only once, at the top level (an earlier double-counting form
  was removed before any reported figure; artifact notes, supplementary
  F.8).
\item
  \textbf{Overall score.} \texttt{get\_overall\_score} computes the
  weighted mean across assessed domains,
  \(S(a) = \frac{\sum_{k} w_k \, s_k}{\sum_{k} w_k}\), falling back to
  the unweighted mean when all weights are zero.
\end{enumerate}

Three properties of this design deserve emphasis. First, it is
\textbf{static rather than live-probing} (runtime statistics and
cross-instruction dataflow-consistency checks remain outside its scope).
Second, it is \textbf{compositional}: fusing or eliminating instructions
during compilation (Section 3.4) changes the profile predictably, and a
production deployment would re-assess after optimization (the shipped
coordinator does not yet do so). Third, it directly serves coordination:
the agent-selection predicate in Section 5.6 chooses the highest-scoring
agent above a capability threshold for each task, subject to the
security policies of the \texttt{SecurityMonitor}---whose exercised
selection path still receives injected scores, as disclosed above.

The scope of this subsystem is limited: \texttt{CapabilityProfile}
assesses \emph{declared instruction-level capability}, which correlates
with---but does not measure---end-to-end task performance. Cross-model
behavioral comparison at benchmark level is the domain of evaluation
suites such as BFCL {[}17{]} and AgentBench {[}29{]}; the two views are
complementary.

\subsubsection{Instruction Selection
Implementation}\label{instruction-selection-implementation}

We implement the tree-pattern matching approach of Section 3.4.3
(Definition 3.8) as dynamic programming over the IR tree, in the
classical manner of bottom-up instruction selection {[}33{]}. The
MATCH-TREE selector ships in
\texttt{agentflow.core.isa.instruction\_selector} as an \emph{opt-in
strategy} (\texttt{selection\_strategy="dp"}, engaging only when the
input carries an \texttt{ir\_tree}; a catalogue instruction declares a
multi-node pattern via \texttt{params{[}"spanned\_child\_ops"{]}}),
following the Appendix D.1 recurrence exactly and exposing the DP table
and root-first covering of Theorem 4.1. The \emph{default}
(\texttt{selection\_strategy="heuristic"}) remains the name-overlap
heuristic matcher, unchanged---so every benchmark number in Section 5 is
produced under the default and none depends on tree-pattern selection.

\textbf{Theorem 4.1} (Selection Optimality, shipped opt-in selector):
Given a set of context-local patterns P and an IR tree T, the MATCH-TREE
algorithm computes the minimal covering cost; the covering itself is
read off the \texttt{selected} table afterwards, by walking from the
root and skipping subtrees spanned by the chosen pattern.

\emph{Proof sketch}: by induction on tree height; the recurrence sums
only over children not covered by the candidate pattern, so minima
compose (full argument, with the context-locality side condition, in
Appendix D.1). This theorem is a property of the shipped opt-in
selector, not of the default heuristic; no optimality claim is made for
the default path.

\subsubsection{Pipeline Scheduling
Implementation}\label{pipeline-scheduling-implementation}

We \emph{specify} the pipeline scheduler following the
instruction-scheduling formulation of Section 3.4.3 (Deps and resource
capacity) and the correctness conditions of Theorem 3.5 (Section 3.4.2),
with hazard detection and resource-constrained issue in the style of
classical pipeline scheduling {[}34{]}. \textbf{This cycle-accurate
scheduler is design-level}: the executed runtime path is the sequential
and parallel-grouped dispatch produced by the compiler's grouping pass
(Section 4.1.3); no benchmark in Section 5 exercises a cycle-accurate
schedule. The specified scheduler is listed in Appendix D.2.

Schedule verification checks the dependency-ordering condition (S2) of
the formal model (Theorem 3.5, Appendix C.5), with the edge convention
of Section 3.4.3---\((i_1, i_2) \in \text{Deps}\) means \(i_1\) must
finish before \(i_2\) starts. The check as written,
\(\forall (i_1, i_2) \in \text{Deps}: \text{slot}(i_2) > \text{slot}(i_1)\),
is equivalent to \(start(i_2) \geq end(i_1)\) only under the
\textbf{unit-slot model} the shipped scheduler assumes---one slot per
cycle, every instruction occupying exactly one slot. Admitting
multi-cycle latencies would require an explicit \(start\)/\(end\)
comparison (or interval slots); that extension remains the specified
component of Section 4.1.2. S1 (exactly-once dispatch) and S4 (in-order
commit) hold by construction of the scheduling loop, and S3 (group
non-interference) is enforced by the grouping check.

\section{Empirical Evaluation}\label{empirical-evaluation}

We evaluate AgentISA with a reproducible microbenchmark suite
(\texttt{examples/benchmarks/isa\_microbench.py}) and a multi-agent
functional test suite, under the scope stated at the end of Section 1.3.

\subsection{Methodology}\label{methodology}

\subsubsection{Instrumentation: Mock LLM
Backend}\label{instrumentation-mock-llm-backend}

All experiments route model inference through a \texttt{MockLLMBackend}
that counts each \texttt{infer} call as one simulated LLM API round trip
and charges a fixed 80 ms simulated latency per call to a simulated
clock. It never sleeps and never contacts a live model, so every ``API
call'' is observable, deterministic given a seed, and reproducible
without network access or inference spend. Everything \emph{around} the
backend is real: the cache, compiler, and optimizer are the production
\texttt{agentflow.core.isa} implementations (\texttt{InstructionCache},
\texttt{InstructionCompiler}, \texttt{OptimizationManager}), exercised
through the same code paths a deployment uses.

\subsubsection{Workloads}\label{workloads}

Workloads are synthetic and seed-controlled:

\begin{itemize}
\tightlist
\item
  \textbf{Caching}: 2,000 tasks from a discrete distribution over 50
  instruction templates \(\times\) 20 parameter values, popularity
  Zipf-distributed with exponent \(s \in \{0.5, 1.0, 1.5\}\). Three arms
  share instrumentation (Section 5.2): no cache, the
  \texttt{InstructionCache}, and a naive exact-response dict keyed on
  the request payload.
\item
  \textbf{Static compilation}: random sequences of length 50, 200, and
  1,000 from \texttt{synthetic\_formal\_sequence}
  (\texttt{examples/benchmarks/isa\_microbench.py}; short enough to
  audit line by line). Each of the first \(n-1\) slots is drawn
  independently: with probability 0.25 a \emph{dead} instruction
  (side-effect-free, \textbf{no declared outputs, hence no
  consumers}---removable by construction, planted not inferred); with
  probability 0.55 a \emph{pure} instruction (side-effect-free, one
  declared output \(v_i\), consumed \textbf{only by the final sink},
  fusable next to a same-type pure neighbor); otherwise
  \emph{side-effectful} (always live, never fused or removed). The
  \(n\)-th slot is a side-effectful \emph{final sink} depending on
  exactly the set of all pure outputs, so every pure instruction has a
  downstream consumer and no pure output is deleted as dead. The
  attributes are disjoint and jointly exhaustive per slot; the passes
  find the planted DCE/fusion targets, so the measured reductions are
  properties of this workload family, not of arbitrary agent programs.
\item
  \textbf{Dynamic optimization}: instruction traces of length 100
  recorded for up to 200 iterations per seed, hot-path detection active
  (threshold 50 recordings). Each trace uses the static arm's slot-draw
  shape at a different mix---dead 0.30, pure-with-output 0.50,
  side-effectful 0.20---plus a side-effectful final sink depending on
  all pure outputs (seed base 3,000; recorded in the results file's
  config). With post-recording counting and a strictly-exceeding
  trigger, the optimizer first fires on recording 51 (the run's 0-based
  iteration 50), so each seed contributes exactly 51 recordings (50
  counted plus the trigger).
\item
  \textbf{Ablations}: two arms. The primary arm is \emph{paired}: it
  re-compiles the static-compilation sequences (identical seed base
  2,000) with fusion and dead-code-elimination toggled individually and
  jointly---a same-input decomposition of the 34.2\% headline. The
  secondary arm is an \emph{independent} draw, same distribution but
  seed base 4,000, a fresh-sequence replication (all-passes total
  35.0\%, within one standard deviation of the headline).
\end{itemize}

\subsubsection{Protocol and Statistics}\label{protocol-and-statistics}

Each synthetic-workload configuration (Sections 5.2--5.5) is run with 5
random seeds; we report mean \(\pm\) sample standard deviation. These
are \textbf{descriptive statistics only}: no hypothesis-test claims (no
p-values, no significance tests) anywhere in this paper. Five seeds
characterize variability across the tested workload instances, not
statistical significance or population-level generality. Section 5.2's
naive response-cache baseline shares the mock-backend instrumentation; a
formal \emph{inferential} comparison against full external systems
remains out of scope, and no such claim is made.

\subsubsection{Metric Terminology}\label{metric-terminology}

Several distinct quantities must not be conflated; each is defined once
here:

\begin{itemize}
\tightlist
\item
  \textbf{Effective-instruction reduction}---fewer \emph{effective}
  instructions in the compiled program (Sections 5.3/5.5); an
  instruction-stream property, not execution time.
\item
  \textbf{Dispatch-count reduction}---fewer dispatch operations at
  runtime, including parallel grouping's folding (Section 5.3); a
  runtime count.
\item
  \textbf{Trace shrinkage}---shorter traces after hot-path
  re-optimization (Section 5.4); the optimized trace's executed-state
  identity is verified separately there.
\item
  \textbf{Cache hit rate / call reduction}---fraction of calls served
  from the result cache; here the call-reduction ratio equals the hit
  rate by construction (Section 5.2).
\item
  \textbf{Simulated latency saving}---avoided-call counts \(\times\) the
  mock's fixed 80 ms (Section 5.2); derived, not measured.
\item
  \textbf{Measured latency/token saving}---wall-clock time and token
  counts against the real gateway (Sections 5.7--5.7.1); measured.
\end{itemize}

For context preservation (Theorem 3.3): \emph{extraction-time
preservation} is the extraction step's copy invariance; \emph{runtime
context validation} is the monitor's pre/post-dispatch constraint
checking---different properties, different coverage (Section 3.2.2
discloses the deletion blind spot).

\subsection{Experiment 1: Result
Caching}\label{experiment-1-result-caching}

\textbf{Research question.} How many simulated LLM API calls does
AgentISA's result caching eliminate, as a function of workload skew?

We execute 2,000 tasks per seed, with caching disabled and with the
\texttt{InstructionCache} enabled, measuring simulated API calls at the
backend; the reduction ratio and hit rate coincide by construction
(every avoided call is exactly one cache hit).

\textbf{Cache-key contract.} The shipped result cache keys an entry on
the (instruction, params) pair---realized as a params-only SHA-256
scoped per instruction instance---deliberately \emph{not} on model
identity/version, prompt-template version, tool schema, decoding
parameters, or ambient context. Soundness requires those factors held
fixed, which every benchmark here guarantees by construction (single
alias, fixed templates and decoding, fresh cache per arm); Section
5.7.1's classifier-keyed step hashes exactly the input dictionary its
prompt is built from, under the same discipline. A deployment changing
any of these factors must invalidate or namespace the cache. The
production cache isolates by TTL, LRU capacity, and never-cached
failures, and an opt-in strict namespace ships for this drift
(\texttt{CacheKeyNamespace} in
\texttt{agentflow.core.isa.instruction\_cache}): the key extends
(instruction, params) with model alias, template version, and a
canonicalized decoding hash, with isolation-not-eviction semantics; the
default key stays the params-only SHA-256, byte-identical to the
published hit statistics. \emph{Automatic} drift detection remains
absent, and no number in this paper runs under the strict key.

\textbf{Naive response-cache baseline.} A third arm runs an app-level
\emph{response} cache keyed on the exact request payload string---what
an exact-match cache in front of the backend keys on---implemented as a
plain dict with no AgentISA machinery. Across the three skews it issues
exactly the same call counts as the table's cached arm: \textbf{parity
with the \texttt{InstructionCache} to the digit}, because the
(instruction, params) key is already canonical on this workload. Parity
is the finding: on call reduction the instruction-level cache adds
nothing over exact-response caching---its value is reducing the program
before any request is issued (Sections 5.3 and 5.5), which a response
cache cannot express. Parity is also a property of this workload, not
the mechanism: under random param-insertion order the instruction key
hits 95.0\% versus an insertion-order response key's 7.3\%---a gap that
vanishes (95.0\%, 0.0 points) under a response key canonicalizing param
order, so the instruction key's advantage there is canonicalization
alone; under template churn the default key false-hits 48.3\% of calls,
which the strict namespace key (90.4\% hit, zero false hits) prevents
(supplementary I.4). Semantic/embedding caching remains out of scope
(Section 5.9).

\subsection{Experiment 2: Static
Compilation}\label{experiment-2-static-compilation}

\textbf{Research question.} How much does the compiler reduce
instruction sequences, and what do the different optimization levels
contribute?

We compile random sequences at four optimization levels and measure two
quantities, kept explicit: \textbf{effective instruction
count}---instructions remaining after fusion and DCE, a program-size
measure---and \textbf{dispatch count}---dispatches the runtime issues;
parallel grouping folds several independent instructions into one
dispatch without changing the effective count.

\textbf{Interpretation} (full table: supplementary I.3). Three
observations:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Effective instruction count reduction is level-stable}: BASIC,
  ADVANCED, and AGGRESSIVE produce identical reductions (34.2\% \(\pm\)
  1.8\% at length 200). BASIC's fusion and DCE already capture the
  available elimination gains; higher levels add \emph{scheduling}
  improvements, not elimination---ADVANCED and AGGRESSIVE coincide here,
  differing only on streams carrying combinable patterns.
\item
  \textbf{Dispatch count drops further with parallel grouping}: at
  length 200, dispatch falls from 131.6 (BASIC) to 74.0 (ADVANCED) with
  effective-instruction reduction unchanged---adjacent side-effect-free
  instructions with disjoint dependencies and outputs grouped into
  shared dispatches. The 74.0 figure is a scheduling reduction, not a
  further program-size reduction (an earlier pass folded more but on
  unproven non-interference---history in supplementary F.8).
\item
  \textbf{Gains are stable across sequence lengths}: 32.8\%, 34.2\%,
  35.4\% at lengths 50, 200, 1,000 respectively, tightest variance at
  length 1,000 (\(\pm\) 1.6\%); length does not materially change the
  opportunity structure.
\item
  \textbf{A non-planted-family control bounds the headline.} Over
  Section 5.10's corpus (100 workflows, 792 steps) the same compiler
  reduces 19.2\%, all dead-guard elimination: pure transforms there form
  dataflow chains, each of the 106 fusions absorbs a dead guard, no live
  pair passes the disjointness gate---the fusion share of 34.2\% belongs
  to the planted linear family (supplementary I.4).
\end{enumerate}

Effective-instruction reduction is again a \emph{program-size} metric:
it translates to simulated API-call savings only where eliminated or
fused instructions carry model inference; the caching experiment
measures the complementary reuse effect.

\subsection{Experiment 3: Dynamic Hot-Path
Optimization}\label{experiment-3-dynamic-hot-path-optimization}

\textbf{Research question.} Does the dynamic optimizer detect and
specialize repeatedly executed traces?

We record an instruction trace of length 100 for up to 200 iterations
per seed with hot-path detection active (Section 5.1.2). Once a path is
flagged hot, the runtime forms an optimized trace; \textbf{this
experiment measures that trace's length and re-executes it}, the replay
check verifying exact reproduction of the original trace's final state
(task-level artifact preservation on realistic streams: Section 5.8).

Across seeds, hot-path optimization shrinks the trace by \textbf{65.8\%
\(\pm\) 4.6\%}; the seed-to-seed spread (59.0\%--70.0\%) reflects which
sub-sequences each trace makes hot. As with the static experiments, this
is trace-length reduction on synthetic traces---workload-controlled
evidence that the loop functions, not a wall-clock speedup claim.

\textbf{Replay verification.} Each seed's optimized trace \emph{is}
re-executed---every instruction reads its declared dependencies from a
threaded state dict and returns deterministic bindings for its declared
outputs (side-effectful instructions leave per-id markers)---and its
final state is compared with the original's, executed the same way. The
states are identical in all five seeds (5/5; recorded per seed as
\texttt{replay\_state\_identical} in the results file), so the 65.8\%
shrinkage carries an executed-equality check at trace level---on the
deterministic mock, not against a live model; this is the same style of
check as Section 5.8's task-level byte-identity, applied to the
synthetic traces. Live-model behavior remains untested---no mock
experiment can address it.

\subsection{Ablation: Per-pass
Contribution}\label{ablation-per-pass-contribution}

To attribute the static gains we run the two ablations of Section 5.1.2.
The primary one is \textbf{paired}: it compiles the \emph{same}
sequences as Section 5.3 (identical seed base 2,000 and generator) with
fusion and DCE toggled individually and jointly, so per-configuration
differences are same-input paired differences---an exact decomposition
of the headline, not a replication:

The paired per-pass decomposition (table: supplementary I.3) gives
fusion+DCE = 34.2\% \(\pm\) 1.8\%---the headline itself, confirming that
these two passes account for the entire static gain at length 200. The
\textbf{paired interaction}, computed per seed as (fusion+DCE − NONE) −
(fusion − NONE) − (DCE − NONE)---34.2 − 21.6 − 24.5 = −11.9 points---is
−11.9\% \(\pm\) 2.0\% (per-seed −14.5/−9.5/−13.0/−12.0/−10.5 points):
the passes overlap---dead slots break fusion chains and fused pairs
absorb neighbors DCE would otherwise have removed individually---so the
sum of the single-pass gains (46.1 points) overstates the joint effect
by 11.9 points.

The secondary ablation is an \textbf{independent-draw replication} (seed
base 4,000, same distribution): fusion alone 21.9\% \(\pm\) 3.5\%, DCE
alone 24.1\% \(\pm\) 3.3\%, fusion+DCE 35.0\% \(\pm\) 3.7\%---the paired
structure reproduces on fresh sequences. Because dead instructions are
planted at rate 0.25, DCE's per-pass share is near-tautological for this
family---it measures that the pass finds the planted dead code,
precisely its function.

  authentication/authorization fails, violations are timestamped,
  declared data sensitivity is enforced (sensitive categories infer a
  high sensitivity level, benign ones pass at medium), resource access
  is open by default and restrictable by configuration.
\item
  \textbf{Collaborative instructions}: barriers wait for the declared
  participant count and time out on a missing peer; resource allocation
  rejects over-allocation and serializes concurrent requests; the
  workflow state machine accepts valid actions and rejects invalid ones
  and double starts; a research-team scenario runs end to end.
\end{enumerate}

These tests exercise the same production modules used elsewhere and are
fully deterministic (no LLM calls). They establish correctness of the
coordination machinery under the tested conditions; what they do not
establish is scalability under contention, crash recovery, or
adversarial inputs beyond the policy checks above---all future work
(Section 6).

\subsection{Live-Gateway Conformance Check of Result
Caching}\label{live-gateway-conformance-check-of-result-caching}

\textbf{Research question.} Does the caching mechanism behave
identically when the ``model'' is a real LLM behind a live gateway, and
how much \emph{measured} wall-clock time and token usage does it save?

\textbf{Setup.} We replace the mock backend with a real model behind a
local Anthropic-protocol gateway (TLS with an internal CA; alias
\texttt{claude-glm-5.3-flash}, a hosted reasoning-capable GLM model;
\texttt{max\_tokens=64}; sequential httpx, 90 s timeout, three bounded
retries---none occurred). Every other component is the production code
path: the same \texttt{InstructionCache} protocol, instruction objects,
and workload generator, with Section 5.2's instruction pool (50
templates) and parameter space (20 values).

\textbf{Scale.} With each round trip costing \textasciitilde2.2 s, scale
drops from 2,000 tasks \(\times\) 5 seeds to \textbf{200 tasks
\(\times\) 1 seed} per Zipf level (s in \{0.5, 1.0, 1.5\}): 1,040
measured round trips (plus one preflight) in 39.4 minutes. The seed pins
the task sequence exactly, so the workload is the one the expectation
below is computed from.

\textbf{An exactness property.} A cache hit depends only on the
(instruction, params) pairs seen so far---not on what the model returns.
In general an LRU-with-TTL hit also depends on wall-clock time and
capacity; under this benchmark none of that can bind: \texttt{max\_size}
= 100,000 (at most 200 distinct keys per arm), \texttt{ttl} = 3,600 s
(every cache-enabled arm completes in under seven minutes; the no-cache
arms run to 7.9 minutes and never consult a cache), a fresh cache per
arm, failed calls never cached. Hit/miss decisions are therefore a pure
function of the (instruction, params) sequence, \emph{computable without
any backend}; if the mechanism is correct the real run must reproduce
that sequence exactly---and at the recorded granularity (per-arm hit
rates and call counts) it does:

Per-call latency was stable across arms (p50 2.13--2.21 s, p95
3.06--3.54 s). Token savings are gateway-reported \texttt{usage}

binding constraint of \texttt{max\_tokens=64} in every call).

\textbf{Interpretation.} First, the mechanism transfers unchanged:
observed hit rates match the computed expectation exactly at every skew
level, so Section 5.2's synthetic results measure the cache, not a mock
artifact. Second, avoided calls convert into measured time and
tokens---14.1\%, 26.6\%, and 45.8\% of the no-cache arm's wall clock at
s = 0.5, 1.0, 1.5---tracking but not identical to the call reduction
(wall and token figures are measurements). At N = 200, one seed, the
wall-clock ratio is sampling-noise-dominated (the 17 avoided calls
average 1.7 \(\times\) the arm mean); the token ratio is the steadier
read. Third, the absolute hit rates (8.5--45.5\%) trail Section 5.2's
(59.5--79.6\%): repetition accumulates with task count---the
backend-free computation at N = 2,000 reproduces the Section 5.2 figures
(the gateway run stays at N = 200).

\textbf{Multi-model rerun.} The identical protocol re-run on a second
production model (\texttt{claude-doubao-seed-2.0-code}, replies
completing below the ceiling) reproduces the expectation exactly in all
three cells---8.5\%, 26.0\%, 45.5\%; calls 200 \(\rightarrow\)
183/148/109; p50 3.6--4.0 s (table: supplementary I.3). The exactness
property is model-independent by construction, so this rerun is a
conformance check of the implementation on a second platform, not new
evidence about model variation.

\textbf{Two-seed rerun.} A reduced-scale rerun (100 tasks \(\times\) 2
seeds per Zipf level) reproduced the computed expectation exactly in all
six (Zipf, seed) cells (hit rates, quota record: supplementary I.3).

\textbf{Scope of the claim.} This experiment is a conformance check of
the caching mechanism's implementation---one gateway, two model aliases
(one seed per alias at N = 200, plus the two-seed reduced-scale rerun:
supplementary I.3), sequential requests, no streaming---recording
per-arm aggregate hit rates and call counts; per-position identity
follows from the deterministic cache decisions above but is not
separately logged, and nothing here is a throughput, availability, or
dollar-cost claim. Sections 5.3--5.5 are structural, never dispatching
to the backend; Section 5.7.1 extends the real-gateway validation to
them via a cache-mediated protocol.

hot-path adoption preserve the observable semantics of an instruction
stream when the stream's LLM step is served by a real model---and what
do they measurably save on a live gateway?

\subsection{Controlled Four-Task System-Level

The mechanism experiments above measure sequences; Appendix H reports

\subsection{Limitations and Threats to
Validity}\label{limitations-and-threats-to-validity}

We enumerate the limitations of the evaluation explicitly:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Mock backend, not a live LLM.} The mock charges a constant 80
  ms per simulated call, returns deterministic responses, and covers
  Section 5.4's replay verification (final-state identity, 5/5 seeds)
  and Section 5.2's naive-cache baseline. The real-gateway experiments
  extend coverage to the cache's hit/miss reproduction with measured
  time/token savings (Section 5.7) and the compiled stream's zero new
  gateway calls and byte-identical artifacts (Section 5.7.1). Still not
  covered: multi-seed behavior beyond the two-seed rerun (Section 5.7),
  real deployment, caching under model nondeterminism, streaming,
  provider rate limits, and live-model quality beyond the Section 5.7.1
  rubric diagnostics (the four-task classification steps remain
  rule-based stand-ins).
\item
  \textbf{Synthetic workloads.} Zipf-distributed synthetic tasks
  reasonably model skewed agent workloads---but are a model; Section 5.8
  partially addresses this, and Section 5.10's generated-trace census
  does not (it characterizes the generator's own vocabulary). The
  cache-reduction figures (59.5--79.6\%) are exact for these workload
  families and should be read as \emph{skew-sensitivity curves}, not
  universal savings; uniformly novel tasks would see near-zero benefit.
  Section 5.8's four-shape characterization calibrates the 65.8\%
  synthetic headline downward with its 12.5--25.0\% per-task compile
  shrink and shows uniform reuse and closed-loop adoption---but the four
  tasks remain hand-constructed, not a production workload study.
  Section 5.12 adds recorded model trajectories: static reduction there
  is 0.0\% and cache reuse is 35.5\% across tasks but 1.5\% within one,
  so each headline is a bound of its construction, not a workload
  constant.
\item
  \textbf{Generated corpora do not establish realism.} The census corpus
  is itself a generator artifact---its 12-signature vocabulary,
  log-linear decay, and 98.5\% recurrence characterize the generator,
  not any production workload. The non-planted-family control
  (supplementary I.4) swaps planted linear sequences for the same
  generator's traces (19.2\% vs.~34.2\%)---a generated-versus-planted
  comparison; Section 5.12 supplies the recorded-trajectory arm.
\item
  \textbf{Capability correlations are small-sample consistency checks.}
  The domain-score correlations (Section 5.11) are computed on n = 25
  declaration-injection pools (generation n = 15), with scores and
  metrics derived from the same injected declarations---consistency
  checks, not calibration. The \(\pm\) 1.000 entries are step-function
  artifacts of declared-and-enforced gates, and no independent,
  live-model capability measure enters any correlation.
\item
  \textbf{No production end-to-end evaluation.} We have not deployed
  AgentISA in a production setting; the paper therefore contains no
  latency-under-load, throughput, availability, or dollar-cost
  measurements, and makes no such claims.
\item
  \textbf{No real cost data (tokens measured; pricing MODELED).}
  Sections 5.2--5.5 latencies are simulated (avoided calls \(\times\) 80
  ms); Section 5.7 measures wall-clock time and gateway-reported tokens;
  Section 5.7.1 prices measured tokens under three modes---no
  optimization, result caching, and a modeled provider prompt cache
  (cache-read discount 0.1). Prices are configurable list-price
  stand-ins; no dollar-savings claim is made. Approximate
  (semantic/embedding) caching remains out of scope and future work.
\item
  \textbf{Program-size metrics, not wall-clock time.}
  Effective-instruction and dispatch-count reduction are structural
  metrics: they correlate with---but do not equal---wall-clock
  improvements, which depend on per-instruction cost, available
  parallelism, and dispatch overhead.
\item
  \textbf{Descriptive statistics only.} Synthetic configurations use
  five seeds (Section 5.1.3); the real-gateway and system-level runs are
  single-seed by design (Section 5.7's two-seed rerun excepted); no
  hypothesis tests, confidence intervals, or significance claims are
  made---standard deviations indicate stability across seeds, nothing
  more.
\item
  \textbf{Functional, not performance, validation of coordination.} The
  43 multi-agent tests verify behavioral correctness under deterministic
  conditions, not throughput or scalability.
\item
  \textbf{No prompt-variant robustness evaluation.} Each experiment
  measures one authored instruction stream per configuration (Sections
  5.2--5.5, 5.8). Outcomes under prompt paraphrase---semantically
  equivalent requests yielding different (instruction, params) keys and
  responses---are unmeasured; the exact-match key design forfeits reuse
  there by construction, but the sensitivity is not quantified.
\end{enumerate}

Despite these limitations, each optimization mechanism is implemented,
active, and produces the claimed structural effects on workloads
designed to expose them.

\subsection{Generated-Trace Vocabulary
Census}\label{generated-trace-vocabulary-census}

This census characterizes the generator's own vocabulary; it does
\textbf{not} discharge the synthetic-workload threat of Section 5.9 (a
generated corpus cannot validate a hand-built benchmark's realism). We
analyze 100 seeded random-task stress traces---randomly shaped streams
through the production engine, not hand-picked---792 steps, 12
signatures (protocol and tables: supplementary Appendix I). The
empirical rank-frequency decay is flatter than classical Zipf yet
strongly log-linear (descriptive log-log slope 0.593; a 12-signature
vocabulary is too small to support a tail-exponent claim, so none is
made---supplementary I.3). 98.5\% of instances recur corpus-wide
(780/792)---reflecting the 12-signature vocabulary as much as the
generator; per-workflow repetition, 18.3\%, is more informative---so
reuse is cross-task vocabulary, not intra-task duplication (shape
census, fusibility counts: supplementary I.3).

\subsection{Mechanism Extensions}\label{mechanism-extensions}

Six experiments exercise opt-in mechanisms (protocols and tables:
Appendix I). \textbf{Capability calibration:} extracted domain scores
correlate with mock-backend behavior on declaration-injection pools
(Pearson r; n = 25 pools, generation n = 15): memory +0.948 (cache hit
rate), coordination −0.977 (dispatch compression---the negative sign is
the designed coupling: more declared dataflow edges, more fusion
barriers, less compression), reasoning −0.965 (fusion reduction),
generation +0.790; optimization −1.000 and security +1.000 are
step-function artifacts of declared-and-enforced gates---consistency
checks, not calibration; 2/8 domains, 9/17 metrics N/A (probe-evidenced;
per-metric table with n, p, and Spearman ρ: supplementary I.2).
\textbf{DP tree-pattern selection:} covering cost \(\leq\) heuristic on
20/20 random IR trees (ratio 0.361; time 0.950); gap size is
synthetic-pricing-dependent. \textbf{EMA hot-path detection:} 3/3
rotated variants promoted (exact: 0/3; Zipf recall per seed: {[}0.333,
1.000, 1.000, 1.000, 1.000{]} (mean 0.867)), zero false promotions on
one-shot diversity. \textbf{Strict security:} of 1,000 paired tasks,
fail-closed denies 400 policy-gap tasks fail-open admits; 0/200
normal-task false denials. \textbf{Cache namespacing:} 100\%
invalidation under template/decoding drift (legacy keys 100\% stale);
modeled cost under the result cache is no higher than under the modeled
provider prompt cache in 195/195 token-mix cells. \textbf{Parameterized
replay:} all 1,050 unseen-parameter replays match the oracle exactly.
Chain-enriched workloads amplify BASIC\(\rightarrow\)ADVANCED dispatch
reduction to 79.1\% (random-slots control 46.7\%---paralleling Section
5.3's 43.8\% random-sequence dispatch reduction (131.6 \(\rightarrow\)
74.0 at length 200; the control's 46.7\% is measured on its own
length-200 slots); protocol and per-seed tables: supplementary I.2),
AGGRESSIVE differing only in the advisory memory plan.

\subsection{Do the Reductions Survive Real
Traces?}\label{do-the-reductions-survive-real-traces}

Every number above comes from workloads we constructed. We therefore ran
the shipped compiler and result cache on 1,960 tool-call trajectories
recorded from real model runs (\(\tau\)-bench; GPT-4o and Claude 3.5
Sonnet; retail and airline; 14,285 calls), converted under a
conservative mapping: same-turn calls are independent, later turns
consume the preceding step's result, unknown tools are effectful, and
final-turn outputs are required so liveness cannot delete the answer.
Static reduction is \textbf{0.0\%} at BASIC and AGGRESSIVE---real traces
chain their observations, so no step is provably dead and no pure pair
provably independent, confirming Section 5.3's 34.2\% as a property of
the planted family. Reuse transfers conditionally: \textbf{1.54\%} of
calls hit within a task, \textbf{35.47\%} across the distinct tasks of
one run (retail 40.9--43.9\%, airline 13.8--18.4\%), and 79.24\% under
the benchmark's trial replay, which repeats identical tasks rather than
exhibiting workload repetition. Section 5.2's benefit therefore survives
on real workloads only where a cache is shared across tasks.

\section{Discussion}\label{discussion}

\subsection{System Limitations and
Challenges}\label{system-limitations-and-challenges}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Instruction-set coverage}: complex reasoning patterns are not
  yet naturally expressible (domain-specific extensions are likely
  needed), and maintaining consistency of pre/post-conditions and typing
  rules across extensions remains an open engineering challenge.
\item
  \textbf{Evaluation scope}: the quantitative evidence is primarily
  microbenchmark-based (Sections 5.2--5.5), supplemented by real-gateway
  spot checks (Sections 5.7--5.7.1) and the four-task characterization
  (Section 5.8); production end-to-end evaluation remains required
  before any deployment claim (Section 5.9).
\item
  \textbf{Performance bottlenecks}: cache memory consumption under large
  instruction universes; synchronization overhead in barrier-coordinated
  multi-agent execution; recompilation cost when hot-path thresholds are
  misconfigured; the \emph{default} hot-path detector keys on exact
  sequence identity, so trace diversity never accumulates counts (the
  opt-in EMA detector of Section 4.2.2 is the remedy, still
  exact-path-keyed---its denominator can be floored by one-shot tails);
  state is bounded by the LRU cap (default 1,000), but recency-only
  eviction can drop a hot path's state, not just cold ones.
\item
  \textbf{Integration challenges}: adapter maintenance as provider
  function-calling surfaces evolve; version management of learned
  instructions across LLM updates.
\end{enumerate}

\subsection{Security and Privacy
Considerations}\label{security-and-privacy-considerations}

AgentISA's implemented security layer is the \texttt{SecurityMonitor} of
Section 5.6, consulted by the coordinator before every assignment. One
shipped default deserves a call-out: \textbf{resource access is open by
default} and restrictable by configuration---a fail-open stance shifting
the burden onto the policy writer. The hardened inversion ships as an
opt-in strict mode (\texttt{SecurityMonitor(...,\ strict=True)},
propagated by \texttt{AgentCoordinator(...,\ security\_strict=True)};
default \texttt{False}, fail-open checks unchanged): strict denies
unregistered resources, malformed resource-access policies, and unknown
data sensitivity, recording each with a \texttt{(strict\ mode)} marker
(\texttt{tests/core/isa/test\_security\_failclosed.py}). A paired
posture matrix (1,000 tasks per mode, five seeds; Section 5.11)
quantifies the difference on the real code paths: fail-open admits all
400 unknown-sensitivity and incomplete-policy tasks that strict denies;
both deny the 200 unregistered-resource tasks, strict adding a
distinguishable reason class; both also deny the 200 malformed-registry
tasks (a malformed registry fails in either posture---the fifth cohort);
strict adds zero false denials on the 200 well-specified tasks, and
every strict denial is recorded (matrix: supplementary I.2). The 43
functional tests validate the implemented checks under configured
policies, not the default posture; nothing in this paper constitutes a
security certification. Beyond what is implemented, hardening
considerations---not claims about the current system: data privacy
(end-to-end data-flow tracking, privacy-preserving computation; Section
6.3.6), secure multi-agent communication channels, audit-log integrity,
and externally audited compliance controls all remain future work; the
system provides enforcement hooks, not certification.

\subsection{Future Research
Directions}\label{future-research-directions}

\subsubsection{Theoretical Foundations}\label{theoretical-foundations}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Formal semantics of agent instructions}: consolidating Section
  3.1 and Appendix B into one standalone semantics---instruction
  language, state space, reduction rules, type system; nothing in it is
  new machinery.
\item
  \textbf{Compositional reasoning}: a parallel-composition rule whose
  disjointness side condition mirrors the \(\parallel\)-typing rule of
  Definition 3.6, enabling modular verification and temporal property
  preservation (rule in Appendix E.1 of the supplementary material).
\item
  \textbf{Type theory for agent capabilities}: a capability type
  discipline with Basic/Composite/Emergent kinds and a composition rule
  \(a \circ b : \text{cap}_1 \otimes \text{cap}_2\) (Appendix E.1).
\end{enumerate}

\subsubsection{Advanced Instruction Set
Evolution}\label{advanced-instruction-set-evolution}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Self-modifying instructions}---a formal model for instruction
  evolution,
  \(I_{t+1} = f(I_t, \text{Performance}_t, \text{Context}_t)\) with
  \(f\) left abstract, under semantic-preservation,
  performance-monotonicity, and safety constraints.
\item
  \textbf{Context-aware optimization}---for each observed context,
  predict the instruction set's performance against a threshold, and if
  it falls short, select and accumulate a best rewrite variant. The
  programmatic sketch (OPTIMIZE-CONTEXT) is listed in Appendix D.9; its
  primitives are future work, not implemented machinery.
\item
  \textbf{Cross-model instruction mapping}: a universal mapping
  framework \(\phi_{A \rightarrow B}: I_A \rightarrow I_B\) with
  semantic preservation, performance bounds, and capability awareness
  stated as goals, not delivered guarantees.
\end{enumerate}

\subsubsection{Theoretical Performance
Bounds}\label{theoretical-performance-bounds}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Asymptotic analysis}: deriving cost bounds per composition
  operator---when does iterative composition \(i_1^*\) admit a
  closed-form cost model, and under what reuse structure does caching
  yield amortized \(O(1)\) effective cost per task? The microbenchmarks
  (Section 5) measure the constants empirically; the asymptotic theory
  remains open.
\item
  \textbf{Resource consumption models}: a calibrated model
  \(R(i) = \alpha C_{cpu}(i) + \beta C_{mem}(i) + \gamma C_{io}(i)\)
  with coefficients fitted against real deployments (Appendix E.1).
\end{enumerate}

\subsubsection{Capability Assessment:
Extensions}\label{capability-assessment-extensions}

The instruction-level capability assessment subsystem
(\texttt{CapabilityProfile}, Section 3.5) now ships at the static layer;
its wiring gap remains disclosed there. Two extensions remain future
work: (i) \textbf{benchmark-calibrated metrics}---correlating scores
with \emph{end-to-end} performance {[}17{]} {[}29{]} and grounding the
weights \(w_k\) therein; and (ii) \textbf{cross-model comparison
matrices}, a pairwise framework \(\Delta(M_1, M_2)\) over capability
dimensions for model selection.

\subsubsection{Emergent Behavior
Analysis}\label{emergent-behavior-analysis}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Collective intelligence modeling}: the open question is a
  formal metric for when multi-agent composition exceeds the sum of its
  members' capabilities.
\item
  \textbf{Learning transfer}: knowledge transfer across agents composes
  Section 3.3's mining-extraction-validation pipeline rather than new
  machinery---patterns mined from a source agent's traces would be
  adapted and re-validated before promotion.
\end{enumerate}

\subsubsection{Security and Privacy
Extensions}\label{security-and-privacy-extensions}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Information flow control}: the classical noninterference
  property
  \(\text{Secure}(P) \iff \forall s_1, s_2: L(s_1) = L(s_2) \implies L(\llbracket P \rrbracket s_1) = L(\llbracket P \rrbracket s_2)\),
  where \(L\) assigns security levels to states and outputs, stated for
  terminating runs (divergence and channel leakage out of scope;
  Appendix E.1).
\item
  \textbf{Privacy-preserving computation}: a direction, not a delivered
  mechanism---if computations over sensitive data were routed through
  per-step differentially private mechanisms, overall loss would follow
  a composition theorem over the per-mechanism
  \((\epsilon_i, \delta_i)\) parameters. We deliberately state no bound:
  which theorem applies and which mechanisms the runtime would expose
  are open design choices; the instruction contract is the natural place
  to carry such annotations once the mechanisms exist.
\end{enumerate}

None of the frameworks above is implemented today; Sections 6.3.3 and
6.3.4 are stated precisely enough to be falsifiable, while the remaining
sketches are programmatic.

\section{Conclusion}\label{conclusion}

This paper presented AgentISA, an instruction set architecture that
treats LLM agent behavior as a first-class compilable artifact. Our
contributions are:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  A formal instruction set with compositional semantics, a type system,
  and pre/post-conditions, with sanity results as design rationale
  (Theorems 3.1--3.3) and semantic-preservation arguments for the
  optimization and scheduling transformations (Theorems 3.4--3.6).
\item
  Agentic Calling, which lifts provider-specific function calling into
  reusable, provider-independent, cacheable agent instructions.
\item
  Trace-based instruction learning---frequency mining with deterministic
  action-signature grouping, developer-controlled promotion, and
  composite replay, with shipped schema-checked parameter binding
  (unseen-parameter replays exact on 1,050/1,050 cases;
  constructor-baked parameters excepted; Section 5.11).
\item
  A compiler and runtime applying classical optimizations---fusion,
  dead-code elimination, scheduling, and dynamic hot-path
  specialization---to agent instruction streams.
\item
  A multi-agent coordination layer with capability-threshold selection
  and a security monitor, now with an opt-in fail-closed mode.
\end{enumerate}

The evaluation shows the optimizations are real and measurable under
controlled conditions: 59.5--79.6\% simulated-call reduction from
caching, 34.2\% instruction-count reduction from static compilation,
65.8\% trace shrinkage from hot-path optimization (Sections 5.2--5.5),
real-gateway validations of the cache and the compiled pipeline
(Sections 5.7--5.7.1), a four-task characterization (Section 5.8), a
100-trace workload census (Section 5.10), six mechanism experiments
(Section 5.11), and 43 functional tests for the multi-agent layer. These
are microbenchmark and controlled-setting results, not production
end-to-end measurements; the threats to validity of Section 5.9 stand.

\textbf{Implementation status of the contributions.} For auditability,
the five contributions split by status: \emph{implemented and exercised
by the benchmarks} (instruction set and contracts, Agentic Calling,
result caching, fusion/DCE/grouping, hot-path detection and adoption,
the coordination layer with injected-score capability selection, the
security monitor); \emph{implemented with known limits, exercised by the
mechanism experiments but not the benchmark arms} (DP tree-pattern
selector, EMA hot-path detector, strict cache namespace, strict security
mode, parameter-binding composite replay, capability metric extraction);
\emph{implemented with known limits, still unexercised by any Section 5
experiment} (the bounded checker; runtime context validation); and
\emph{specified, not implemented} (cycle-accurate pipeline scheduling,
block-granular trace formation, adaptive recompilation,
symbolic-equivalence checking). The per-mechanism status table and the
full limitations of each entry are in supplementary F.9; Theorems 3.4
and 3.6 are conditional arguments for the implemented rewrites, Theorem
3.5 covers the shipped unit-slot dispatch, and the specified components
carry no verification claim.

AgentISA's longer-term significance is architectural: an
instruction-level contract for agent behavior makes agent systems
amenable to the discipline that transformed hardware and compiler
engineering---precise specification, portability across backends, and
semantics-preserving optimization. Establishing these gains on
production workloads and mechanically verifying the conditional
arguments are the immediate next steps.
